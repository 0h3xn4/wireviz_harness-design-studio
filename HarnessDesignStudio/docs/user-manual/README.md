## The pages

## How to read the pages

- **Commands** use a practice project called `wheel-link`, made with `harness-design-studio new wheel-link --template first-steps`. Put your own folder where you see `wheel-link` or `DIR`. Output blocks are real output of the tool. Numbers such as the model hash (shown as `<hash>`) depend on the project and the tool version; yours can differ.
- **Command names.** The command line tool is `harness-design-studio`; `harness` is a short alias that runs the same program, so older scripts keep working. The app is `harness-design-studio-gui` (alias `harness-gui`) when started from a terminal.
- **App steps** (menus, buttons, tabs) use the names that version 1.17.0 of the program shows. They were checked against the program's texts (`gui/strings.py`) and against the menus and buttons of the window started without a screen, in all three roles. Nobody watched the steps on a screen, so pages with app steps say "GUI, not run" where it matters.
- **Where things are in the window.** The rail on the left opens an area: **Next step**, **Home**, **Model** (the **Diagram** and **Devices** tabs), **Checks**, **Drawings** (the **Harness** tab), **Outputs** (the **Lists** tab), **Versions** (the **Versions** tab, called **Releases** before 5.1.0; **Revisions** before 3.0.0) and, at the bottom, **Settings**. The pages name the tab, as the **Go** menu does (Ctrl+1 to Ctrl+6; Ctrl+7 is Home, Ctrl+, is Settings). The user guide, section 4, describes the window.
- **Roles, Quick mode and modes.** These are separate choices. The **role** (**Systems engineer**, **Electrical engineer** or **AIT engineer**, in the **View** menu under **Role** and under **Settings > Editing**) decides how much is on screen and where a project opens; it replaces the *Simple* and *Full* workspaces of 1.7.0. As a **Systems engineer** a project opens on the Next step page, the project tree, the inspector and the Problems panel start closed, and the rail lists Next step, Model, Checks, Versions and Settings only (**Home** is still in the **Go** menu, Ctrl+7; **Drawings** and **Outputs** are reached with Ctrl+2 and Ctrl+3, the command palette, Ctrl+K, and the buttons of the Next step page, because since 1.9 the **Go** menu of this role leaves out **Go to Harness** and **Go to Lists**). As an **Electrical engineer** or **AIT engineer** a project opens where it opened before and every area and panel is there. A first start, a settings file with nothing stored yet, asks *Who are you working as?*; a settings file that already holds values gets **Electrical engineer** without a question. **Quick mode** (the **Role** button in the top bar, **View > Quick mode**) is a short layout on top of any role for a quick block diagram; see [Make a block diagram in five minutes](quick-diagram.md). The **mode** (**Guided** or **Expert**, in the top bar) decides only how much of a device and a link the diagram shows. Every page works in both roles; where a step needs a panel that the Systems engineer role has closed, the page says so: press **Show panels** in the top bar. To reach the Model area from the Next step page, press **Model** in the rail or Ctrl+1.
- **Since 5.0.0.** Projects are saved in format 5; a project of 4.x is upgraded once, by the editor's question or `migrate`, and afterwards versions 4.x open it read-only ([Upgrade a project](upgrade-a-project.md#9-from-format-4-to-format-5-500)). Format 5 holds the fields of the feedback of an electrical engineer: the segments of a cable connector may run to its mating face, with the depth of its part and backshell taken off each wire ([Lengths to the face](lengths-to-the-face.md)); a device pin may state its current, from which the current of a wire comes ([Define a device](define-a-device.md#the-current-of-a-pin-since-500)); a connection may join one pin to several (a junction), and the harness made from it gets a splice ([Connect two connectors](connect-two-connectors.md#a-junction-one-pin-to-several-since-500)); a shield end may say the pin its pigtail lands on and its backshell ([Edit a wire](edit-a-wire.md), [Enter the build data](enter-the-build-data.md#3a-cable-ends-and-shield-ends-since-500)); and a device may be marked as checked against its ICD ([Use the library](use-the-library.md#10-mark-a-device-as-checked)). A project without such data writes every file as 4.x did.
- **Since 4.4.0.** Names can take the signals of a device to that device. With **Signal names name the far device** in **Settings > Project** (or `config DIR --far-device-names on`; off until you set it), a pin or port name that starts with a device ID and `_`, `.` or `-` (`TTC1_TX+`) names that device: Generate gives each interface the port named after the device at its other end, **Choose port…** marks the ports named after another device, the Inspector warns under such an end, and **Link connectors** does not offer the pins of a third device. A project can keep a **Signal map** of its own signal names (`TXP` for `TX+`; in **Settings > Project**, or `config DIR --signal-map FILE`), which `import-pinout` and `import-netlist` apply, also inside a port. **Unassign from interface** keeps the names of a fixed pinout ([Generate harnesses](generate-harnesses.md), [Connect two connectors](connect-two-connectors.md), [Import data](import-data.md)). The file format does not change.
- **Since 4.3.0.** A reviewer has one place per harness. A project can hold its own review checklist (in **Settings > Project**, or `config DIR --review-checklist FILE`; empty until you set it). The build workbook has a sheet **Review** with the checklist, every finding of the harness with its state, the values still open, the sources and how a number is explained; the editor shows the same as the **Review** page, with tick boxes; **Release…** (or `release DIR HARNESS --ticked POINTS`) records the ticks in the comment of the release, and points not ticked never stop it; `explain DIR FINDING` explains one finding by its ID ([Release a harness](release-a-harness.md), [Export the outputs](export-the-outputs.md)). The file format does not change.
- **Since 4.2.0.** The design rule check has four electrical rules more, 43 in all: a signal pair that is not twisted, a signal that its interface type shields running in no shield, a wire that joins two signal levels your project keeps apart, and two outputs, or only inputs, on a wire drawn by hand ([Build a harness by hand](build-a-harness-by-hand.md#6-check-list-and-release), [Edit a wire](edit-a-wire.md)). The pairs of levels to keep apart are a table your project fills in; until then the level check checks nothing and says so ([See what the tool assumes](see-what-the-tool-assumes.md)). The file format does not change.
- **Since 4.1.0.** The build workbook and the harness plan have a sheet **Production**: one block per connector, with where each wire goes, its part, colour, gauge, length and the label at that end; every length heading says what it is measured from (*rear to rear*), and the plan's harness sheet prints over several pages ([Export the outputs](export-the-outputs.md#3-the-build-workbook-sheet-by-sheet), [Export the harness plans](export-the-harness-plans.md)). A new project starts in the label format `harness_device_connector` (`W001:MTQ1:J01`), which versions 4.0.x refuse, so the whole team updates at the same time ([Naming and title block](naming-and-title-block.md#what-a-label-prints)). The file format does not change.
- **Since 4.0.0.** Projects are saved in format 4; a project of 3.x is upgraded once, by the editor's question or `migrate`, and afterwards versions 3.x open it read-only ([Upgrade a project](upgrade-a-project.md#8-from-format-3-to-format-4-400)). A connector part or a device connector can hold the rows of pins on its face: **Edit rows…** in the Devices tab, the column **Pin row**, `pin-rows`; the check of power and return pins reads the face of such a connector ([Pin rows of a connector](pin-rows-of-a-connector.md)). `system/export.json` no longer has the older key `revision`.
- **Since 3.1.0.** The harness plan has the two search boxes of the users' template: type a text into `I3` (Function) or `M3` (Shielding) of the harness sheet, and every cell of that column in the rows of the near connectors that contains it shows in red bold ([Export the harness plans](export-the-harness-plans.md)). The file format does not change.
- **Since 3.0.1.** The editor opens nothing with the program your system uses: **F1** (**Help > User guide**) shows the guide in a window of the program, where its links move within it and a web link is copied to the clipboard; in the Export window and in **Exported files**, **Copy path** puts the path of the selected file on the clipboard, in place of **Open**. **Reveal in folder** still shows a folder in the file manager, and only a folder.
- **Since 3.0.0.** A harness has a version of three numbers, MAJOR.MINOR.PATCH (`1.0.0`, `1.1.0`), in place of a revision letter, and the screen and the files say *version*: the rail area is **Versions**, the button **New version…**, and a new version asks for its kind, major, minor or patch. The upgrade to format 3 makes each letter a version, the Nth letter N.0.0 ([Versions](versions.md)). A harness you drew can join wires at a splice ([Splices](splices.md)), and the export can write the harness plan of each harness, an `.ods` spreadsheet with formulas in the users' layout ([Export the harness plans](export-the-harness-plans.md)). The editor opens no browser: the link of a part or of a pinout's source is copied to the clipboard.
- **Since 2.4.0.** A new project starts with `per_connector_group`, so a device connector with links to several devices gets one plug and the harness branches; a project made before keeps its mode, and the editor offers **Make one harness that branches** once after **Generate** ([Branching harnesses](branching-harnesses.md)). The file format does not change.
- **Since 2.3.0.** A harness can branch: one plug on each device connector, branch points and segments with lengths. Generate makes one with the choice `per_connector_group` (**Settings > Project**); a harness you drew gets its tree in the **Routing** table, a new leg from a plugged port and *Join into one harness*; a harness with a branch point gets `segments.csv` and the *Routing* and *Segments* sheets ([Branching harnesses](branching-harnesses.md)). The program starts on **Home** and asks the role there, the tour of the first start is gone, and every window moves on its own ([Choose your role](choose-your-role.md#choose-and-change-your-role)). The file format does not change.
- **Since 2.2.0.** A project follows its device library: a folder of device files, one device each (`OBC1.device.json`), that the project names in `device-libraries.json`. A device added from it keeps an import record of its file; the program says when the library has a newer version, shows what changes and takes it only when you ask: `libraries`, `add-device`, `update-device`, `save-device`, and in the editor the *Status* column, the line on a device, the notice and the review window ([Use the library](use-the-library.md#5-set-up-a-device-library-as-a-git-repository)). The file format does not change.
- **Since 2.1.0.** A device connector can carry several interfaces while it has room, and on a pinout that names its ports each interface gets the pins of one port: the **Port** column of the Devices tab and of `import-pinout`, the port of each end in the Inspector with **Choose port…**, and a full connector refused with the reason ([Define a device](define-a-device.md#a-connector-with-several-ports-since-210), [Generate harnesses](generate-harnesses.md#worked-example-three-rs-422-links-on-one-connector-since-210)). The file format does not change.
- **Since 2.0.0rc1.** Projects are saved in format 2. A project saved by 1.17.1 or older is upgraded once, by the editor's question or `migrate`; afterwards versions 1.x open it read-only ([Upgrade a project to format 2](upgrade-a-project.md)).
- **Since 1.17.0.** A project saved in an older file format is upgraded only when you agree: the editor asks once (*Upgrade*, *Open read-only* or *Cancel*), and `migrate DIR --dry-run` shows what an upgrade would do and writes nothing; the upgrade keeps a backup and a record and checks itself ([Use Git and CI](use-git-and-ci.md#other-helpers), [FAQ](../FAQ.md)). Nothing else on screen changed.
