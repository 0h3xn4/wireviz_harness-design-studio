# Outputs

`harness-design-studio export DIR` (or **Export…** in the top bar of the app) writes everything below into `DIR/outputs/`. The files are produced from the model only: the same model gives the same bytes. Nothing in them is typed in by hand; edit the model and export again.

**Format 3 (3.0.0, D-242).** A harness has a version MAJOR.MINOR.PATCH (`1.0.0`) where it had a revision letter, and the written files say *Version* where they said *Revision* (owner question Q23): the title block field *VERSION* and the header `Version 1.0.0  status draft` of a drawing, *Start here*, the change log, the version report (Q31) and the findings of the release consistency. `system/export.json` writes each harness with `version`; 3.0.x kept `revision` beside it with the same value (Q29), and 4.0.0 drops it with `format_version` 2 ([below](#json-export-systemexportjson)). The fixed list of these changes is `tests/fixtures/format3/word_changes.json`; `tests/test_format3.py` compares every file that 2.x wrote for the examples and test projects (the record `tests/fixtures/format3/before/`) with the file of this version after the stamp, the file name and that list (and the older name of `export.json` dropped, for 4.0.0), and finds nothing else. The harness plan (`<ID>_plan.ods`, [below](#harness-plan)) is written by `export --harness-plan`.

**Format 4 (4.0.0, D-251).** A connector part and a device connector can hold a row layout, the rows of pins on the face ([Pin rows of a connector](user-manual/pin-rows-of-a-connector.md)). The written files show it only where some connector has one ([below](#a-row-layout)): a project without a row layout writes every file as 3.x wrote it, apart from the older key `revision` that `system/export.json` dropped with `format_version` 2 ([below](#json-export-systemexportjson)).

The screen says *device*, the files say *unit*: the written files keep the word *unit* in their headings and texts (for example the *Unit* column of `mating_matrix.csv`), so that a file made now has the same bytes as one made by version 1.7.0. (The *Unit* column of the bill of materials is a unit of measure.) This page keeps the words of the files.

The main output of a harness is its **build workbook** (`<ID>_build.xlsx`, new in 1.7.0, decision D-169). The PDF and SVG drawings of the harnesses are **optional**: `export` writes none of them unless you add `--drawings` (in the app: the check box **Include the PDF drawings** in the Export window, ticked at the start only when the last export of the folder had them). An `export` without `--drawings` into a folder whose last export had the drawings removes them and says so. Everything else, the system diagrams too, is always written. For the `first-steps` example `export` writes 34 files and `export --drawings` 40 (not counting `manifest.json`; with 1.6.0 and earlier the same command wrote 38). The build data (decision D-170, below) adds nothing to a project that does not use it, and one file, `accessories.csv`, to each harness that has accessories. A harness with a branch point (2.3.0) gets one file more, `segments.csv`, and a sheet more in each of its two workbooks ([below](#a-harness-that-branches)).

```
outputs/
  manifest.json                    format, generator version, model hash, placeholder config, sha256 and size of every file
  harnesses/<ID>/
    <ID>_build.xlsx                the build workbook: the file to build the harness from (see Build workbook)
    <ID>_plan.ods                  the harness plan in the users' layout, with formulas (only when asked for; see Harness plan)
    drawing_A3_s<n>.svg            harness drawing, one SVG per A3 sheet (only with --drawings)
    drawing_A3.pdf, drawing_A4.pdf vector PDF, multi-sheet, same content (only with --drawings)
    wirelist.csv  pinouts.csv  bom.csv  mass_length.csv  tests.csv  labels.csv
    accessories.csv                the accessories of the harness (only when it has some)
    segments.csv                   the routing tree: one row per segment with its length and its wires (only for a harness with a branch point; 2.3.0)
    wireviz.yaml                   WireViz-style input (best effort, see below)
    <ID>.xlsx                      all tables of the harness as sheets (data, no layout; an Accessories sheet when it has accessories, and a last sheet Segments when it has a branch point)
  system/
    block_diagram.svg|pdf          units in zone lanes (each card with the band, badge and pictogram of its kind), interfaces and connections coloured by category, a key to the kinds
    harness_overview.svg|pdf       harnesses between units, solid = nominal, dashed = redundant
    bom.csv  mass_length.csv  mating_matrix.csv  traceability.csv  box_pinouts.csv
    changelog.csv  version_report.md    change log and per-harness history with differences between versions
    drc_findings.csv  drc_report.md
    asbuilt_report.md  asbuilt_report.csv   what was built and measured against the design and the test limits (only when the project has as-built records, S9)
    export.json                    the whole model in one documented JSON file
    provenance.json                which tool version, library and configuration made the outputs (see Provenance)
    system.xlsx                    BOM, mass and length, matrices, box pinouts, DRC findings, change log
    connections.csv                the connection list, one row for each pair of pins (only when the project has connections)
    connections.xlsx               the same as a workbook to hand over, with a summary sheet (only when the project has connections)
```

## Build workbook
`harnesses/<ID>/<ID>_build.xlsx` is a document to build the harness from; the other files are data. It holds only what the model holds: a missing value reads `to fill in` on an amber cell, and the tool puts no default there. Nine sheets, in the order of the work, and a tenth, *Routing*, for a harness with a branch point:

| Sheet | Content |
| --- | --- |
| **Start here** | Title, version (`Version 1.0.0 · status …`), status and stamp; `Ready to build` (yes when no check below is marked `TO FIX`; `yes (values rest on placeholder configuration: …)` while a configuration file is still a placeholder, with a *Placeholder files* line listing them); a table of checks with the number open and a status: wires without a length, wires without a gauge, wires without a colour and wires without a part (`TO FIX`), pins in use without a termination, wires without strip lengths (a wire that lacks either end), pins in use without a contact part and parts that are not approved (`NOTE`); the author, checker, approver and release date from the harness (`not set` until then); a row **Lengths** with the four short sentences, one row each, that say what every length of the workbook is measured from (4.1.0, worded from the project's settings: from the rear of a connector along the segments, through the centre of each branch point, to the rear of the other connector, and the service loops a generated wire adds); how to use the sheets, *Production* before *Connectors*; a sign-off block (cut and stripped, terminated, assembled and labelled, tested, released for delivery) to fill in by hand. |
| **Cut list** | One row per wire in cut order: thick before thin (smaller AWG first), then colour name, then length, the shorter first; a wire without a gauge comes last, and inside a gauge one without a colour or a length comes last in its group. Columns: **Cut (x)**, wire, colour (a coloured cell with the name and the IEC 60757 code, for example `red (RD)`), AWG, part, **Length (m), rear to rear** (`Length (m)` before 4.1.0), **Strip A (mm)**, **Strip B (mm)**, from, to, signal or label, shield groups (every group of the wire in natural ID order, joined by `;`, since 4.1.0), note. A totals row gives the number of wires and the length; after an empty row the last three rows are the length sentences of *Start here*, one each. |
| **Routing** | Only for a harness with at least one branch point (2.3.0), after **Cut list**: one row per segment in natural ID order (`W001-L2` before `W001-L10`): segment, from, to, **Length (m), rear or branch centre** (`Length (m)` before 4.1.0; `segments.csv` and the *Segments* sheet of `<ID>.xlsx` keep `Length (m)`; `to fill in` on an amber cell when it has none), number of wires and the wires, joined by `; `; then an empty row, a header and one row per branch point: its ID, its name and the connectors beyond it on each segment that meets it, on one line (`W001-L1: W001-P3, W001-P4; W001-L2: W001-P1`; a side with no connector says `(none)`). **Start here** lists the sheet under *How to use this workbook*. No new readiness check: a segment without a length already shows as *Wires without a length*. The last three rows are the length sentences. |
| **Production** | New in 4.1.0, after **Cut list** (and **Routing**), before **Connectors**: where each wire goes, at a glance, both ends. One block per cable connector in natural ID order (`W001-P2` before `W001-P10`), the splices last under the heading *Splices: each node joins the wires listed on it*. A block starts with a heading row: the ID, the part, the gender, `mates MTQ1-J01 (MTQ1:J01)` (the box connector's ID, then its device and name; `not plugged into a unit` when there is none), `label …` (the connector label in the label format in force) and the position of a label accessory on the connector; a loose end reads `open end, to fill in`, a splice `splice · 1 node`. Then one row per pin and wire: **Pin**, **Signal**, **Wire**, **Goes to** (the other end `CONNECTOR.PIN`, then in brackets what that connector plugs into, `(open end)` or `(splice)`), **Wire part**, **Colour** (as on the cut list), **AWG**, **Length (m), rear to rear**, **Length from** (`on the wire`, `locked` or `segments only, no service loops`; empty when the length is to fill in), **Label at this end** (the wire label's end A or end B text), **Shield group: here / far end** (every group of the wire, `W002-S3 overall shield: here backshell 360, far floating`; end A of a group is the `from` end of its wire with the lowest ID), and the tick column **Done (x)**. A run of spare pins is one row (`3 to 9`, `(spare)`); a pin with a signal or an interface and no wire reads `(no wire)`; a pin with two wires has two rows. A value the design does not hold reads `to fill in` on an amber cell. A page break comes before a block that would pass 42 rows; the last three rows are the length sentences. |
| **Connectors** | One block per cable connector in ID order: a heading row with its ID, part, gender, what it mates with (or `not plugged into a unit`) and its label, then a row for every pin: signal, function, wire, colour, AWG, where the wire goes, termination (`to fill in` for a pin in use that has none), contact size, **Contact** (the contact part of the pin; `to fill in` for a pin in use that has none), **Tool** (the crimp tool of that contact part) and the tick columns **Terminated (x)**, **Inserted (x)**, **Checked (x)**. A pin without a wire is grey and reads `(spare)`. |
| **Parts** | The rows of the harness `bom.csv` with the approval coloured and in words (green approved, amber pending, red anything else). |
| **Accessories** | The rows of `accessories.csv` with a column **Done (x)** in front: accessory, kind, part, target (a harness-level accessory shows `(harness)`), position, length (mm), quantity, note. With none the sheet says `No accessories entered.` |
| **Labels** | The rows of `labels.csv` with a column **Done (x)**. |
| **Tests** | The rows of `tests.csv`, and the empty columns **Measured**, **Result** (a list: `Pass` or `Fail`), **Initials** and **Date**. What is typed into them is not read by the tool; the results are recorded with the as-built sheet (`export-asbuilt`, `import-asbuilt`). For a harness with an override or a deviation (1.13) the sheet starts with the band *Overrides and deviations* (the title and the lines `OVERRIDE ...` and `DEVIATION ...` of *Start here*, one cell each, running over the empty cells to the right), an empty row and then the column headings, with no frozen panes (the headings repeat on every printed page), and a last column **Deviations** (the cell of `tests.csv`) when a test is about such a wire. Without them the sheet starts with the headings, as before. |
| **As-built** | Only for a harness that has as-built records, between *Tests* and *About*: what was recorded and how it compares with the design and the test limits (the rows of `system/asbuilt_report.csv` for this harness). |
| **About** | The stamp and the full model hash, as in the other workbooks. |

The sheets other than **Start here** and **About** keep a bold header row on screen; **Cut list**, **Parts**, **Accessories**, **Labels** and **Tests** have filters; the tick cells offer an `x` and turn green when one is entered; every sheet except **About** is set up to print on A4, landscape, with the stamp at the left of the footer, the sheet name in the middle and the page number at the right. There are no formulas. A cell that starts with `= + - @` is stored as text. The columns for results and ticks are for people: the tool never reads them back, and a build workbook in `outputs/` that was edited fails `verify --outputs` (`out_modified`, `out_build`), so work on a copy.

**Build data (1.7.0, D-170).** Strip lengths, contacts, crimp tools and accessories are optional values a person enters; the tool computes nothing from them, checks nothing and sets no default, so an empty value stays empty and reads `to fill in`. How to enter them: [`user-manual/enter-the-build-data.md`](user-manual/enter-the-build-data.md). The tables show them only where they are used (see Tables), so a project that does not use them keeps byte-identical files. Use: [`user-manual/export-the-outputs.md`](user-manual/export-the-outputs.md).

## Harness plan

**Written only when asked for** (D-242, [`ait/DESIGN_3.0_HARNESS_PLAN.md`](ait/DESIGN_3.0_HARNESS_PLAN.md) sections 3, 6, 7, 9 and 10): `harness-design-studio export DIR --harness-plan` (and the library calls `build_outputs(project, harness_plan=True)` and `api.export(folder, harness_plan=True)`) writes one OpenDocument spreadsheet per harness, `harnesses/<ID>/<ID>_plan.ods`, in the layout of the users' harness plan template, and lists it in `manifest.json` with its SHA-256 like every file; `--json` lists the plans under `harness_plans`. The option is one choice for all harnesses, as `--drawings` is. It is off by default: an output set without it is the set it always was. An export without it into a folder whose last export had the plans removes them and says so (*The harness plans of the earlier export were removed; add --harness-plan to write them again.*; `--json`: `harness_plans_removed`), as for the drawings (D-169). The re-export at a release keeps the choice of the export before it: with the plans only if it had them (`harness_plan_exported(folder)` reads the manifest). In the editor the choice is the check box **Include the harness plans (.ods), one per harness** of the Export window, ticked at the start when the folder's last export had the plans; an export from the window without it removes them and says so in the same words, with the check box for the option, and an export that runs without the window keeps the set of the folder's last export. The Cover shows the document data that `harness-design-studio document` sets (below). The build workbook stays the file to build a harness from; the plan is the document in the users' form. The tool never reads a plan back, and an export overwrites it, formulas and typed changes alike: work on a copy.

| Sheet | What it holds |
|---|---|
| **Cover** | Doc.-No., Version and Release of the harness's plan (`meta.document.plans`), the project name, the title (the plan's, else the document's, else `<project> Harness Plan`), the company, the stamp, *This file is written by Harness Design Studio. An export overwrites it; work on a copy.*, the notice and the contact lines (an e-mail address becomes a `mailto:` link). An empty field reads `to fill in` on an amber cell. The Version is the person's plan document version, else the harness version. |
| **Change_Register** | The entries of the change log of this harness, in ID order: Version, Sub-Version (the entry ID), Date, Name, Sheets (the harness sheet), Description (`in review`, `released`, `new version`, `version changed`, then the comment). |
| the harness, named after its ID | Above the header, the two search boxes (since 3.1.0): *Column Search String* and `#` in `I2:I3` over Function and `M2:M3` over Shielding (below). The header (system code, else the project name; the harness ID; `VERSION: v1.0.0 (draft)`; `[no SGND*]` in red while a device pin of the role signal ground on a connector of the harness has no wire), the title by formula (`Harness SYS-W001: OBC1 <–> STR1`), *used Connectors*, *used Cable Types* (the No. of wires in cable is `Part.conductors`; the length is the sum below) and *used Backshells*. Then one block per connector of the near end: the device side (Pin No., Function, Direction, Level, Description, copied from its `CON_…` sheet) and the harness side (Pinout, Function, Direction mirrored, Color, Cable / Type, Shielding, Length [mm], Level, and the far Cable / Type, Color, Direction, Function and one Pinout column per far connector), one row per pin of the device connector, in pin order, or, for a device connector with a row layout (4.0.0), row by row in the order of the layout and then the pins in no row in pin order, with *Pin row* in column A beside *Pin No.* (a formula that copies column F of its `CON_…` sheet; column A is outside the printed range `H6:U64`); a pin with no wire is a yellow row. Beside it, the far device side of each far device connector. Wires that end on no near pin are listed under *Further wires*. Then *Sum of length of cable type [mm]* (the lengths of a type divided by its wires per cable; `n wires without a length` beside it) and, under each far device side, the reference pinout of that connector with *Used in Row*. A text names `drawing_A3.pdf` when the export has the drawings. |
| **Notes** | The colour codes an end of this harness uses (a code marked as an example is headed *Example colour code from the users' template: check it against the supplier's pigtail code*), the note lines of `config/harness_plan.json`, and a legend: the Direction words, the yellow rows, `[no SGND*]`, which cells are formulas, where the register comes from. |
| **CON_&lt;connector&gt;** | One per device connector the harness plugs into, in ID order: Device, Connector ID, Interface Name, Connector Type, Number of Pins, Gender, Connector Name/Part Number and Connector Description (formulas, as in the template), Link to ICD (`source_doc`, linked to `source_link`), ICD version, then the pin table from row 18; a device connector with a row layout (4.0.0) has a column *Pin row* in F after *Description*, the row of each pin. The same, cell for cell, in every plan that has it. |
| **About** | The stamp, the full model hash and the notice, as on the About sheet of the workbooks; the stamp and the notice are also in the footer of every sheet. |

**The two ends.** The connectors of the harness are split into a near end (blocks of rows) and a far end (columns): a walk in breadth from the first connector in natural ID order puts the connectors joined by a wire on opposite ends; the end with more connectors is the near end, on a tie the end of the first connector. A loose end is a far column headed `open end, to fill in` with no `CON_…` sheet. **Splices** are left out of the walk: two connectors whose wires meet at a splice node are joined as if by a wire, so a Y harness through a splice has its two branches at the near end and the trunk at the far end. A near row's wire is the first wire on the pin, by ID, that reaches a far pin directly or through splices; the row fills every far pin it reaches. A row that reaches two or more far pins holds the far *Cable / Type*, *Color*, *Direction* and *Function* as values, each far wire's value in column order joined by ` + ` (`LVDS + `, an empty value keeps its place), and a far pin column with two pins of its connector holds `3 + 4`; a row through a splice to one far pin keeps the formulas of a straight row where they depend on the far pin only (*Direction*, *Function*, the far device side, the colour by pin code), and its far *Cable / Type* is that far wire's type as a value (under the rule `wire`, its colour too). *Further wires* also lists the wires beyond a splice, so every wire is in exactly one row. A harness without a splice gets the plan it had without them, byte for byte.

**The Direction words.** Role first: `PWR`, `PWR-RET`, `GND`, `SGND` (the role signal ground), `SHIELD`, empty for a spare pin; otherwise the direction `IN`, `OUT`, `IN/OUT`, else empty. On the harness side `IN` and `OUT` swap.

**Formulas.** Only where a cell follows other cells of the file: the copies of the `CON_…` sheets, the harness side Pinout, Function and Level, the mirrored directions, the colours by pin code, the title, the connector descriptions, the sums and the cable type lengths, and *Used in Row*. Each is OpenFormula from the closed list `IF`, `ISNA`, `VLOOKUP` (exact match), `MATCH` (exact match), `SUMIF` and the operators `&`, `=`, `/`, `+`, with direct references only, and each carries its value, so a reader that does not recalculate shows the same. A copy of an empty cell is an empty cell. Every other cell is a value of the design. The conditional format of the template (red where one end is `GND` and the other `PWR`) is on both Direction columns.

**Search boxes** (since 3.1.0, D-250). Type a text into `I3` (Function) or `M3` (Shielding / (Grouping)) of the harness sheet: a cell of that column in the rows of the near connectors that contains the text, without regard to case, shows in red bold, as in the users' template. The conditional format is `IF([.$I$3]="";0;ISNUMBER(SEARCH([.$I$3];[.I34])))` on each block, so an empty box marks nothing; `ISNUMBER` and `SEARCH` are allowed in a conditional format only, as `AND` and `OR` are. The file turns regular expressions and wildcards off (`table:calculation-settings` in `content.xml`), so LibreOffice reads a search text such as `TX+` as typed; Excel always reads `*`, `?` and `~` in it as wildcards. The box holds `#` when written, which marks nothing unless a cell holds `#`. An export overwrites a typed search text, like every other cell.

**Colours.** By default each end shows the wire's colour. With `"colour_rule": "pin_code"` in `config/harness_plan.json`, an end whose connector part a colour code lists gets the colour of its pin from that code's table on the Notes sheet; pins are matched exactly as text (`01` matches only `01`), and a pin the code does not list reads `to fill in`. A part may be in one code only (`validate`). `templates/pigtail-colour-code-EXAMPLE.csv` holds the colour code of the users' template as an example: it is not a standard and not a supplier's table, and it is applied only when a person takes it.

**The notes of `check`.** `harness-design-studio check DIR` gives a note `plan_colour_example` once for each colour code that still carries the example mark (`"example": true`; take it off once the code is checked against the supplier's pigtail code), and a warning `plan_colour_missing` once for each harness connector whose part a code lists (rule `pin_code`) and that has a wire on a pin the code does not list, which the plan reads `to fill in`. Neither stops generation or an export. A key of the document data that names no harness is the warning `plan_document_unknown`.

**The document data.** What the Cover shows comes from `meta.document` in `project.json`: `harness-design-studio document DIR` shows it; `--set system=…`, `--set title=…`, `--set company=…` and `--contact LABEL=VALUE` (at most eight lines; an empty value removes the line) set the project's part, and `--harness ID --set number=…|version=…|release=…|title=…` the part of that harness's plan; `--clear FIELD` empties a field. Each change is one undo step and goes into the change journal of a project that keeps one; a release does not lock it. The data is part of the design (a new phone number makes every plan out of date) and goes into no other output; it is in the project's Git history.

**The package.** Every entry is stored, not compressed, with fixed dates, so the same model gives the same bytes on every platform; `meta.xml` holds the title and the generator only.

**The check.** `harness-design-studio verify DIR --outputs` reads each plan that `manifest.json` lists and works it out again from the design, without the code that wrote it ([Verifier v2](#verifier-v2-coreoutputsverifypy), `core/outputs/verify_plan.py`). `out_plan_package`: the package is not as written (the entries `mimetype`, `META-INF/manifest.xml`, `meta.xml`, `styles.xml`, `content.xml` in that order, every entry stored with the fixed date, the manifest listing exactly the entries), or an XML entry holds a DOCTYPE or entity declaration, which is refused before it is read. `out_plan`: a sheet is missing, extra or out of order; a cell's value, value type, shown text or link differs from the design (the message names the sheet and the cell); a pin row is missing or a wire is in two rows; a plan belongs to a harness that is no longer in the design; or a harness has no plan in an export that has plans. `out_plan_formula`: a formula is not the one the design gives, is outside the closed list above (`AND`, `OR`, `ISNUMBER` and `SEARCH` only in a conditional format), or does not give the value stored with it; a conditional format whose formula or base cell is not the design's, and a plan whose `content.xml` does not turn regular expressions and wildcards off, are `out_plan_formula` too. `out_stamp` is read from the About sheet, and a plan changed after the export also fails `out_modified`. At most ten findings of one kind are listed per plan; the rest are counted. The styles, column widths, print set-up and how a program shows the file are not checked.

## As-built report (`system/asbuilt_report.md` and `.csv`)

Written **only when the project has as-built records** (`asbuilt/records.json`, [record what was built](user-manual/record-what-was-built.md)); a project without them writes exactly the files it always wrote, and the output hashes are identical. `asbuilt_report.md` is the report to print: the summary of each harness (state, values needed, recorded, missing, out of limit, within limit, not compared, different from the design, stale), then the lists of what is out of its limit, missing, different from the design, stale or not compared, and the notes and non-conformances of the records. `asbuilt_report.csv` has one row for each value: *Harness, Kind, Item, Value, Status, Actual, Designed or limit, Unit, Margin, Note*. The harness that has records also gets a sheet **As-built** (the rows of the csv for that harness) before *About* in its build workbook. The report says in its first lines that it is not a sign-off and does not say that a harness passed or is compliant. The files carry the stamp (the model hash does not change with the records), and the manifest has `asbuilt_hash` while there are records, so the outputs are *out of date* when the records changed although the design did not. The records are compared as [as-built results](models/asbuilt.md) describes; `harness-design-studio asbuilt DIR` prints the same lines.

## Connection list (`system/connections.csv` and `.xlsx`)
New in 1.9. A project that has **connections** (the links of two device connectors, pin to pin; `logical/links.json`) gets two more files in `system/`. A project without connections writes neither, and every other file of it keeps its bytes, so nothing changes for a project that does not use connections. They do not need a harness: `export` and the Export window work for a project that has connections and no harness, and the connection list is then the main document. (A project with neither a harness nor a connection still cannot be exported.)

`connections.csv` has one row for each pair of pins of each connection, connections by ID and pairs by the natural order of the pin of the first connector. The headings say *device*, not *unit* (this file is new, so no earlier file changes; the older files keep *unit*). A connection with no pair still has one row (the pin cells empty), so none is left out. The columns:

| Column | Content |
| --- | --- |
| `Connection` | the ID of the connection (`L1`) |
| `Name` | its name, empty when it has none |
| `From device`, `From connector`, `From pin`, `From signal`, `From role` | the first end: the device (its ID, the `unit_id` of the project files), the device connector, the pin, the signal on the pin (empty when none) and the role of the pin (`power`, `return`, `ground`, `signal`, `shield`, `spare`: the role a person gave it, else the one the signal name gives; empty for a pin without a signal) |
| `To device`, `To connector`, `To pin`, `To signal`, `To role` | the same for the second end |
| `Interface` | the interface type the pair belongs to, by name (`CAN`); `RS-422 or Ethernet` when several types fit equally; empty when no type has both signals. Worked out from the pins and never stored, the same as the diagram shows |
| `Harness` | the ID of the harness made from the connection with **Create harness**, empty before that |
| `Note` | the note of the connection |

The signals of the two ends are both written because they may differ (TX meets RX); the design rule *link-signal-mismatch* says when they should not. Nothing is invented: an empty cell means the model has nothing there.

`connections.xlsx` is the file to hand over, in the style of the build workbook (written by the same code, no formulas, equal model equal bytes, set up to print on A4 landscape with the stamp in the footer). Three sheets: **Connections** (the rows of the CSV file under a bold header that stays on screen), **Summary** (one line for each connection: `Connection, Name, From device, From connector, To device, To connector, Pairs, Carries, Harness, Note`; `Carries` reads like the diagram, `CAN, 2 wires; Power, 2 wires`) and **About** (the stamp).

The same connections are in two more files: the block diagram draws a line for each connection between two different devices, coloured and dashed by what it carries like an interface (a pair no interface type explains is grey), with the connection ID beside it; and `traceability.csv` lists them under the interfaces. In a project with connections the first heading of `traceability.csv` reads `Interface or connection` and a last column `Kind` (`interface` or `connection`) is added; a connection row has its ID, its name (or its two connectors), the interface type IDs its pairs belong to (`ethernet;rs422`), the two ends as `device/connector`, the harness made from it and the wires of that harness between the two cable connectors, and `Routed` is `yes` when it has such wires. A project without connections keeps the eight columns.

## Stamps
Every file carries `harness-design-studio <version> model <first 12 hex of the model hash>`: CSV and YAML as a first comment line (`# ...`), SVG in `<desc>`, PDF in the Subject, Markdown as the first line, XLSX on the About sheet (the build workbook also in the footer of every printed sheet and on **Start here**), JSON as `model_hash`. CSV readers must skip lines that start with `# `. Cells that start with `= + - @`, a tab or a carriage return and are not plain numbers are written with a leading `'` so spreadsheet programs do not run them as formulas (`+5V` is written `'+5V`, `-12` stays `-12`). The guard can be undone exactly: a cell that already starts with `'` followed by such a character gets one more `'`, and a reader removes exactly one. The XLSX files hold the text as it is (no `'`), stored as text, and are written without lxml (`OPENPYXL_LXML` is forced off before openpyxl is imported), so they are identical with or without lxml installed.


## The notice

Every written file also carries a short notice: the tool, its version and *Provided as is, without warranty. Verify before use.* (the one text of `compliance/legal/texts.md`, decision D-210). It is in these places:

| Format | Where the notice is |
| --- | --- |
| `.csv` and `.yaml` | the second comment line, under the stamp line (readers skip every line that starts with `#`) |
| `.md` reports | a note line under the stamp comment, before the title |
| `.xlsx` workbooks | the row *Notice* of the sheet **About** (after the two stamp rows), the description of the file, the print footer and, in the build workbook, the status line under its title (no row is added) |
| `.svg` and `.pdf` drawings | a line at the bottom of the title block of a harness sheet, or on the line of the stamp of a system sheet, and in the description of the file |
| `.json` and the open data | the file `README.txt` of the folder (these formats cannot hold a comment) |

`README.txt` in the outputs folder also repeats the disclaimer and the intended use. Pending and placeholder values stay marked as before: `pending`, `(example data)`, `PLACEHOLDER`, `Complete: no`, *not checked*. The file with the connection structure for WireViz (`wireviz.yaml`) holds no electrical value, so a value that is pending is left out and never filled in. A test per format (`tests/test_output_notices.py`) keeps this true. The notice was added after release 1.17.0: the written files of 1.17.0 and earlier do not have it, and the self-check does not require it of them.

## Stale detection
`manifest.json` stores the model hash. The editor compares it with the current model (quick check) and shows "up to date", "out of date" or "not exported". `harness-design-studio verify DIR --outputs` also hashes every file (detects edited or missing files) and re-checks content against the design.

In the editor, **Outputs > Lists** has an *Exported files* panel under the lists (version 1.3.0, D-157). It shows every file of the outputs folder with its state, SHA-256, document, harness, format, size and time written. The SHA-256 is that of the file **on disk**, worked out in the background, and the state compares it with the one `manifest.json` lists: *Matches export*, *Changed since export*, *Missing* or *Not in the export*. *Verify* reads the folder again; *Copy path* (to the clipboard), *Reveal in folder* (the folder, in the file manager) and *Copy to folder* act on the selected files; nothing there changes a file, and the manifest is never copied.

## Drawing
The **block diagram** (`system/block_diagram.svg` and `.pdf`, and the SVG, PDF and PNG of Export diagram) draws each device card with the looks of the window (since 1.16.0, [telling devices apart](user-manual/telling-devices-apart.md)): a band down the left edge in the colour of the family and a badge with the pictogram of the kind in the shape of the family, in the light theme's colours (the written file is paper), and a key to the kinds of the project beside the key to the lines. The kind is the one the tool reads from the name, the ID, the subsystem and the links, or the one a person set on the device (`Unit.kind`); nothing else decides it, so equal designs give equal bytes. The pictograms and the badge outlines are `<path>` elements (`M`, `L`, `C`, `Z`, absolute, at most three decimals); a pictogram is stroked with round ends and joins. The text of a card is still `<text>`: the ID in bold (set smaller, never cut, when it is long) and the name (cut with `~`). `harness_overview` (`.svg` and `.pdf`) keeps its plain boxes, and so do the harness drawings.

The harness drawing is written only with `export --drawings` (see the top of this page); the system diagrams `block_diagram` and `harness_overview` are always written. A set of files with the drawings of every harness or with none is valid for the output check. A wiring diagram: the connectors are tables on the left and the right (name, part, gender in words, pin count, the mating box connector, and for every used pin its number and signal), the wires run between them as curves in their wire colour, and between the connectors each cable (the wires of one connector pair) has a block that lists its wires (ID and IEC 60757 colour code) with the number of wires, gauge ("pending" when undecided) and length. Wires whose colour is not set are grey; a two-colour wire written `yellow/green` (or `green-yellow`) shows both codes (`YE/GN`) and is drawn grey; the colour comes from the wire (set by hand) or from the optional `wire_colour_by_signal` entry of `generation.json`, and the tool defines none. Wires are drawn on a dark outline and carry their colour code as text, so a greyscale print loses nothing. Shields are drawn as sleeves: the wires of a shield sit together in the cable block under a grey jacket that carries the shield's ID and kind and shows how each end is terminated (a solid bar for a 360 degree backshell connection, a lead for a pigtail, a cross for a floating end). Routing segments, spare pins and notes follow beneath, and the shields are also listed there. A title block closes every sheet (project, harness, title, revision, status, sheet n / N, stamp). Long harnesses continue on further sheets; a cable block that continues is marked "(continued)". The first sheet starts with a routing sketch (connectors and branch points as boxes, segments with lengths; schematic, not to scale; omitted above 14 nodes). Limits: the drawing is a wire-by-wire diagram plus this sketch, not a geometric layout of the branches. Author, checker, approver and date come from the harness (set by review and release, see change control); they show "-" until then. The title block field list comes from `config/titleblock.json` (placeholder, D-15): field names must be known (`project`, `harness_id`, `title`, `revision`, `date`, `author`, `checker`, `approver`, `sheet`, `status`), each at most once and written as text; anything else is a configuration error and the default fields are drawn. Any field may be left out, `sheet` too (the output check then does not look for the sheet number). A shield's end A is the start of its wire with the lowest ID in the whole harness, so the ends do not change sides between sheets. Pin IDs longer than about 12 characters are drawn smaller (down to 1.4 mm) and the pin column of that connector grows, so a pin ID is never cut. In the SVG every pin number and pin signal text carries a `data-ref` attribute (`pin/<connector>/<pin>`, `sig/<connector>/<pin>`) for the output check. PDF text is Windows-1252: characters outside it (for example the ohm sign or Greek letters) appear as `?` in the PDF while the SVG shows them; the export check lists them as a warning (`out_pdf_chars`). The harness overview draws one line for every pair of units that a harness joins.

## Tables
Numbers in the tables and in the YAML keep all their digits (the shortest text that reads back as the same value, no exponent; totals are rounded to 9 decimals so sums show no floating point noise). Only the text on the drawings is rounded (6 significant digits). Rows that share a key are in ID order whatever order the harnesses were created in (wire IDs in the pinouts are sorted, mating rows are ordered by connector and harness), so equal designs give equal bytes. A long ID is drawn in a smaller font instead of being cut (down to 1.4 mm for the 64 characters the model allows).

- `wirelist.csv`: Wire, Signal, Interface, From connector/pin, To connector/pin, AWG ("pending" when undecided), Part, Colour, Length (m), Shield group (every group of the wire in natural ID order, joined by `;`: a wire of a pair inside an overall shield reads `W002-S2;W002-S3`; since 4.1.0, before it only one group), Locked; then `EMC class` when interface types have one, `Requirement` when any interface has a requirement ID (1.10), `Label` and `Note` when a person gave a wire one (1.4.0), and `Strip A (mm)` and `Strip B (mm)` (From end, To end) when any wire of the project has a strip length (1.7.0), and a last column `Overrides` (`gauge_awg: reason; colour: reason`) when any wire of the project has an override with a reason (S4), so a project without them keeps the wire list it had. In the same way, only when they exist: the cut list of the build workbook of a harness with overrides has a column `Override` and its *Start here* sheet a section *Overrides and deviations*; the drawing has lines `OVERRIDE …` and `DEVIATION …` beneath the diagram; `drc_findings.csv` reads `deviation` in the column Waived for an error accepted as a deviation, and `drc_report.md` has a section *Deviations*. None of them holds a name or a time: those are in `journal.json`, which no output holds. The other harnesses of such a project get the two columns with empty cells.
- `pinouts.csv` / `box_pinouts.csv`: every pin of every cable / box connector, wires attached, spare flag. In `Signal` and `Interface` a cable pin that has none of its own shows those of the wires that end on it (several different values sorted and joined with `;`; a pin of its own keeps what it has; a spare pin stays empty; box connectors are unchanged) (1.10); then `Function` when a person gave any pin a function, and `Termination` (crimp, solder, unspecified) when any pin has one (1.4.0); then `Contact` (the contact part of the cable side) when any pin has one (1.7.0), then `Direction` (`in`, `out` or `bidirectional`; empty for a pin that has none) when any pin has a direction of its own (1.9.0); then a last column `Pin row` (the row of the pin on the face, empty for a pin in no row; 4.0.0, [below](#a-row-layout)) in `box_pinouts.csv` when any device connector of the project has a row layout, and in the `pinouts.csv` of a harness when a connector of that harness has one, so a project without them keeps the tables it had.
- `bom.csv`: one line per part and unit (`ea` before `m`), with the approval status. `ea` counts the connector parts, each contact part once for every pin that has a wire attached (1.7.0), and the accessory parts that have no length (the quantities added). `m` counts the wire parts by the metres known (plus the number of wires without length) and the accessory parts that have a length (length in mm times quantity, added, divided by 1000). For a wire part with `conductors` of 2 or more (a twisted pair: every wire that names it is one conductor of it) the metres are the sum of the wire lengths divided by that number, the metres of the cable (1.11). A part used both ways gets two lines. An accessory with no part adds no line.
- `accessories.csv` (per harness, only for a harness that has accessories; 1.7.0): `Accessory, Kind, Part, Target, Position, Length (mm), Quantity, Note`, sorted by ID. `Kind` is `sleeving`, `heat_shrink`, `label`, `backshell` or `other`; an empty `Target` means the harness itself.
- `segments.csv` (per harness, only for a harness with at least one branch point; 2.3.0): `Segment, From, To, Length (m), Number of wires, Wires`, one row per segment in natural ID order. `From` and `To` are connectors or branch points of the harness; the length is empty when it is not set; the wires are those whose one path between their connectors takes the segment, joined by `;`. The *Segments* sheet of `<ID>.xlsx` holds the same rows.
- `mass_length.csv`: known wire length (every conductor), mass of wires and cable connectors (a wire part's mass per metre is the mass of one metre of the part, so a part with `conductors` of 2 or more counts the wire length divided by that number; 1.11), margin, whether the data is complete, what is missing. Totals count only what is known and say so. Backshells, shielding, sleeving and tie-downs are not in the mass (the tool has no mass data for them); "Complete" refers to the wires and cable connectors only.
- `tests.csv`: continuity per wire, isolation per wire (against all others and shields) and per shield. Limits come from `generation.test_*` and read "TBD (placeholder)" until set. A last column `Deviations` exists only for a harness in which a test is about a wire that has an override or a deviation (1.13): the cell reads `override gauge_awg: reason; deviation current-over-wire: reason` (the field or rule, then the reason, cut at 120 characters), a shield row names the wire before each mark (`W001-001: ... | W001-002: ...`), and a test of any other wire has an empty cell. A deviation is about the wires named by its object: the wire itself, the wires of the interface for a finding on `INTERFACE.CONNECTOR` (contact current, connector voltage), the wires that end on a cable connector (temperature margin of a connector part). Without an override or a deviation of that kind the file is as before, byte for byte. The column holds no name and no time: those are in `journal.json`, which no output holds.
- `labels.csv`: one label per connector, two per wire (one per end); a wire label prints the wire's label (1.4.0) instead of its signal name when it has one. A connector label starts with the label of the connector (or, for a cable end without one, of the box connector it plugs into) and then says `<ID> mates <box connector>`; a harness with a label gets one more row of the kind `harness` (1.4.0).
- `mating_matrix.csv`, `traceability.csv`: box connector to cable connector; interface to harness and wires. While any interface has a requirement ID (`requirement_id`), `traceability.csv` gets a `Requirement` column after `Routed` (before `Kind` in a project with connections; a connection row leaves it empty) and the wire list gets a `Requirement` column after `EMC class` (the requirement ID of the wire's interface; empty for a wire without one) (1.10). A project with no requirement ID keeps both tables as they were.

## WireViz YAML
Each wire is written as its own one-conductor cable, with `connectors`, `cables` and `connections` in the structure WireViz reads. It is written from the model by this tool and has not been validated against the WireViz program (outside this project). Treat it as a convenience export.

## JSON export (`system/export.json`)
```
{ "format": "harness-design-studio-export", "format_version": 2,
  "generator": {"name", "version"}, "model_hash": "<64 hex>",
  "project": {"name", "description"}, "placeholder_config": [names],
  "units": [...], "interface_types": [...], "interfaces": [...],
  "box_connectors": [...], "harnesses": [...], "parts": [...],
  "field_units": {"harnesses[].wires[].length_m": "m", ...} }
```
Each list holds the model objects exactly as in the project files (sorted by ID); fields are described in `FILE_FORMAT.md`. `format_version` changes only for incompatible changes. **Since 3.0.0** each harness has `version` (`"1.0.0"`). 3.0.x wrote `revision` beside it with the same value, for scripts written for 2.x, with `format_version` 1. A part of category `connector` and a device connector carry `row_layout` (`{"rows": [["1", …, "11"], ["12", …, "21"]]}`, and `"rings": true` for the rings of a circular insert) while they have a row layout (4.0.0), as in the project files; the key is left out where none is set. **Since 4.0.0** (D-251, owner answer L4) the older name is gone and `format_version` is 2: a script that read `revision` reads `version`, which holds the same value. The output check compares each harness with the model as saved, so a file of 3.0.x (`format_version` 1, with `revision`) reads *does not match the design* until it is exported again.

**Units of the numbers (1.13, D-195).** `field_units` gives the unit of every numeric field of the file: the key is the path of the field (`[]` for a list, `.key` for an object key: `harnesses[].wires[].length_m`, `parts[].ratings.contact_current_a`), the value is the unit: `m`, `mm`, `A`, `V`, `ohm`, `g`, `g/m`, `degC`, `AWG` (the wire gauge, written as the plain AWG number, D2), or `none (what it is)` for a number with no unit (a count of pins, the number of conductors in one metre of a part, a flag, the format number). A rating a project names itself gets the unit its name ends in, or `not stated (...)`. The key `units` of the file holds the devices, so the new object has another name. The table is one list in the code (`core/outputs/export_units.py`), checked by a test against the fields of the model; the output check reports a number of the file that has no unit. A file written before 1.13 has no `field_units` and is still read and verified.

## Print
Dark colours and dash patterns carry every distinction (category, nominal/redundant), so greyscale prints stay readable. Tests check contrast against white (at least 3:1) for the system diagrams. Harness drawings draw wire colours on a dark outline and write every colour as a code (REQ-OUT-03).

## Change control in the outputs
`system/changelog.csv` lists every change log entry (column *Version*; the event *new version started*). `system/version_report.md` (called `revision_report.md` until 3.0.0; an export removes the old file) gives, per harness, the history and the differences between consecutive baselines and between the working design and the latest baseline. The manifest also stores `content_hash` (model hash without release bookkeeping) which the release gate compares; see DECISIONS D-104.

## EMC class on wires and labels

When at least one interface type has an EMC class, the wire list gets a last column `EMC class` and the wire labels end with `[EMC <class>]`, so personnel can see the category of every wire (ECSS-E-ST-20-07C 4.2.13.1 d). Projects without EMC classes get byte-identical files. The output verifier checks the column against the design.

## Provenance

`system/provenance.json` states which tool version and which design made the outputs: the model hash, the project name, the parts library (name, version, number of parts by approval status), every configuration file with its placeholder flag and a short hash of its values, and the counts of units, interfaces, harnesses and wires. There are no dates and no paths, so equal designs give equal bytes. The output verifier checks the placeholder flags and counts against the design. The WireViz-style YAML files are an export format only; WireViz is not used to make any output.

## Open data and the run record

The outputs above are what you build from. `harness-design-studio export-data DIR --out FOLDER` writes the numbers behind them as JSON and CSV (wire sizing, lengths, mass, bill of materials, rule results with actual, limit and margin, readiness, test limits, pin allocation, segmentation, findings, parts, settings, the configuration as used, and a provenance file) to a folder of your choice, so that a result can be reproduced from the files alone ([export the data](user-manual/export-the-data.md); the files are described in [`FILE_FORMAT.md`](FILE_FORMAT.md#open-data-files-and-the-run-record-not-part-of-a-project)). They are not part of `export`, are not listed in the manifest and do not change the hashes of the outputs.

No written output holds a time or a name, so the same design gives the same bytes. When you want the time, the operator, the tool and Python versions and the model hash of a run on record, add `--run-record` to `export` or `generate` (or `export-data`): `run_record.json` is then written beside the files, in the `outputs` folder, outside `manifest.json` and every hash. `verify --outputs` does not call it an unlisted file. Without the option no record is written.

The wire gauge is written as the plain AWG number in every output (the drawing, the lists, the workbook, the design rule report); its cross-section in mm² is shown beside it on screen and in explanations, and is a column of its own in the open data (D2, D-193).

## Requirement IDs on findings

`system/drc_findings.csv` ends with a column `Requirement`: the IDs of the standard requirements the rule serves (empty when the rule serves none). The Problems panel shows the same IDs under the explanation of a finding, and the design rule report prints them after it. The IDs are those of `compliance/requirements` in the tool's repository (`docs/RULES.md` lists them per rule).

## A loose cable end

A **loose end** is the end of a cable that is not on a connector yet (role `loose`, placeholder part `TBD-CONNECTOR`; [build a harness by hand](user-manual/build-a-harness-by-hand.md#a-cable-with-a-loose-end), decision D-201). The written files name it as an open end, and only in a harness that has one: a project without a loose end writes the same bytes as before (`tools.output_hashes --check` and `tools.numbers_snapshot --check` print *identical*).

| File | What a loose end looks like |
| --- | --- |
| `pinouts.csv` (and the Pinouts sheet) | Role `loose`, Mates with `open end`, Part `TBD-CONNECTOR (loose end)` |
| `labels.csv` (and the Labels sheet) | `W009-P2 open end` (with a name: `NAME (W009-P2 open end)`); in a custom template `{mates}` is `open end`. A wire label still names the pin, `W009-001 PWR to W009-P2.1` |
| `bom.csv`, `system/bom.csv` (and the Parts sheet) | no line for `TBD-CONNECTOR`; one line `(open end)`, category `connector`, description *Connector not chosen yet (loose end)*, approval *to fill in* (amber in the workbook), quantity the number of ends, unit `ea` |
| `mass_length.csv`, `system/mass_length.csv` | the end is never counted, whatever mass the placeholder part has; *Missing data* says `mass of open end W009-P2 (no connector chosen yet)` and *Complete* is `no` |
| `tests.csv` (and the Tests sheet) | a pin of the end reads `W009-P2.1 (open end)`; a continuity test with an open end, and an isolation test from one, expects `test when the end is decided` (never `continuous`); the limit is the one that will apply |
| drawing (SVG, PDF) | the connector table has a dashed outline, its part line reads `TBD-CONNECTOR (loose end), 4-pin` and its mate line `open end` (no gender) |
| build workbook, Connectors sheet | the head of the end reads `W009-P2 · TBD-CONNECTOR (loose end) · open end, to fill in`; *Start here* has the ninth check *Ends not decided* |
| `wireviz.yaml` | `type: "TBD-CONNECTOR (loose end)"` |
| as-built sheet (`export-asbuilt`) and report | no lot is asked for `TBD-CONNECTOR`; the row of the end says `open end: no connector chosen yet`; its tests are those of the Tests sheet |
| `system/export.json`, the open data | data as stored: role `loose`, part `TBD-CONNECTOR`, no `mates_with` (the open-data pin and BOM tables follow the CSV tables above) |
| `version_report.md`, `diff`, `compare` | the object is named *Loose end* instead of *Cable connector* (after the change; a plug reads *Cable connector* again) |

`explain` of a loose end says *Open end: no device connector and no part chosen yet* and its label `W009-P2 open end`; `explain TBD-CONNECTOR` explains the BOM line `(open end)`. The independent verifier words every row of this table again on its own and refuses a file that names an open end as an ordinary connector. The golden set of a project with loose ends is `tests/fixtures/outputs/loose_ends.json` and the text files in `tests/fixtures/outputs/loose_ends/` (`python -m tools.gen_output_goldens`).

## A harness that branches

A harness with at least one branch point (2.3.0, decision D-243, owner question B7; [branching harnesses](user-manual/branching-harnesses.md)) gets its routing tree in three places. A straight harness keeps its files and sheets byte for byte (`tools.output_hashes --check` and `tools.numbers_snapshot --check` print *identical* for every example harness without a branch point).

| Output | What it holds |
| --- | --- |
| `harnesses/<ID>/segments.csv` | One row per segment: segment, from, to, length in metres (empty when not set), number of wires, the wires joined by `;` ([Tables](#tables)) |
| *Segments* sheet of `<ID>.xlsx` | The same rows, as the last sheet, so the sheets before it keep their places |
| *Routing* sheet of `<ID>_build.xlsx` | The same rows with the length or *to fill in* (the heading `Length (m), rear or branch centre` since 4.1.0), then the branch points with the connectors beyond each side, after *Cut list*; **Start here** lists it ([Build workbook](#build-workbook)) |
| Drawing, wire list, pinouts, labels, BOM, mass and length, tests | Unchanged. The drawing already draws a routing sketch up to 14 nodes and lists the segments with their lengths. Without a splice every wire runs pin to pin, so one continuity and one isolation test per wire stay right |
| `system/export.json`, `wireviz.yaml`, `export-data` | Unchanged: they already carry the branch points and the segments |

No cell of the *Routing* sheet holds a line break (the sides of a branch point are on one line), so the workbook has the same bytes on Linux and Windows. The output check reports `out_routing` ([Verifier v2](#verifier-v2-coreoutputsverifypy)). The `flatsat` example has six harnesses with branch points (W001, W002 and W004 to W007), so its export writes six `segments.csv` files more than 2.2.0 did, and their two workbooks changed once. `harness-design-studio routing DIR HARNESS` prints the same rows ([CLI](CLI.md)).

## A splice

A splice (format 3, M6a; design `docs/ait/DESIGN_2.3_BRANCHING.md` section 6.5; [File format](FILE_FORMAT.md#format-3-versions-and-the-fields-of-the-harness-plan-300)) changes the files of its own harness only: every harness without a splice keeps its files byte for byte (`tools.output_hashes --check` and `tools.numbers_snapshot --check` print *identical*; no example holds a splice). A **net** is the set of pins that the wires of a harness join; a node of a splice joins every wire on it, and the pins of the net that are not on a splice are its **ends**.

| Output | What a harness with a splice holds |
| --- | --- |
| `tests.csv` and the *Tests* sheets | For a net through a splice, one continuity test per pair of its ends, `From` the first end and `To` the second with the splices of the net (`W003-P2.1 via W003-X1`), `Wire` the wires of the path between them joined by `;`; and one isolation test of the net, `From` its ends joined by ` + `, `To` *all other nets and shields*, `Wire` every wire of the net. They take the place of the tests of the wires of that net, at the place of its first wire; every other wire keeps its two tests |
| `wirelist.csv` and the *Wire list* sheet | A last column *Via*: the splices of the wire's net, joined by `;` (empty for a wire of a net without a splice). From and To name a splice as they name any connector |
| `pinouts.csv` | A splice is listed like a connector: role `splice`, no mate, one row per node |
| `labels.csv` and the *Labels* sheet | No label for a splice (it is inside the sleeve); its wires keep their two labels |
| `bom.csv` | One line per splice part, of category `splice`, counted per splice as connectors are |
| `mass_length.csv` | A splice is not counted under *Connectors*, and its mass only by the model `full_bom` (D-200), with the contacts and accessories; the default model leaves it out |
| *Connectors* sheet of `<ID>_build.xlsx` | The connectors, then the heading *Splices: each node joins the wires listed on it* and each splice in a block of its own (`W003-X1 · EX-SPLICE-1 · splice · 1 node`): a row per node with its signal, the wires on it, the colours, the gauges, where each goes, the termination (crimp or solder, else *to fill in*) and the tool of the splice part. A node has no contact, so it is not counted under *Pins in use without a contact part*. The cut list cuts each piece (each piece is a wire) |
| Drawing | A splice is a small node on its wires (a dark bar, a dot per node, the node numbers, its ID labelled `data-ref="splice/<ID>"` and its part), not a connector table; the lines beneath list each splice with its part and the wires on each node |
| `wireviz.yaml` | A splice is a WireViz connector of style `simple` |
| `system/export.json` | The splice as saved: a connector of role `splice` |
| `<ID>_plan.ods` (with `--harness-plan`) | The ends and rows follow the splices, and the wires beyond a splice are under *Further wires* ([Harness plan](#harness-plan), *The two ends*). The plan's own check (`out_plan`) names a missing row of a wire beyond a splice and a far pin cell that differs |

The output check works the nets out with its own code and words each of these again; a wrong cell is `out_tests`, `out_wire_differs`, `out_labels`, `out_mass`, `out_build`, `out_drawing` or `out_yaml` ([Verifier v2](#verifier-v2-coreoutputsverifypy)).

## A row layout

A row layout (format 4, 4.0.0; design `docs/ait/DESIGN_4.0_ROW_LAYOUT.md` section 7; [File format](FILE_FORMAT.md#format-4-the-row-layout-of-a-connector-400); [Pin rows of a connector](user-manual/pin-rows-of-a-connector.md)) changes the files only where a connector has one: a project without a row layout writes the same bytes as before (`tools.output_hashes --check` and `tools.numbers_snapshot --check` print *identical*; no example and no starter part holds one, owner answer L3). The rows of a connector are its own rows, else those of its part, else, for a connector of a harness, those of the device connector it plugs into; a name that is not a pin of the connector is left out, and a row keeps its number.

| Output | What a project with a row layout holds |
| --- | --- |
| `system/box_pinouts.csv` (and the Devices tab's *Pinout as exported*) | A last column *Pin row* while some device connector of the project has a layout: the row of each pin (`1`, `2` …), empty for a pin in no row and for every pin of a connector without a layout. The rows stay in pin order |
| `harnesses/<ID>/pinouts.csv` and the *Pinouts* sheet of `<ID>.xlsx` | The same column for the cable connectors while a connector of that harness has a layout; the pinouts of every other harness keep their columns |
| `export-pinout` | The column *Pin row*, before *Level* and the source columns, while a connector of the device has a layout, so the file reads back through `import-pinout` as no change; a device without one writes the file it wrote |
| `<ID>_plan.ods`, `CON_…` sheet | *Pin row* in column F after *Description* (heading in row 18, a row number from row 19) on the sheet of a device connector with a layout |
| `<ID>_plan.ods`, the harness sheet | The near block of such a device connector lists its pins row by row, in the order of the layout, then the pins in no row in pin order; column A has the heading *Pin row* beside *Pin No.* and in each row a formula `=[$'CON_PCDU-J01'.F19]` with its value (empty for a pin in no row). Column A is outside the printed range. The far side and the reference pinouts keep their columns |
| `system/export.json` | `row_layout` of each part and device connector that has one (`rows`, and `rings` while true) |
| `system/drc_findings.csv`, `system/drc_report.md` | The rule `power-return-adjacent` judges the face of a connector with a layout ([RULES.md](RULES.md)): *PCDU1-J01: PWR (pin 1) and RTN (pin 6) are neighbours on the face of the connector (rows 1 and 2), with no unassigned contact between them*; pins of different rings are not judged, and `unchecked-config` names them (object `power-return-rings`). The finding IDs stay those of 3.0.0 |

The output check works the rows out with its own copy of the rules (`verify_plan.face_rows`, used by `verify.py` too; neither imports `core/row_layout.py`): a wrong row, a missing column or a column where no connector has a layout is `out_box_pinouts` or `out_pinout`; a wrong cell, a wrong order of a near block or a wrong formula of the plan is `out_plan` or `out_plan_formula`; a `row_layout` of `export.json` that differs from the model is `out_json` ([Verifier v2](#verifier-v2-coreoutputsverifypy)). The drawings, the build workbook, the labels, the BOM, the mass and length tables, the connection list, the traceability table, the version report and the WireViz file do not show the rows.
