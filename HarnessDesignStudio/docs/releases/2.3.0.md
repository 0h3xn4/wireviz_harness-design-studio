This is **version 2.3.0**, a minor release. **A harness can branch**: one harness with one plug on each device connector, a branch point where it splits, and a segment with a length between each two of its nodes. Generate makes such a harness when you choose the new mode `per_connector_group`; on a harness drawn by hand you draw the routing tree yourself. 2.3.0 also brings the owner's feedback from a real display: the program starts on Home and asks the role there, the tour is removed, every window moves on its own, and the `.deb` has a page in Ubuntu's App Center. **There is no format change:** branch points and segments are in every harness file since format 1, and the place of a branch point on the diagram is a mark outside the model hash. 2.3.0 writes format 2 as 2.2.0 does, and format 2 stays frozen. If you come from 2.2.0 or 2.1.x, install 2.3.0 over it; your projects need no step. If you come from 2.0.x, read the notes of 2.1.0 first: 2.0.x does not read port names. If you come from 1.17.1 or older, upgrade each project once to format 2, as the notes of 2.0.0 say. The guide is *Upgrade a project to format 2* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### From 2.2.x to 2.3.0

- **Install over 2.2.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Projects stay as they are.** A project that generates at 2.2.0 generates the same at 2.3.0, and its harnesses stay as they are until you choose `per_connector_group` or join two of them. Every written file has the same content, apart from the version stamp and the model hash that includes it, with two exceptions: a harness with a branch point gets `segments.csv`, a sheet *Segments* in its workbook and a sheet *Routing* in its build workbook (the example `flatsat` has six such harnesses), and the advice on more than one cable plug on a device connector now names `per_connector_group`. The text of a finding is part of its ID, so a waiver of that finding shows as stale once: waive it again. The bytes of the `.xlsx` and PDF files can differ, because they are compressed; so can the sizes of the `.xlsx` files in `outputs/manifest.json`.
- **Update the whole team at the same time,** before anyone chooses `per_connector_group`. Each version writes its number into `project.json` and the generation record. A 2.2, 2.1 or 2.0 tool reads the mode `per_connector_group` as not known, uses `per_connector_pair` and removes a joined draft on its next Generate (a released harness stays). It reads a tree drawn by hand as it is, with the same wire lengths, but cannot edit it, and its outputs have no *Routing* or *Segments* sheet and no `segments.csv`.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 2.2.x fail it until you export them with 2.3.0.
- **The first start changed.** The program starts on Home and asks *Who are you working as?* there; nothing opens by itself. A settings file that holds values keeps its role and skips the question.

### The main changes

- **Generate can make one harness that branches.** The new choice `per_connector_group` of `segmentation.mode` (*Settings > Project*, *How interfaces are grouped into harnesses*) joins the interfaces that plug into one device connector into one harness, with one plug on each device connector and a branch point on an end with more than one connector. Connectors wired in a ring are not joined, and Generate warns `branch_not_built`. When you choose the mode, the generated drafts are taken over: the one with the lowest ID keeps its ID, and its locked wires, labels, notes, strip lengths and edited cable connectors carry over; what cannot carry over is reported. The default stays `per_connector_pair`.
- **You draw the routing tree of a harness drawn by hand.** The **Routing** table under the wires of the **Harness** tab has one row per segment and one per branch point; **Add branch point**, **Add segment…**, **Rename…** and **Delete** change the tree, and a double-click on a length enters it in metres. On a harness Generate made only the lengths are yours, and Generate keeps them. Each change is one undo step; a released harness refuses them with the reason.
- **A new leg and the join on the diagram.** A cable dragged from a port that one harness drawn by hand plugs into, and let go on empty ground, is a new leg of that harness: a loose end with a wire from each free pin of the plug that has a signal. **Join into one harness** makes one harness of two harnesses drawn by hand that plug into one device connector. Branch points are drawn as small diamonds that you can drag; where one sits is a mark outside the model hash, so no output goes out of date. The **Problems** panel offers the join, or `per_connector_group` for drafts that Generate made.
- **Three new warnings** of the design rule `model-inconsistent`: `segment_tree_split` (the segments do not reach every connector), `branch_point_unused` (a branch point with fewer than two segments) and `shield_across_branch` (a shield group whose wires end on different connectors). A shield group runs between two connectors. The design rules are still 39.
- **The routing in the written files.** A harness with a branch point gets `harnesses/<ID>/segments.csv`, a sheet *Segments* in `<ID>.xlsx` and a sheet *Routing* in the build workbook after *Cut list*, with a length to fill in on an amber cell. `verify --outputs` works the rows out on its own and reports `out_routing`. A harness without a branch point keeps its files byte for byte.
- **`routing DIR HARNESS`** prints the routing tree of a harness: each segment with its nodes, its length and where the length came from, and the connectors beyond each branch point. `explain DIR W001-L3` explains a segment and `explain DIR W001-B2` a branch point. `routing` has `--json`.
- **The program starts on Home, and Home asks the role.** The three roles are big buttons on Home; a press stores the role and Home stays. The window of its own that asked the role is gone.
- **The tour of the first start is removed**, with **Help > Replay the tour**. **Guided mode** stays.
- **Every window moves on its own.** The dialogs are no longer glued to the main window. A dialog whose answer the next step needs still waits for it, and the main window takes no input meanwhile.
- **A page in Ubuntu's App Center.** The `.deb` installs an AppStream file, so App Center shows the name, a description, the licence, five screenshots and the newest releases. The screenshots load from the web; the program itself never uses the network.
- **The scripting interface is unchanged** (`harness_design_studio.api`, `API_VERSION` 1).
- **The user manual** has a page *Branching harnesses* (`docs/user-manual/branching-harnesses.md`), with a worked example that the end-to-end test of 2.3.0 runs.

### Known limits

- **Splices are not in 2.3.0.** Two wires on one pin need a splice, so a new leg takes only the free pins of a plug. Splices need a format change and are planned for 3.0.0, with format 3.
- **Joining is in `per_connector_group` only.** Chains kept apart and the interfaces of a released harness are not joined, and `per_unit_pair` and `per_zone_pair` keep their warning.
- **The tree, the legs and the join are edited in the app.** The command line reads them (`routing`, `explain`) but has no edits of them.
- **No kind of branch point** (a breakout, a boot, a transition) and **no backshells** as their own rule; a shield or a jacket does not end at a branch point.
- **The limits of 2.2.x stand.** In Guided mode the message after connecting does not say that a shared connector gets a second plug. The prototype counts the pins of the part, not the ports, and has no device library and no branch points.
- **Nobody has looked at the new screens on a real display**, and the Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values are placeholders until your project supplies them.
