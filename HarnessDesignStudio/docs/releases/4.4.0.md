This is **version 4.4.0**, a minor release of 4.3.0, and it reads the names a team gives its pins. A project can now say that its port names name the device at the other end (`TTC1_TX+` for the transceiver TTC1): Generate then gives each interface the port named after its far device, the verifier reports a port named after another device, and the pairing of a connection reads the other device's name off a pin name. A project can keep a **signal map** of its own words (`TXP` for `TX+`), which the pinout and KiCad imports apply, also inside a port. *Unassign from interface* keeps the names of a fixed pinout. **Both settings are off until a project sets them**, and a project that sets neither keeps every file as 4.3.0 writes it. **There is no format change:** 4.4.0 writes format 4 as 4.3.0 does, and format 4 stays frozen. The guides are *Generate harnesses*, *Connect two connectors* and *Import data* in the user manual (`docs/user-manual/generate-harnesses.md`, `docs/user-manual/connect-two-connectors.md`, `docs/user-manual/import-data.md`).

The work answers points 10, 11 and Cb of the feedback that an electrical engineer gave in November 2026 ([the plan](../ait/ELEC_FEEDBACK_PLAN.md), milestone E4; [the design](../ait/DESIGN_4.4_NAMES_PORTS.md)): an on-board computer with many interfaces on one connector, to two transceivers, where the signals of TTC1 must go to TTC1 and those of TTC2 to TTC2, from the signal and device names; reading the ICDs; and names that a team thought were right and that need manual work afterwards.

### From 4.3.x to 4.4.0

- **Install over 4.3.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Your projects open as they are.** Nothing is upgraded and nothing in a project file changes. No project sets the two settings by itself: no template, example or new project has them.
- **Projects stay as they are.** A project that sets neither key generates and writes the same as with 4.3.0: every written file has the same content, apart from the version stamp and the model hash that includes it.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 4.3.x fail it until you export them with 4.4.0.
- **Update the team together** before a project sets a key. A 4.3.x tool reads a project with the keys, keeps them when it saves and says nothing about them, but it ignores them: its Generate gives a new interface the first free port in name order, which the 4.4.0 verifier then reports (`port_far_device`), its imports do not apply the map, and its `settings --set` refuses both keys.

### Ports named after the far device

An on-board computer OBC1 has one connector J1 with the pins `TTC1_TX+`, `TTC1_TX-`, `TTC1_RX+`, `TTC1_RX-` (pins 1 to 4) and `TTC2_TX+` … `TTC2_RX-` (pins 5 to 8). The import reads two ports, `TTC1` and `TTC2` (since 2.1.0). Generate gives interfaces the free ports in name order and the interfaces in ID order. So when the RS-422 interface to TTC2 is IF-001 and the one to TTC1 is IF-002, 4.3.0 gives IF-001 the pins named for TTC1, and `generate`, `verify` and `drc` report nothing; only `system/box_pinouts.csv` shows `TTC1_TX+` on IF-001.

The new setting `naming.far_device_names` says that a name names a device: it starts with a device ID and one of `_`, `.` or `-` (`TTC2_TX+`), or ends with one of them and an ID (`TX+.TTC2`); a port named `TTC2` names it too. The ID is compared exactly, with case; the name of a device (`Transceiver 2`) is not read. When several IDs fit, the longest wins (`OBC1-R_TX` names `OBC1-R`, not `OBC1`), and a name that names two devices (`TTC1_TX_TTC2`) names neither, with a note. Set it with `config DIR --far-device-names on` or the check box **Signal names name the far device** under *Settings > Project*; `--far-device-names off` takes the key out again, so the file is as it was. With it on:

- **Generate** gives an interface on a fixed pinout, after the pins a person locked, the port named after the device at its other end: the one it held before while it is free, else the first free one in name order. It keeps a port held before only when it names no other device, and it never gives an interface a port named after another device. When nothing else is left, it stops with an error that names the ports: *IF-003: OBC1-J01 has a fixed pinout and no free pin named TX+, TX-, RX+, RX-, and no free complete RS-422 port for unit TTC3 (port TTC1 is named after unit TTC1; port TTC2 is named after unit TTC2).* A port that names no device (`RS422_2`) is taken by any interface as before. In the example IF-001 gets pins 5 to 8 and IF-002 pins 1 to 4, in either order of the IDs, and a second Generate changes nothing. The reason of each such pin says *the port named after unit TTC2 at the other end (naming.far_device_names)*, and the generation record has the note `naming:far_device_names`.
- **The verifier** checks it with its own copy of the reading (`port_far_device`): *Interface IF-001 goes to unit TTC2 but uses port TTC1 of OBC1-J01, which is named after unit TTC1 (naming.far_device_names). Regenerate, or choose the port of TTC2.* For pins nobody locked it is an error, which the design rules list as `verify-mismatch` (fix *Regenerate harnesses*) and which blocks a release; a project generated before the setting was on shows it until the next Generate. For pins a person locked, or a released harness, it is a warning that ends *It is kept because a person locked the pins.* or *It is kept because harness W001 is released; a new version takes the port of TTC2.*, and the design rule report does not list it.
- **`explain DIR OBC1-J01.5`** says *the port named after TTC2, the device at the other end of IF-001, comes first (naming.far_device_names), then ports in name order, interfaces in ID order*, with the input *Signal names name the far device = yes* and the assumption `A-FAR-DEVICE`.
- **The editor.** The room of a connector and the Guided choice follow the same rule: a connector whose free ports are all named after other devices has no room (*OBC1-J01 cannot take another RS-422: its free RS-422 ports TTC1 and TTC2 are named after other devices*). **Choose port…** lists the far device's port first (*TTC2 (pins 5-8), named after TTC2 at the other end*), then the ports that name no device, then the others, marked (*TTC1 (pins 1-4), named after TTC1*); you can still choose one, and its pins are locked. The Inspector then shows the verifier's sentence under the end.

Turning the setting off leaves the ports where they are. A device renamed, or imported under another ID, keeps its pin names: a port named after the old ID names no device.

### Pairing that reads the far device

The proposal of **Link connectors** already lets a prefix be missing on one side, so `TTC1_TX` on OBC1 meets `RX` on TTC1. But it did not know which device a prefix means: with the pins `TTC1_TX`, `TTC1_RX`, `TTC1_PPS`, `TTC2_TX`, `TTC2_RX`, `TTC2_PPS` on OBC1 and `TX`, `RX`, `PPS` on each transceiver, the connection to TTC2 was proposed `TTC1_TX=RX` and `TTC1_RX=TX`, and `TTC1_PPS` never met `PPS`. With the setting on, the proposal reads the other device's name off a pin name (`TTC2_TX` is `TX` in a connection to TTC2), reads a name of the pin's own device or of no device whole, and does not offer the pins of a third device:

```
Pins 1, 2 and 3 of OBC1-J01 name device TTC1, so they are not offered in a link to TTC2 (Settings > Project: Signal names name the far device).
```

So OBC1 to TTC2 is proposed `TTC2_TX=RX, TTC2_RX=TX, TTC2_PPS=PPS`, in whatever order the connections are made; with `OBC1_RX` and `OBC1_TX` on the transceivers, `TTC2_TX=OBC1_RX` and `TTC2_RX=OBC1_TX`, where 4.3.0 pairs nothing. The one-click connection starts with the connector of the far device's pins. **The review of connections** reads names the same way: `link-signal-mismatch` names a pair whose pin names a third device (*Link L1 pairs pin 1 of OBC1-J01 with pin 2 of TTC2-J01, but TTC1_TX names unit TTC1, not TTC2. Pair it in a link to TTC1, or rename the pin.*), and `link-unpaired` sends such a pin to its device (*Pin 3 of OBC1-J01 is named TTC1_PPS (unit TTC1) but no link pairs it. Link OBC1-J01 to a connector of TTC1, or set its role to Spare if it is not used.*). A connection made before the setting was on shows these warnings; delete it and connect again. A loose cable end reads names as before.

### The project's signal map

The interface types name their signals their way (`TX+`, `CANH`). A team's pinout may say `TXP` and `CAN_H`, and until now only `import-netlist --signal-map` translated them, on every import, for KiCad only and for whole names only: `TTC1_TXP` was not read as the `TX+` of port TTC1. The new key `signal_map` of `config/naming.json` keeps the team's words in the project. **The tool ships no map** (D-11); the template `signal-map.csv` that `templates` copies is an example to take on purpose:

```
harness-design-studio templates my-templates
harness-design-studio config DIR --signal-map my-templates/signal-map.csv
```

```
Signal map: 6 name(s) in config/naming.json.
```

The file is read as `import-netlist --signal-map FILE` reads it: a CSV of two columns with an optional heading row, or a JSON object. `--signal-map none` takes the key out. In the editor, *Settings > Project* has the section **Signal map**: one `TEAM NAME = SIGNAL` per line, **Take the names of a file…** and **Save**, one undo step. `settings DIR --set naming.signal_map='{"TXP": "TX+"}'` takes it as JSON. `validate` refuses a name mapped to itself, a signal name that is also a team name, a name that is not a signal name and a table of more than 1000 entries (`config_invalid`).

`import-pinout` and `import-netlist` then write the type's name for the team's: the whole name (`TXP` becomes `TX+`) and a name inside a port, read by the rule of ports (`TTC1_TXP` becomes `TTC1_TX+`; the port and its separator stay). `import-pinout` maps the *Signal* cell before it writes the *Port* column in. A name that reads in two ways (`TXP_RXN`) is not renamed, and a warning says so. Each import lists what it renamed after its rows:

```
OBC1-J01: OK added (8 pin(s))
Renamed by the project's signal map (config/naming.json signal_map): 8 signal(s)
  TTC1_TXP -> TTC1_TX+: OBC1-J01 pin 1
  …
  TTC2_RXN -> TTC2_RX-: OBC1-J01 pin 8
OBC1-J01: Ethernet or RS-422 ports: TTC1 (pins 1-4), TTC2 (5-8)
```

`--json` has the same list as `renamed_signals`, the import record keeps each rename as a converted value (field `signal`, unit `signal map`), so `imports DIR` counts them, and the import wizard shows them. `import-netlist --signal-map` keeps its meaning and wins for a name it holds. The map acts at import only: Generate, the rules, the verifier and the pairing read the names the import stored, so changing the map renames nothing already in the project. The library imports (`import-devices`, `import-subsystem`, `add-device`, `update-device`) do not read it. The map is not read by Generate, so changing it does not make the harness plans out of date.

### ICDs

There is **no importer of a team's ICD format** and none of an ICD's README: no example of either was given, and a format of the tool's own making would be one that no team uses. `import-pinout`'s table is the generic form of a pinout (its columns are in `docs/IMPORTS.md`, new section *Reading an ICD*), and the signal map brings the team's names. An importer waits for an example ICD with its README, with made-up names.

### *Unassign from interface* keeps the names of a fixed pinout

*Unassign from interface* in the Devices tab cleared the signal of every pin it freed. On a fixed pinout that name is the device's own, so a port was lost: after *Unassign* of pins 5 to 8 of OBC1-J01, *Choose port…* said *OBC1-J01 has no RS-422 port TTC2.*, and two ports could not be swapped by hand. Now a fixed pin keeps its name and loses only its interface and its lock; a pin that is not fixed is freed as before. With it, the swap works with or without the setting: *Unassign* pins 5 to 8, *Choose port…* TTC2 for IF-001, Generate.

### Which written files change

- **Nothing**, for a project that sets neither key: every example, template and test fixture. The stored hashes of the written files, the numbers snapshot and the golden outputs are as for 4.3.0, apart from the version stamp.
- **With `naming.far_device_names` on** and ports named after devices: the pins of the device connectors (the interface on each pin), `generated/generation.json` (the reasons and the note), and so every output that shows a pin's interface (`system/box_pinouts.csv`, the mating matrix, the wire lists, the harness plans). That is the purpose of the setting. `system/drc_findings.csv`, the design rule report and the *DRC findings* sheet list `port_far_device` as `verify-mismatch`, and the new texts of `link-signal-mismatch` and `link-unpaired`, where a port or a connection has them.
- **`config/naming.json`** of a project that sets a key, and through it the model hash of its written files.
- **The pins an import writes** with a map, and the import record (`imports/records.json`, outside the model hash and every output).

| `config DIR` | — | `--far-device-names on\|off` (prints `Signal names name the far device: on (config/naming.json, far_device_names).`, after a line that says the harness plans are out of date when they were current) and `--signal-map FILE\|none` (prints `Signal map: N name(s) in config/naming.json.`); then the hand-over list, whose exit code it keeps (1 while an engineering value is missing). The scripting interface keeps its names (`API_VERSION` 1). With the setting off and no map, Generate, the pairing, the review of connections and the imports are those of 4.3.0: tests compare them with word-for-word copies of the 4.3.0 modules on random cases.

### Known limits

- **Nobody on a team has named pins after devices in this tool yet.** The convention (`TTC1_…`, the separators, the ID with its case) is read from the feedback's one example. A team that writes `TTC-1_TX` for the device `TTC1` gets nothing from the setting. The editor's new controls were tested offscreen; nobody has looked at them on a real display. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **A device ID that looks like a port name.** In a project with a device `RS422`, every port `RS422_n` is read as that device's. The setting is opt-in, and *Choose port…* and the Inspector name the device.
- **Two tools on one project.** A 4.3.x tool ignores both keys; the 4.4.0 verifier then reports what it did. Update the team together.
- **The map renames at import.** A wrong entry renames every pin it fits. The echo, the wizard's preview and the import record list each rename, and an import is one undo step.
- **No ICD importer** (above).
- **A connection is not moved.** A connection made before the setting was on keeps its pairs; the review names them, and you connect again.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
