This is **version 2.0.1**, a patch release of 2.0.0. It brings one new tool for teams that use Git, a shorter release page and new pages of the user manual. **There is no format change:** 2.0.1 writes format 2 as 2.0.0 does, and format 2 stays frozen. If you come from 2.0.0, install 2.0.1 over it; your projects need no step. If you come from 1.17.1 or older, upgrade each project once to format 2, as the notes of 2.0.0 say. The guide is *Upgrade a project to format 2* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### From 2.0.0 to 2.0.1

- **Install over 2.0.0.** Install the `.deb` or the Windows setup program the same way as before; unpack the `.tar.gz` or the `.zip` into a new folder.
- **Projects stay as they are.** A project saved by 2.0.0 opens and saves as before. Every written file is the same, apart from the version stamp and the model hash that includes it.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 2.0.0 fail it until you export them with 2.0.1.

### The main changes

- **`merge-fix` resolves the same ID made on two branches.** A new harness gets the next free number (`W003`) and a new connection the next free `L1`, `L2` ... So two people who each make one on their own Git branch get the same ID for two different things, and the merge stops. `merge-fix` now keeps the harness or connection of the branch you are on under its ID and gives the other branch's the next free ID, with everything of that branch that names it. It prints every rename (`old -> new`), records them in the journal and runs `check`. It refuses, and changes nothing, when the harness or connection has a release history. `merge-fix --dry-run` shows what it would do and writes nothing. How: *Use Git and CI* in the user manual (`docs/user-manual/use-git-and-ci.md`).
- **`merge-fix` merges more files entry by entry.** When `logical/links.json`, `waivers.json` or `diagram/marks.json` is in conflict only because the two branches changed different entries, `merge-fix` merges them against the version both branches started from. An entry that both branches changed in different ways is still left to you.
- **A shorter release page.** The page has seven files: the four packages, `SHA256SUMS`, its signature `SHA256SUMS.sigstore.json`, and one archive, `harness-design-studio-2.0.1-release-bundle.tar`. The archive holds everything else: the source of the LGPL and GPL components, the SBOMs, the inventories, the notices, the offline-audit report and the signatures of the packages and the SBOMs. One signature over `SHA256SUMS` covers the packages and the archive.
- **New pages of the user manual**, written after the first demo: how auto-linking and the checks work, connector IDs and tags, every PDF and Excel file in one table, and how to use the tool in an organisation.

### Known limits

- **The editor does not show the renames of `merge-fix`.** They are on the command line only.
- **The release page with the bundle is new.** This is the first release made with it.
- **The merge of the journal was tried with `git merge` in the tests only.** Whether the *Merge* button of the GitHub web site honours `merge=union` is not checked.
- **Nobody has looked at the screens on a real display**, and the Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values are placeholders until your project supplies them.
