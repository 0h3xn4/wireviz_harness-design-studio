This is **version 4.3.0**, a minor release of 4.2.0, and it gives the reviewer of a harness one place to work from. A project can now hold its own **review checklist**, the points a reviewer goes through before a release. The build workbook of every harness has a new sheet **Review**, and the editor has a page **Review**, one harness at a time. Both show the checklist with a place to tick, every finding about the harness and what it means for the release, the values still open, and the sources to look at: the ICD named on each device connector and the page of each part. A release records which points the person releasing says were ticked, as one note in its comment. `explain` takes the ID of a finding. *Settings > Project* shows the label format. **There is no format change:** 4.3.0 writes format 4 as 4.2.0 does, and format 4 stays frozen. The guides are *Release a harness*, *Export the outputs* and *Read and fix problems* in the user manual (`docs/user-manual/release-a-harness.md`, `docs/user-manual/export-the-outputs.md`, `docs/user-manual/read-and-fix-problems.md`).

The work answers point 9 of the feedback that an electrical engineer gave in November 2026 ([the plan](../ait/ELEC_FEEDBACK_PLAN.md), milestone E3; [the design](../ait/DESIGN_4.3_REVIEW_VIEW.md)): a checklist of what the reviewer checks, and quick links to all sources.

### From 4.2.x to 4.3.0

- **Install over 4.2.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Your projects open as they are.** Nothing is upgraded and nothing in a project file changes. No project gets a checklist by itself: no template, example or new project has one.
- **Export once.** Every build workbook gets the sheet *Review* and one more line on *Start here*. `verify --outputs` compares the files in `outputs/` with the version that runs, so outputs written by 4.2.x fail it until you export them with 4.3.0.
- **Update the team together.** A 4.2.x tool reads a project with a checklist, keeps the list when it saves and says nothing about it. But it shows no Review page, writes no Review sheet and adds no note to a release, and its `verify --outputs` refuses the outputs of 4.3.0, which have a sheet it does not know.

### The review checklist

The checklist is a list of points in the order a reviewer goes through them, kept in the project as the key `review_checklist` of `config/naming.json`. A point is one line of 1 to 300 characters; each point appears once; a list has at most 100 points. **The tool ships no point.** The template `design-review-checklist.md`, which `templates` has always copied, is a start that you take on purpose: copy it, take out what does not apply (nine of its 26 points are for the ECSS profiles), and give it to `config`:

```
harness-design-studio templates my-templates
harness-design-studio config DIR --review-checklist my-templates/design-review-checklist.md
```

```
Review checklist: 26 points in config/naming.json (list 8b3d7a5b).
```

Each list item of the file is a point (a line that starts with `- [ ] `, `- `, `* `, `+ ` or a number and a dot); headings and other lines are skipped, and the list mark, `**` and backticks are taken away. A file without list items gives one point per line. `--review-checklist none` takes the list out. In the editor, *Settings > Project* has a section *Review checklist*: a box with one point per line, **Use the template's points**, **Take the points of a file…** and **Save**, one undo step. `settings DIR --set naming.review_checklist='[...]'` takes the list as JSON. `validate` refuses a list that breaks the rules above (`config_invalid`); a refused list is no list, and like any refused value it stops every release.

The **list hash**, the first 8 hexadecimal characters of a SHA-256 of the list (`8b3d7a5b` for the template's 26 points), names the list on the sheet and in the release comment. A release does not freeze `naming.json`, so the hash tells a later reader whether a comment and a sheet speak of the same list. The list is not read by Generate, so changing it does not make the harness plans out of date; it is part of the design, so the outputs are out of date until the next export.

### The Review sheet

The build workbook (`<ID>_build.xlsx`) has the sheet **Review** before **About**, after **Tests** and, for a harness with as-built records, **As-built**. The other sheets keep their places, and *Start here* lists the new sheet under *How to use this workbook*. The sheet is in the order of a review:

- **The head**: the harness, its version, status and stamp, and the release entry of the version: `Release: not released yet.`, or `Release: version 1.0.0 released on DATE by NAME, checked by NAME. Comment: …`.
- **Checklist**: each point with its number and the columns **Done (x)** and **Note**, empty. Without a list, one sentence says how to set one.
- **Findings of the harness**: every finding of the design rules, the verifier and the logical checks that is about this harness, open errors first, with its rule, ID, object and text, its state (`open`, `open: its waiver no longer applies (the finding changed)`, `waived: …`, `accepted as a deviation: …`) and, in the column **Release**, `stops the release` for an open error and `needs a written reason` for a part that is not approved.
- **For the whole project**: the notes of the checks not run, such as *EMC class separation was not checked*, and a refused setting (`config-invalid`), on the sheet of every harness.
- **Values still open**: the placeholder files, the engineering values not set, each open check of *Start here* with its count, its first five items and where to see them all, the interface types of example data the harness carries, the values set by hand, and the as-built records while that gate is on.
- **Sources to look at**: each device connector the harness plugs into, with the ICD, version and link the Devices tab gives it (`not named` while it has none), and each part it uses, with its approval and link. A link is written as text.
- **How the numbers were made**: `explain DIR ID` for any ID on the sheet, and `explain DIR --all --out FOLDER`.

A finding is about a harness when it is on the harness, its connectors, wires or shields, on a device connector it plugs into, on an interface it carries, or on a part it uses. The release gate now takes the errors of a harness from the same selection, so what the sheet marks *stops the release* is what `release` refuses; a test holds the gate's blockers word for word as they were. The independent verifier words every row of the sheet a second time, from its own copy of the rules, and reports a difference as `out_review`. On the example `flatsat`, the sheet of W002 lists 18 findings (11 notes and 7 warnings), 3 notes of the whole project, 8 rows of values still open and 28 sources.

**Where to tick.** Tick a printout, or a copy saved outside `outputs/`. A file in `outputs/` that you change after the export stops the release (`outputs_modified`), and `verify --outputs` reports `out_review`: *The build workbook of W003 (Review) has ticks before anyone reviewed it.* The tool never reads a ticked sheet back.

### The Review page

The editor's page **Review** shows the same rows for one harness, from the same function and the findings the window already has. It is on the rail of the Electrical engineer and the AIT engineer, after *As-built*. In every role, the step *Review and release* of the Next step page opens it with **Open the Review page** (it said **Go to Releases**), and so do **Review page** in the Releases tab, **Go > Go to Review**, the command palette and **Review…** in the menu of a harness in the project tree. On the page:

- the checklist has a box to tick for each point, **Tick all** and **Clear**;
- the findings have **Show**, **Explain**, **Waive…** and **Accept as deviation…**, as in the Problems panel;
- a value still open has **Show**, **Show all** and, for an engineering value, **Supply value…**;
- a source has **Copy link** and **Show**, and the column **Library** says the state of the device in your device library (*Up to date*, *Library changed* …), which a written file cannot know;
- **Release…** opens the release window for the harness, and **Edit the checklist…** opens *Settings > Project*.

**The ticks stay on this computer.** They are kept in the editor's settings for that project folder, with the list hash and the design they were made for, and never in the project or a written file. When the list or the design changes, they go, and the page says *The checklist or the design changed after these points were ticked; tick them again.* A released harness shows its release entry and no boxes.

### The ticks in the release comment

The person releasing says which points were ticked. On the command line, `release DIR HARNESS --ticked POINTS` takes `all`, `none`, or point numbers and ranges such as `1-20` or `1-5,7`. In the editor, **Release…** on the Review page hands the ticks of the page to the release window, which shows the note under the comment (*Added to the comment: [Review checklist …]*) and has **Open the Review page**. The note is added last to the comment, after the notes of placeholders, parts, loose ends, as-built records and deviations:

```
[Review checklist (26 points, list 8b3d7a5b), recorded by A. Engineer: ticked 1-20; not ticked 21 (Drawing: connectors, pins and signals match the device do...), 22 (Wire list, pinouts and BOM agree with the drawing.), 23 (Mass and length tables look plausible.), 24 (Test tables list the limits your programme requires.), 25 (The release comment says what this version is for, and th...) and 1 more]
```

It says `all ticked` or `none ticked`, or, when the project has a list and no ticks are given, `no ticks recorded`. At most five points not ticked are named, each cut to 60 characters. **No point stops a release:** points not ticked are written into the comment, and the release goes ahead. **A tick is a statement:** the note says *recorded by* the person releasing, never *checked*. `--ticked` on a project without a list (`ticked_no_checklist`) or with a number that is not a point (`ticked_invalid`) is refused. A project without a list releases with the comment of 4.2.0, byte for byte.

The note is read wherever a release comment is: `log`, the Releases tab, the baseline, `system/changelog.csv` and `system/version_report.md`, and row 3 of the Review sheet once the outputs are written again. The command line's `release` writes them again itself; after a release in the editor, export again.

### `explain` takes a finding

`explain DIR FINDING` explains one finding by the ID that `drc --json` and the *Finding* column of the Review sheet give it (`part-unapproved.EX-WIRE-SINGLE`, `unconfirmed.IF-010`, `unchecked-config.emc`; a waived finding too). It prints what the editor's *Explain* shows: the limit the rule checked and how it was derived or, for a yes/no rule, what it compares, the statement of the finding, the configuration the rule reads and what it saw, with the model page. `--json` prints the derivations as a list, as for an object. An ID is looked up among the findings only when it names no object, so every object keeps its meaning; an ID that is neither exits with 2 and says *… or a finding of this project.*

### The label format in Settings > Project

*Settings > Project* has the choice of `model.label_format`: the five formats, with `harness_device_connector` marked *(a new project's choice)*, and a line that says what the chosen format prints. A choice is one undo step. For `custom`, the page says to set the two templates with `settings --set`. It changes no file but `config/model.json`, as `settings DIR --set model.label_format=…` does.

### Which written files change

- **Every build workbook** (`<ID>_build.xlsx`): the sheet *Review* before *About*, and the line *Review* under *How to use this workbook* on *Start here*. Its content changes when a finding, a waiver, an open value, a source or the checklist of the harness changes.
- **`config/naming.json`** of a project that sets a checklist: the key `review_checklist`.
- **The comment of a release** (the change log, the baseline, `system/changelog.csv`, `system/version_report.md`) in a project with a checklist, or with `--ticked`: the note.
- Nothing else. The other files, `system/export.json`, the drawings, the harness plans and the project files are as 4.2.0 writes them, apart from the version stamp.

### For scripts

| Place | 4.2.x | 4.3.0 |
| --- | --- | --- |
| sheets of `<ID>_build.xlsx` | … *Tests*, (*As-built*,) *About* | … *Tests*, (*As-built*,) *Review*, *About*: the sheets before *About* keep their places |
| `config DIR` | — | `--review-checklist FILE\|none`; it prints `Review checklist: N points in config/naming.json (list HASH).`, then the hand-over list, whose exit code it keeps (1 while an engineering value is missing) |
| `settings DIR` | — | the setting `naming.review_checklist` (no default) |
| `release DIR HARNESS` | — | `--ticked POINTS`; the blockers `ticked_invalid` and `ticked_no_checklist`; the note at the end of `comment` |
| `explain DIR OBJECT` | an object | also a finding ID; `--json` prints the same list of derivations |
| `verify --outputs`, `export`'s self-check | — | the code `out_review` (the object the harness) |
| `--json` of every command | — | the same keys; the note is inside the comment that `log --json` prints |

The scripting interface keeps its names (`API_VERSION` 1); `api.explain_finding(project, finding_id)` was already there. The release gate gives the same blockers with the same texts as 4.2.0 for a project without a checklist.

### Known limits

- **Nobody at a review has used the page or the sheet yet.** The order of the blocks, the first five items of an open check and the words are the design's. The editor's new screens were tested offscreen; nobody has looked at them on a real display. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **The ticks are not kept in the project.** A field for them would be a format change (planned with format 5, milestone E5). The page keeps them on one computer; a team that reviews on several computers records them at the release.
- **A ticked sheet is not read back.** The person releasing types or ticks what was done, as they type the checker's name.
- **No gate on the checklist.** A setting that makes a release wait for every tick, like `release_requires_asbuilt`, can follow if teams ask.
- **A long sheet.** W002 of `flatsat` has about 80 rows without a checklist and about 105 with the template's points. Nothing is cut; the sheet breaks pages before a block that would start at the foot of a page.
- **A release in the editor writes no output file.** The sheet shows the release and its note after the next export.
- **The library state of a device** is on the page only: it depends on folders outside the project, so no written file holds it. A device has no *checked* state of its own yet (format 5).
- **A `single` type that shields per pair still gets no shield.** Found again on the way; give the type a twisted construction (`twisted_shielded_pair`) or let it shield overall.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own. A ticked checklist is a person's statement, not a check by the tool.
