This is **version 5.0.0**, a major release. It brings **format 5**, a new version of the project file format, and with it the answers to five points of the feedback of an electrical engineer: segment lengths **measured to the mating face** with the depth of a connector and its backshell taken off, a **current per device pin** from which the current of a wire is worked out, a **splice in a harness made from a connection**, **where each end of a shield lands**, and a record of **who checked a library device against which ICD**. Each of them is opt-in, sparse data: a project that holds none of it writes the files it wrote with 4.4.1, apart from the version stamp and the new table `devices` of `export-data`. **Format 5 is frozen with this release:** it does not change any more, and a later change of the file format would be a new format with its own upgrade. **Upgrade each project once** (`migrate`, or the editor's question): the step writes the number 5 and nothing else, and after it versions 4.x open the project read-only, so update the whole team at the same time. If a script reads the written files or the output of the commands, read *For scripts* below. The guides are *Lengths to the face* and *Upgrade a project* in the user manual (`docs/user-manual/lengths-to-the-face.md`, `docs/user-manual/upgrade-a-project.md`).

### From 4.x to 5.0.0: upgrade each project once

- **Install over 4.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Nothing is upgraded without you.** A project saved by 4.x is in format 4. This version reads it, but saves it only after you upgrade it. Commands that save refuse a format 4 project and write nothing; `validate`, `check`, `drc` and `export` still read it.
- **How to upgrade.** In the editor, open the project and answer the question with **Upgrade**. On the command line, look first with `harness-design-studio migrate DIR --dry-run` (it writes nothing; it lists `project.json`, and `journal.jsonl` when the project keeps a change journal), then run `harness-design-studio migrate DIR`. The backup is the folder `.migration-backup-v4/` with the record `MIGRATION.json`.
- **What changes.** The number in `project.json`, and nothing else: nobody has data of format 5 before format 5, and every new key is left out of the files while it is unset. The model hash, the findings, the baselines and the released harnesses stay as they are; the upgrade checks them, and a full export, before it keeps the files.
- **Export once after the upgrade** if you use `verify --outputs`, because it compares the outputs with the version that runs. The files are those of 4.4.1 apart from the stamp.
- **Lengths that were already taken to the faces.** The step writes no `length_to`, so every length stays a length to the rear, as 4.x meant it. If your team measured its segments to the mating faces, set `model.length_reference` to `face` after the upgrade (`settings DIR --set model.length_reference=face`, or *Settings > Project*) and give your connector and backshell parts their depths; the length note of the build workbook then says which ends are faces.
- **Older versions and Git branches.** After the upgrade, versions 4.x open the project read-only (*saved by a newer version of the tool*) and change nothing: `generate` and `export` refuse it (*this project is read-only*), while `validate`, `check` and `drc` still read it. Once the project holds data of format 5, a 4.x tool also sets aside each object with a key it does not know as a damaged file: a harness with a face end or a shield place, a part with a depth, a device connector with a pin current, a checked device, and the import records of the kinds `cable-ends` and `shield-ends`. It reads a connection with a junction as the error `link_pin_reused`. `validate` then lists those files, and `generate`, `export` and `drc` refuse the project (*the project has damaged files*) and write nothing. This was tried with the code of 4.4.0. A device library file that holds a depth, a pin current or a check is written as version 4, and a subsystem file as version 3, which 4.x does not read. Upgrade on the main branch first, then bring the other branches up to date before they merge; the files of a format 4 branch are valid in format 5, so a merge needs no rewrite.
- **From 3.x or older**, the upgrade goes through every step in one go; read the notes of 4.0.0 first.

### The main changes

- **Lengths to the mating face, and the depth of a connector** (pull request 357). A cable connector can say that the routing segments ending at it are measured to its mating face (`length_to`), or the whole project can say so with the new setting `model.length_reference` (`rear` by default, the meaning of every length so far). A connector or backshell part has a depth (`depth_mm`). At a face end the tool takes the depth of the connector and of each backshell on it off every wire there, so each wire length is still rear to rear. A depth is never assumed: a face end without one leaves its wires without a length, Generate says why, and `check` warns `length_depth_missing` (or `length_below_depth` when the segments are shorter than the depths). Set them in the Inspector (*Lengths measured to*, *Depth (mm)*), with `import-parts` (a column *Depth (mm)*), with `import-build-data` (a table of cable ends) or with the scripting function `set_length_reference`.
- **A current per pin** (pull request 359). A pin of a device connector can hold the current through its contact in operation, as the ICD gives it (`current_a`; `2`, `2 A` or `500 mA` in the Devices tab, or a column *Current* or *Current (mA)* in `import-pinout`). When every end of a net has a current and they add up, each wire gets its share; otherwise the interface's *Max current* applies as before. `current-over-wire`, `bundle-current` and `voltage-drop` judge a wire with it, so **the wires of a harness made from a connection or drawn by hand get current checks for the first time**, and `current-over-contact` judges each pin on its own instead of giving every contact the whole current of the interface. One gap remains: a wire with a current from its pins but no interface type gets no voltage-drop check, because without a type the tool does not know how many conductors carry the way back; the note `voltage-drop-wires` names such wires. `check` warns `current_unbalanced` when the currents of a net do not add up. Generate does not read pin currents.
- **A splice in a harness made from a connection** (pull request 360). A connection can now pair one pin with several, a **junction**, or give a pair twice, a **parallel pair**. The review of a connection names each junction (`link_junction`, an info). **Create harness** makes one splice per junction from a splice part you choose (the program ships none), and the verifier compares the connection with its harness net by net. Generate still makes no splice.
- **Where a shield end lands** (pull request 361). Each end of a shield group can name its connector, the pin a pigtail lands on, and the backshell for a 360 degree bond or a pigtail to its lug (`at_a`, `at_b`). Only a person sets it: **Change group…**, the scripting function `set_shield_end`, or `import-build-data` with a table of shield ends. Generate keeps the place when it makes the group again with the same wires, and never fills one in. `check` warns when a place no longer fits its group. The *Production* and *Connectors* sheets, the drawing and `system/export.json` show the place.
- **The checked state of a library device** (pull request 362). A person can record that they checked a device against its ICD: the new command `device-checked DIR DEVICE --by NAME [--icd TEXT] [--date YYYY-MM-DD]`, **Mark as checked…** in the Devices tab and the Library window, or `set_device_checked`. The tool stores the SHA-256 of what was checked, and when the device changes afterwards `check` warns `device_check_stale`; the check stays, and a release neither locks it nor needs it. The library carries the check, the Review page and sheet list each device a harness plugs into while some device is checked, and `export-data` has a new table `devices`.
- **The editor** (pull request 363). *Settings > Project* has *Segments are measured to*. The Problems list shows the notes of format 5 as *Info* rows, and a click on a warning of format 5 goes to the place where you put it right; a shield group has its own Inspector.
- **The end-to-end walk** (pull request 364) runs every part on one project, through the command line and the editor, and compares the outputs with the golden set. It found one fault, fixed in the same pull request: the help of `import-build-data`, and so `docs/CLI.md`, did not name the table of shield ends. An earlier fault was fixed along the way in pull request 361: the command line refused a table of cable ends when it wrote its import record, because the record had no kind; it now has the kinds `cable-ends` and `shield-ends`.
- **No new design rule.** Every new warning is a code of `check`, reported by `model-inconsistent`, so *Rules run* stays 43.

### Which written files change

- **A project without data of format 5** writes every file of `export` and the harness plans as 4.4.1 did, apart from the version stamp (the output-hash baseline, the numbers snapshot and every golden of the earlier fixtures say *identical*).
- **`export-data` writes 37 files for every project, 35 before**: the new table `devices` comes as a CSV and a JSON file, even when no device is checked. `settings DIR` and the settings table list one setting more, `model.length_reference`.
- **A project with data of format 5** gets the new columns, sentences and keys listed under *For scripts*.

**The scripting interface** (`harness_design_studio.api`): `API_VERSION` stays 1; it only adds `set_length_reference`, `set_shield_end`, `set_device_checked` and `clear_device_checked`, and the models it returns carry the new fields.

**The extensions:** `PLUGIN_API_VERSION` and `format_version` of the extension data files stay 1. The field `wire.current_a` takes the current from the pins where they give one.

### Known limits

- **Nobody on a team has entered a depth, a pin current or a shield place in this tool yet.** The definitions (a backshell's depth adds to the connector's; a pin current is the operating current of the contact) are the design's; no real connector datasheet or ICD with a current column was read.
- **Unbalanced currents are common in real ICDs**, for example from rounding or a maximum on one side and a typical value on the other. Such a net is not worked out, and `current_unbalanced` says so.
- **No voltage drop without an interface type.** A wire that gets its current only from its pins is not judged for its voltage drop; the note `voltage-drop-wires` names it.
- **No parts are shipped for the new features.** The starter library has no backshell and no splice part: add your own before you use a splice from a connection or a backshell place.
- **Two tools on one project.** A 4.x tool opens a format 5 project read-only and sets aside every object with data of format 5. Update the team together.
- **No look at a real display.** The new controls were tested offscreen only. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
