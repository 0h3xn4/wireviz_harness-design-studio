This is **version 2.2.0**, a minor release. **A project follows its device library**: a device library is a folder of device files, one device each (`OBC1.device.json`), best kept as a Git repository. A project names its libraries in `device-libraries.json` at its root. A device added from a library keeps an import record of its file; the program says when the library has a newer version of the device, shows what changes, field by field, and takes it only when you ask. **There is no format change:** the import record of kind `devices` exists in format 2, and `device-libraries.json` is outside the project format. 2.2.0 writes format 2 as 2.1.1 does, and format 2 stays frozen. If you come from 2.1.1 or 2.1.0, install 2.2.0 over it; your projects need no step. If you come from 2.0.x, read the notes of 2.1.0 first: 2.0.x does not read port names. If you come from 1.17.1 or older, upgrade each project once to format 2, as the notes of 2.0.0 say. The guide is *Upgrade a project to format 2* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### From 2.1.x to 2.2.0

- **Install over 2.1.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Projects stay as they are.** A project that generates at 2.1.1 generates the same at 2.2.0. Every written file has the same content, apart from the version stamp and the model hash that includes it. The bytes of the `.xlsx` and PDF files can differ, because they are compressed; so can the sizes of the `.xlsx` files in `outputs/manifest.json`. A project without a device library keeps the same bytes and the same model hash.
- **Update the whole team at the same time.** Each version writes its number into `project.json` and the generation record, so a team that mixes them changes these files on every save. A 2.1 tool does not read `device-libraries.json` and does not know the link to a library. Its *Save to library* writes `<ID>.json` (or `devices.json` for several devices); next to the `<ID>.device.json` of 2.2.0 the device is then in two files, and 2.2.0 offers it from neither. Update everyone who saves to a library at the same time.
- **A library folder of 2.1 is still read**, with its files of several devices. What is new: a device that is in two files of the folder is offered from neither, and two device files of the same name are refused; the message names the files.
- **Devices that the editor of 2.1 added from a library** have no import record, so they show as *same ID, not from the library*. To link one, name the library in the project, open the device's review and choose *Take the library's version*, or run `update-device DIR ID --apply --adopt`.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 2.1.x fail it until you export them with 2.2.0.

### The main changes

- **The device library.** One device per file, `NAME.device.json`, where `NAME` is the device's ID. The file is the device library file of 2.1 (format `harness-device-library`, version 1), so a 2.1 tool reads it. An optional `library.json` gives the library a name that stays the same in every clone. The program never starts Git and never commits: it reads the commit and the branch from the `.git` folder.
- **A project names its libraries** in `device-libraries.json`, with paths relative to the project folder. The program writes it at once, outside undo and the change journal, and says so. On the command line `--library FOLDER` replaces the list for one run; the command line never reads the editor's library folder.
- **The link and the state of a device.** A device added from a library keeps the import record `devices:<file>` (in `imports/records.json`, outside the model hash and every output), with the SHA-256 of the file, the library's name, the file and its Git commit. Its state is one of *not in project*, *up to date*, *library changed*, *changed here*, *same ID, not from the library*, *source not found* or *in more than one library*. The library owns the connectors with their pins, the kind, the mass relevance and the notes; the project owns the name, the subsystem, the zone, the side, the place and the interfaces on the pins.
- **Four new commands.** `libraries DIR` lists the project's libraries with their Git commit (`--add` and `--remove` change `device-libraries.json`; `--devices` lists every device with its state). `add-device DIR NAME…` adds a library device with its record in one undo step; a taken ID is refused with the choices (`--count` for copies, `--as` for a copy that does not follow the library, or `update-device --adopt`). `update-device DIR [NAME…|--all]` shows one row per changed field and changes nothing; `--check` ends with exit code 1 while a device differs; `--apply` takes the library's version, all or nothing per device and its copies, and refuses a change that a released harness locks, naming the harness. `save-device DIR DEVICE` writes the device into the library and links it. Each has `--json`.
- **In the editor.** The library window lists the libraries of the project and your library folder, with a *Library* and a *Status* column, and its preview names the source of a device. The Inspector and the Devices tab show where a device comes from and its state (*From ACME devices, PCDU00.device.json, up to date*). When a project opens, a notice says when a device has a newer version in its library; it never applies anything. The review window shows the changes field by field, with *Take the library's version*, *Keep this project's* and *Save this project's to the library…*. *Edit > Add device*, *Add here* on the diagram, Ctrl+K and the Quick mode *Add device* window have a *From library* section. *File > Device libraries of this project…* and *Settings > Project* edit `device-libraries.json`; *Save As* copies it with its paths rewritten.
- **Adding a device from a library now records where it came from**, in the library window and on the Devices tab too, and a taken ID asks what to do (add copies, adopt, or add under another ID) instead of taking the next free ID without a word.
- **`imports` and `explain` know the device library.** `imports DIR --check` ends with 1 when a library file changed, and names `update-device` for it. `explain DIR DEVICE` names the library device a device follows, its state and its record.
- **Two more JSON Schemas.** `schema DIR` also writes `device-file.schema.json` and `device-libraries.schema.json`.
- **The scripting interface is unchanged** (`harness_design_studio.api`, `API_VERSION` 1). The new commands have new `--json` documents, and `explain DIR DEVICE --json`, which was an error for a device, prints the document `explain DEVICE`.
- **The user manual** has the device library from setup to update as one page, *Use the library* (`docs/user-manual/use-the-library.md`), with a worked example that the end-to-end test of 2.2.0 runs.

### Known limits

- **Only the device whose ID is the library's ID follows it,** and its copies (`PCDU00-R`, `PCDU00-3`). A device you renamed in the project, or added under another ID, does not follow the library. A field that would link any device is left for a later format.
- **No common base.** The program compares the project's device with the library's version of today. When both sides changed a device, it cannot tell which side changed a field: the review shows both values, and you choose.
- **`import-devices` is unchanged.** It reads one file you name, gives a taken ID the next free one without asking, and writes the same kind of record. Use `add-device` and `update-device` for devices that should hear about changes.
- **Two project folders that went through the same steps differ in `journal.jsonl` only:** each entry of the change journal carries the time of the change.
- **The program keeps the old file as `.bak`** when it replaces a device file. Add `*.bak` to the library's `.gitignore`.
- **The limits of 2.1.x stand.** Until a harness can branch (2.3.0), interfaces from one connector to different far connectors get one plug each on it. In Guided mode the message after connecting does not say that a shared connector gets a second plug. The prototype counts the pins of the part, not the ports, and has no device library.
- **Nobody has looked at the screens on a real display**, and the Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values are placeholders until your project supplies them.
