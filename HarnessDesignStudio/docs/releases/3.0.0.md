This is **version 3.0.0**, a major release. It brings **format 3**, a new version of the project file format, and with it three things: a harness has a **version MAJOR.MINOR.PATCH** (`1.0.0`, `1.1.0`, `2.0.0`) in place of a revision letter, and the screen and the written files say *Version* where they said *Revision*; the export can write the **harness plan** of each harness, an `.ods` spreadsheet with formulas in the users' layout; and a harness you drew can join wires at a **splice**. **Upgrade each project once** (`migrate`, or the editor's question): after the upgrade, versions 2.x open the project read-only, so update the whole team at the same time. If a script reads the written files or the output of the commands, read *For scripts* below: every renamed heading, key, file and command is listed there. The guides are *Upgrade a project* and *Versions* in the user manual (`docs/user-manual/upgrade-a-project.md`, `docs/user-manual/versions.md`).

### From 2.x to 3.0.0: upgrade each project once

- **Install over 2.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Nothing is upgraded without you.** A project saved by 2.x is in format 2. This version reads it, but saves it only after you upgrade it. Commands that save refuse a format 2 project and write nothing; `validate`, `check`, `drc` and `export` still read it.
- **How to upgrade.** In the editor, open the project and answer the question with **Upgrade**. On the command line, look first with `harness-design-studio migrate DIR --dry-run` (it writes nothing), then run `harness-design-studio migrate DIR`. The backup is the folder `.migration-backup-v2/` with the record `MIGRATION.json`.
- **What changes.** Each revision letter becomes a version by its place, **the Nth letter is N.0.0**: A is `1.0.0`, B is `2.0.0`, Z is `26.0.0`, AA is `27.0.0`. That holds for the harness, each of its baselines and each change-log entry; each baseline is stored under its new name (`baselines/W001/W001.1.0.0.json`). A revision that is not a letter (`A1`, `-`) is not guessed: `migrate --dry-run` names it, and `migrate --set-version W001:A1=1.1.0` gives its version. Before it writes, the upgrade checks on the files that nothing but the versions changes (the same design, findings and released harnesses) and that every version is the mapping of its revision; if anything differs, it writes nothing.
- **Export once after the upgrade.** Unlike the step to format 2, this step changes the model hash once, so the outputs exported before it read *out of date*. `verify --outputs` compares them with the version that runs, so outputs written by 2.x fail it until you export them with 3.0.0.
- **Older versions and Git branches.** After the upgrade, versions 2.x open the project read-only (*saved by a newer version of the tool*) and change nothing. Upgrade on the main branch first, then bring the other branches up to date. A branch still in format 2 that is merged later brings a key `revision` or a letter into a file of format 3: `check` names it (`revision_not_version`), and `merge-fix` rewrites it by the same rule.
- **From 1.17.1 or older**, the upgrade goes through format 2 to format 3 in one step; read the notes of 2.0.0 first.

### The main changes

- **Versions.** A new harness starts at `1.0.0`. `new-version DIR HARNESS --kind major|minor|patch` (in the editor **New version…**) starts the next version of a released harness: from `1.4.2`, major gives `2.0.0`, minor `1.5.0`, patch `1.4.3`. A person chooses the kind; the tool suggests none. Until the review starts the kind can be chosen again, and the change log records *version changed*. Two notes help with the choice and block nothing: one on a major version (the template gives an incompatible harness a new ID instead), one on a minor or patch version that changes the pinout at a device. `diff --from A` still reads an old letter and says which version it is.
- **The harness plan.** `export --harness-plan` (in the editor the check box **Include the harness plans (.ods), one per harness**) writes `harnesses/<ID>/<ID>_plan.ods` for each harness: the Cover, the change register of that harness, the harness sheet with the device side and the harness side of every pin, the Notes and one `CON_…` sheet per device connector, in the layout of the users' template. The cells that follow other cells are formulas from a short closed list, each with its stored value, so a program that does not recalculate shows the same. `document` (in the editor **Settings > Document** and the Inspector's **Plan document**) sets what the Cover shows. A colour code by pin number can colour the ends of a connector with pigtails; the users' code ships as an example only (`pigtail-colour-code-EXAMPLE.csv`), applied when a person takes it. `verify --outputs` works out every sheet and cell of each plan again, without the code that wrote it.
- **Splices.** A splice joins several wires inside a harness you drew: the **Splices** list of the Harness tab has **Add splice**, **Splice this wire** and **Delete splice**. The tests follow the nets through the splice (one continuity test per pair of ends, one isolation test per net), the wire list gets a last column *Via*, the build workbook a block per splice, and the harness plan follows the wires through the splices. The template `splice-parts-EXAMPLE.csv` holds one example splice part; the tool ships none.
- **The users' sheets come in.** `import-pinout` reads the headings *Pinout*, *Function*, *Direction*, *Level* and *Description* and the Direction words `PWR`, `PWR-RET`, `GND`, `SGND`, `SHIELD` and `SPARE`, and the source of a pinout (*Source*, *Source version*, *Source link*); `import-parts` reads a part's *Link*. The Devices tab has the pin column **Level**, the role **Signal ground** and the connector's source.
- **The editor opens no browser.** The link of a part and the source link of a connector are copied to the clipboard (**Copy link**, **Copy**), to paste where you choose.
- **A project without the new things writes what it wrote**, apart from the words and the versions: the drawings, *Start here*, the change log and the version report say *Version*, and `system/revision_report.md` is now `system/version_report.md`. An export without `--harness-plan` writes no plan, and a harness without a splice keeps its files.

### For scripts

Every place where a script can meet the renamed word, from section 5.8 of the design (`docs/ait/DESIGN_3.0_HARNESS_PLAN.md`). The old names that are kept work through 3.0.x.

**Written files**

| File | 2.x | 3.0.0 |
| --- | --- | --- |
| `system/revision_report.md` | the file name; `# Revision report: …`; `revision A, released`; `revision A to B`; `- revision: A -> B`; `working design against revision B` | `system/version_report.md` (an export removes the old file); `# Version report: …` and the same lines with *version* and the version |
| `manifest.json` | lists `system/revision_report.md` | lists `system/version_report.md` |
| `system/changelog.csv` | heading `Entry,Harness,Revision,Event,…`; the letter in the third column; event *new revision started* | heading `Entry,Harness,Version,Event,…`; the version; events *new version started* and, new, *version changed* |
| `system/system.xlsx`, sheet *Change log* | heading *Revision*; the letter; *new revision started* | heading *Version*; the version; *new version started*, *version changed* |
| `system/export.json` | `"revision": "A"` in each harness | `"version": "1.0.0"`, and `"revision"` beside it with the same value through 3.0.x; `format_version` stays 1 |
| drawings (`drawing_*.svg`, `drawing_*.pdf`) | title block field *REVISION* with the letter; header `Revision A  status draft` | *VERSION* with the version; `Version 1.0.0  status draft` |
| build workbook `<ID>_build.xlsx`, *Start here* | `Revision A   ·   status …` | `Version 1.0.0   ·   status …` |
| `system/drc_findings.csv`, `system/drc_report.md` | the findings of the release consistency and the fix of `released-modified` with *revision* (*start a new revision for the change*) | the same with *version* (*start a new version*); they appear only where a release history is broken |
| harness plan `<ID>_plan.ods` | — | new; *VERSION:* and *Version* as in the users' template |

**Project files (format 3)**

| File | 2.x | 3.0.0 |
| --- | --- | --- |
| `project.json` | `"schema_version": 2` | `"schema_version": 3` |
| `physical/harnesses/<ID>.json` | key `revision`, a letter | key `version`, MAJOR.MINOR.PATCH |
| `changelog.json` | key `revision`; kind `new_revision` | key `version`; kinds `new_version` and, new, `version_changed` |
| `baselines/<harness>/` | `W001.A.json`, `"id": "W001.A"`, key `revision` | `W001.1.0.0.json`, `"id": "W001.1.0.0"`, key `version` |
| `config/titleblock.json` | the field `revision` in `fields` | the field `version` |
| `journal.jsonl` | — | old lines keep their keys and letters; the step's entry *migrated from format 2* names the mapping (`W001: revision B → version 2.0.0`), as `MIGRATION.json` does |

The schemas of `schema FOLDER` and `docs/FILE_FORMAT.md` follow. In a file of format 3, a key `revision`, an upper-case letter under `version`, the kind `new_revision` or the title block field `revision` is the error `revision_not_version`; `merge-fix` rewrites them.

**The command line**

| Place | 2.x | 3.0.0 |
| --- | --- | --- |
| `revise` | *start a new revision of a released harness* | `new-version` with `--kind major\|minor\|patch`; `revise` stays as its older name, needs `--kind` too and is left out of the command list of `--help` |
| `migrate` | — | `--set-version HARNESS:OLD=VERSION` for a revision that is not a letter |
| `diff --from`, `--to` | *baseline revision …*; `W001: revision A to B` | the option names stay; *baseline version …*; `W001: version 1.0.0 to 2.0.0`; an old letter is read as its version, said once (`--json`: `read_as`) |
| `log` | heading *Revision*; `--json` key `revision` | heading *Version*; `--json` key `version`, with `revision` beside it through 3.0.x |
| `review`, `release`, `new-version` | `Release W001 revision B: done.`; `New revision B of W001`; the same in `--json` `action` | `Release W001 version 2.0.0: done.`; `New version 2.1.0 of W001`; `--json` also lists the notes under `notes` |
| `compare` | *only their revision, date, name, comment and hash*; the baseline field `revision` | *only their version, …*; the field `version` |
| `workflow` | the stage *Revisions*; *start a new revision (revise)*; `system/revision_report.md` | *Versions*; *start a new version (new-version)*; `system/version_report.md` |
| messages of `check`, `validate`, `explain` and of refused edits | *released (revision B)*, *start a new revision*, *Revision B of W001 already has a baseline* | the same with *version* |
| the expression field of the extensions | `harness.revision`, *The revision letter.* | `harness.version`; `harness.revision` stays as its older name through 3.0.x, with the version as value |
| `export` | — | `--harness-plan`; `--json` adds `harness_plans` and `harness_plans_removed` |
| `document` | — | new: the document data of the plans |
| `merge-fix` | — | rewrites a key `revision` and a letter after a merge with a branch in format 2 (`--json`: `versions`) |

**The scripting interface** (`harness_design_studio.api`): `API_VERSION` stays 1. `api.export(..., harness_plan=True)` writes the plans, and `ExportResult` gets the fields `harness_plans` and `harness_plans_removed`.

**What still says *revision*:** old journal lines, files exported by 2.x, printed drawings, the migration record (it names both words), and identifiers that are never shown (the undo counter of the history, the constant names of the screen texts, the object names and the file names of the screenshots).

### Known limits

- **No look at a real display.** The new screens (the *New version* window, the Export window's check box, *Settings > Document* and *Settings > Harness plan*, the Devices tab's new columns, the *Splices* list) were tested offscreen only. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **The harness plan.** The tool never reads a plan back, and an export overwrites it: work on a copy. The search boxes of the users' template are not written (they need functions outside the closed list). With LibreOffice installed, a test compares the values it shows with the stored ones; no workflow installs LibreOffice, so in CI that test skips.
- **Splices.** Generate makes no splice, and a splice is placed only in the editor (no command-line edits). The Inspector shows a splice as a connector.
- **No compliance and no sign-off is claimed.** The configuration values and the example colour code and splice part are placeholders until your project supplies its own.
