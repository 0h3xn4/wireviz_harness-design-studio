This is **version 4.0.1**, a patch release of 4.0.0. With it a project whose labels are in the format `compact`, `descriptive` or `custom` can be exported again: the export's own check of the written files now knows every label format, where before it knew only the standard one and wrote nothing. **There is no format change:** 4.0.1 writes format 4 as 4.0.0 does, and format 4 stays frozen. If you come from 4.0.0, install 4.0.1 over it; your projects need no step. If you come from 3.x, read the notes of 4.0.0 first: each project is upgraded once to format 4. If you come from 2.x or older, the same upgrade takes a project through every format to format 4 in one step. The guide is *Upgrade a project* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### From 4.0.0 to 4.0.1

- **Install over 4.0.0.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Update the whole team at the same time.** 4.0.0 and 4.0.1 each write their version into `project.json` and the generation record. A team that mixes them changes these files on every save.
- **Projects stay as they are.** Every file that 4.0.0 wrote has the same content, apart from the version stamp and the model hash that includes it. The command line and the scripting interface are unchanged.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 4.0.0 fail it until you export them with 4.0.1.

### Every label format passes the export's check

- **Why.** The setting `model.label_format` chooses the text on the labels of wires and cable connectors: `standard`, `compact`, `descriptive`, or a template of your own (`custom`). Since 1.15.0 the export checks every file it writes against the design on its own, before it writes anything, and that check knew only the standard text. So `export` stopped a project in any other label format with `out_labels` (the labels table) and `out_build` (the Labels sheet of the build workbook) and wrote nothing, in the editor as on the command line, and `verify DIR --outputs` refused such a set the same way (pull request 306).
- **What changes.** The check now words the label of a wire and of a cable connector for the format in force, and fills a template in by the same rules as the writer, with its own copy of them. A project in any label format is exported, and a wrong label text is still refused in every format, also the standard text where another format is in force.
- **What stays.** The labels table and the Labels sheet are the only written files that carry the label texts, and the writer is unchanged: a project in the standard format writes the same bytes as with 4.0.0, apart from the version stamp. See [labels and colours](../models/labels-and-colours.md).

### Also on master since 4.0.0

- **The publication record of 4.0.0** (pull request 305): the record in `compliance/SIGNOFF.md`, the checksums in `compliance/evidence/release_4.0.0_SHA256SUMS` and the status lines. It is a document only; the program is unchanged.

### Known limits

- **The limits of 4.0.0 stand.** No datasheet was read, so the rows in the documents are examples of the form; the rule on the face takes the rows as centred on each other and does not judge pins of different rings; Generate does not read the rows, and no face is drawn. 3.x opens a format 4 project read-only.
- **No look at a real display.** Nobody has looked at the screens of 4.0.0 on a real display; they were tested offscreen. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
