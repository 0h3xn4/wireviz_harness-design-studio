This is **version 4.2.0**, a minor release of 4.1.0, and it teaches the design rule check four electrical questions it could not ask before. Is a signal pair twisted? Does a signal that its interface type shields actually run in a shield? Does a wire join two signal levels that must stay apart? Do two outputs drive one wire, or does a wire join only inputs? **The tool now has 43 design rules**, and every DRC report says so. A fault of Generate is fixed on the way: an interface type of construction `single` that shields overall now gets its shield. **There is no format change:** 4.2.0 writes format 4 as 4.1.0 does, and format 4 stays frozen. The rules read what a project already holds (the pairs and the shielding of the interface types, and the *Direction* and *Level* of the device pins), plus two new settings in `config/`. The guides are *Build a harness by hand*, *Connect two connectors* and *Edit a wire* in the user manual (`docs/user-manual/build-a-harness-by-hand.md`, `docs/user-manual/connect-two-connectors.md`, `docs/user-manual/edit-a-wire.md`), and the rules themselves are listed in [the rule reference](../RULES.md).

The work answers points 2 and 8 of the feedback that an electrical engineer gave in November 2026 ([the plan](../ait/ELEC_FEEDBACK_PLAN.md), milestone E2; [the design](../ait/DESIGN_4.2_ELECTRICAL_CHECKS.md)): an RS-422 pair has to be twisted, some analog signals need a shield of their own, a supply-level signal must not land on a 3.3 V input, and two inputs on one wire are a mistake.

### From 4.1.x to 4.2.0

- **Install over 4.1.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Your projects open as they are.** Nothing is upgraded and nothing in a project file changes. A project made from one of the five templates gets no finding of the new rules: their harnesses are all generated, and none of them has a connection, a wire drawn by hand, a pin direction or a pin level.
- **Update the team together if you draw harnesses by hand.** A 4.1.x tool reads a project with the two new settings, keeps them when it saves and says nothing about them, but it does not run the new rules. So a colleague on 4.1.x sees none of the findings and can release a harness that 4.2.0 blocks with a `level-conflict` or `wire-direction` error.
- **Export once.** Every `system/drc_report.md` changes (it says `Rules run: 43.`), and a project with such harnesses or levels gets new rows in its findings files. `verify --outputs` compares the files in `outputs/` with the version that runs, so outputs written by 4.1.x fail it until you export them with 4.2.0.

### Four new design rules

The first two rules are warnings. They can be waived with a reason. The last two are errors, which block the release of their harness.

- **Twisted pairs** (`pair-untwisted`, a warning). Two wires of a signal pair that no twisted pair, shielded pair or quad holds together. On a generated harness the pair is the one the interface type names; Generate twists those pairs anyway, so this matters there only for a type of construction `single` whose signals name a pair. On a harness drawn by hand or made from a connection the wires have no interface, so the rule reads the signals at the device pins. Two signals are a pair when every interface type that has both pairs them (`TX+` and `TX-` of `rs422`). Where no type has both, two names that differ only by a pair of endings count as a pair: `+` and `-`, `P` and `N`, `H` and `L` by default (`1PPS+` and `1PPS-`, `TXP` and `TXN`, `CANH` and `CANL`). It needs nothing new from the project: the signal names and the pairs of the interface types are there already. A wire part with two conductors does not count as twisting; only a group does.
- **Shielded signals** (`signal-unshielded`, a warning). A wire of a harness that Generate did not make, whose signal is shielded by every interface type that has it (overall, per pair for a signal of a pair, or a coax), and that sits in no shielded pair, overall shield, coax or quad. A twisted pair is not a shield. A generated harness stays with the check that has judged its shields for years (the verifier's `shield_missing`), so one missing shield gives one finding, not two. When the types that have a signal disagree, for instance when a team's own unshielded type also has a `TX+`, the rule says nothing about that signal.
- **Signal levels** (`level-conflict`, an error that may be accepted as a deviation). A wire, or wires joined on one pin or through a splice, that join two device pins whose **Level** is a pair the project keeps apart; and, for a connection that has no harness yet, a pair of pins with such levels. The levels come from the pinout (the *Level* column of `import-pinout`, or the Devices tab), and the pairs to keep apart come from a new table, `config/segregation.json` `level_pairs_to_separate`, for example `[["28V", "3V3"]]`. Levels are compared as whole words, with case and outer spaces ignored. The tool reads no number out of a word, so `3V3` and `3.3V` are two different words, and `RS422-3V3` is not `3V3`. A level shifter inside a device is something a table of words cannot know, so an accepted deviation (`deviation DIR FINDING --reason TEXT`, or *Accept as deviation* in the editor) lets the release go on, and the finding stays on every list marked DEVIATION, with a line under *Overrides and deviations* on *Start here* of the build workbook.
- **Directions of drawn wires** (`wire-direction`, an error). A net of wires drawn by hand that joins two outputs, which drive against each other, or only inputs, which nothing drives. The directions are those the review of connections reads: the *Direction* set on the pin (from a pinout's *Direction* column, or from a KiCad netlist with `--pin-direction`), else the direction its interface types give the signal. A generated wire stays with `direction-conflict` and a pair of a connection with `link-direction`, as before, so no fault is reported twice. A net with a loose end is not judged.

**The level table is empty by default.** The tool ships no level word and invents none: no template, example or new project has the table. Until a team fills it in, *Signal levels* checks nothing. It does not stay quiet about that, though. Where a pin has a level, a note says *Signal levels were not checked: 9 pin(s) have a level (18V, RS422-3V3), but no pairs of levels to keep apart are set*, and the *Checks* tab shows the rule as *pending*. So a team that wants the level check lists the pairs of its own ICD words, in *Settings > Engineering values*, *Signal levels kept apart* (`28V + 3V3`), or on the command line:

```
harness-design-studio settings DIR --set segregation.level_pairs_to_separate='[["18V", "RS422-3V3"]]'
```

**Silence is not a pass.** Each rule says, as a note of *Checks not run*, what it could not judge, but only where the project holds the data that makes the question real: `levels` (pins have levels, the table is empty), `no-level` (the table is set and no pin has a level), `level-unknown` (a net has an end without a level) and `wire-direction-unknown` (a pin at an end of a drawn wire has no direction). A project without such data gets no new note.

**How you answer them.** For the first two, select the wires and use **Group wires**. A pair that must be twisted and shielded, such as an RS-422 pair, is one *shielded pair*: a wire that is in a group already cannot go into a second one by hand, so that one group says both. For the last two, move the wire to a pin that fits, or correct the level or the direction of the pin in the Devices tab. `explain DIR --all --out FOLDER` and the editor's *Explain* say what each rule read: the pair and where it came from, the types and how each shields, the levels at the device ends and the pair of the table, and the direction of each end with whether it came from the pin or from the types.

A short example, the one the release was tested with. Two RS-422 devices are imported with their *Direction* and *Level* columns, joined by a connection, and given a harness made from it. That harness of four plain wires gives two *Twisted pairs* and four *Shielded signals* warnings and the note `levels`. Add the table `[["18V", "RS422-3V3"]]` and a second harness drawn by hand between the same connectors, with a TX+ on a TX+, an RX+ on an RX+, the 18 V return on a TX- and a TX- on an RX-, and the report has seven *Shielded signals*, one *Signal levels* and two *Directions of drawn wires* findings.

### Generate makes the shield of a `single` type that shields overall

An interface type of construction `single` with `shielding` `overall` got no shield group from Generate. The generator skipped every `single` type before it looked at the shielding, a skip that dates back to its first version. Its own verifier then reported `shield_missing`, `generate` refused to save (*Not saved: fix the errors above first*), and `drc` showed a `verify-mismatch` error whose fix, *Regenerate harnesses*, changed nothing. Now such an interface gets one `overall_shield` over all its wires, made the way the overall shield of every other construction is made, with the shield ends of the grounding concept. `explain` of the group says why. None of the starter types is such a type, so a project made from a template never met the fault and nothing of it changes. In a project with such a type, Generate now saves, and the wire list, the cut list, the *Production* sheet, the drawings and the plan name the new group; groups made after it in the same harness take the next numbers.

### The new settings

| Setting | Default | What it does |
| --- | --- | --- |
| `segregation.level_pairs_to_separate` | not set | the pairs of level words that a wire, a net or a pair of a connection must not join; read by *Signal levels* ([configuration](../CONFIG.md#signal-levels-kept-apart-since-420)) |
| `naming.pair_suffixes` | `+ -`, `P N`, `H L` | the endings that make two signal names a pair where no interface type pairs them; read by *Twisted pairs* ([configuration](../CONFIG.md#the-endings-of-a-signal-pair-since-420)) |

Both are set with `settings DIR --set`; the level table also has its field in the editor. `validate` refuses a table that holds a word twice in one pair (`["3V3", "3v3"]` is one word, case ignored), an ending longer than three characters or an ending in two rows, with `config_invalid`, and a refused table keeps its rule silent. Four assumptions are new: `A-PAIR-NAMES`, `A-SHIELD-BY-TYPE`, `A-LEVEL-WORDS` and `A-DIRECTION-AT-DEVICE`, listed by `settings DIR` and explained on [shield groups and shield ends](../models/shields.md) and [the limit of every design rule](../models/rule-limits.md).

### Which written files change

- **Every `system/drc_report.md`** says `Rules run: 43.` where it said `Rules run: 39.`.
- **`system/drc_report.md`, `system/drc_findings.csv` and the *DRC findings* sheet of `system/system.xlsx`** of a project with a harness drawn by hand or made from a connection that has a signal pair, a shielded signal or a net of known directions, or with pin levels: the new findings and notes.
- **The build workbook's *Start here*** of a harness whose `level-conflict` was accepted as a deviation: a line under *Overrides and deviations*.
- **The generated harnesses** of a project with an interface type of construction `single` that shields overall: the new shield group, and with it the files that list groups.
- Nothing else. The other files, `system/export.json`, the drawings, the plans and the project files are as 4.1.0 writes them, apart from the version stamp.

### For scripts

A script that reads the findings of the design rule check may see the following.

| Place | 4.1.x | 4.2.0 |
| --- | --- | --- |
| `drc --json`, `api.run_checks()` | `rules_run` 39 | `rules_run` 43 |
| `api.list_rules()` | 39 rules | 43: `pair-untwisted`, `signal-unshielded`, `level-conflict` and `wire-direction` come right after `direction-conflict` |
| `rule` of a finding | — | the four IDs above; `can_waive` is true for the two warnings and false for the two errors, and of those `level-conflict` takes a deviation (`deviation DIR FINDING`), `wire-direction` does not |
| `id` of a finding | — | `signal-unshielded.W001.W001-001` and `wire-direction.W002.W002-001` (harness and wire); `pair-untwisted.W001.W001-001_W001-002.<hash>` (the two wires); `level-conflict.W002.W002-003.DEV1-J01.6_DEV2-J01.4.<hash>` (the wire and the two device pins); the hash is short and stable |
| `object_id` | — | a wire (the first of a pair or a net); for a `level-conflict` on a connection without a harness, the connection (`L1`), which no harness's release counts |
| notes (`rule` `unchecked-config`) | — | `object_id` `levels`, `no-level`, `level-unknown`, `wire-direction-unknown` |
| `open_errors`, exit code of `drc` | — | a harness drawn by hand can now have open errors, so `drc` exits 1 for it (and `release` refuses it) where 4.1.x exited 0 |
| `drc_findings.csv` | — | the rows of the four rules; *Waived* reads `deviation` for an accepted `level-conflict` |
| `Rules run:` in `drc_report.md` | `39` | `43` |

The command line keeps its commands and options; the help of `deviation` now names *signal levels* among the errors that take a deviation. The scripting interface keeps its names (`API_VERSION` 1). An extension's rules start with `x-`, so they cannot clash with the new IDs, and `Rules run` counts 43 plus the extension's rules.

### Known limits

- **A `single` type that shields per pair still gets no shield.** A `single` construction twists no pair, so there is no pair for a per-pair shield to go over; the verifier still reports `shield_missing` for such a type. Give the type a twisted construction (`twisted_shielded_pair`) or let it shield overall.
- **Pairing by endings can pair signals that are no pair.** A `HEATER_H` and `HEATER_L` that are the high and the low side of one heater read as a pair by their `H`/`L` endings, and *Twisted pairs* then asks for them to be twisted. Take the row `H L` out of `naming.pair_suffixes` for such a project (`settings DIR --set naming.pair_suffixes='[["+", "-"], ["P", "N"]]'`), or waive the finding with a reason. Endings are compared exactly, so `p` is not `P`.
- **Levels are words.** The rule is only as good as the table and the words the ICDs use; nobody has told the tool a team's real level words yet. Neighbouring pins, two pins of one connector and one bundle are not checked for levels in this release; only a wire, a net or a pair of a connection is.
- **A shield is asked per interface type, not per signal.** A field that says *this one signal needs its own shield* would be a new key of a project file, so a format change; it is planned for a later major release (milestone E5 of the plan). Until then a signal asks for a shield through its interface type (`analog` shields overall, a coax).
- **One finding per wire** for *Shielded signals*: a connection with ten RS-422 lines gives forty findings until its pairs are grouped.
- **A generated wire's directions** are still judged by its interface type (`direction-conflict`), even where both device pins carry a direction of their own.
- **`explain` takes no finding ID on the command line.** `explain DIR --all --out FOLDER` writes what each rule read for every finding (`derivations.json`), the editor's *Explain* shows it for one, and a script calls `api.explain_finding(project, finding_id)`.
- **Nobody at a bench or a review has read the findings yet.** The texts are the design's. No screen of the editor changed its layout: the new rules show up where every rule does (the *Problems* panel, the *Checks* tab, *Explain*), and the level table is one more field under *Engineering values*. Nobody has looked at those screens on a real display; they were tested offscreen. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
