This is **version 4.4.1**, a patch release of 4.4.0. With it a new issue of a device's ICD in the library shows as a change: the review of a library device now compares the ICD a connector came from (document, issue, link) and the level of a pin too, where before a library file whose only change was one of them read *up to date*. **There is no format change:** 4.4.1 writes format 4 as 4.4.0 does, and format 4 stays frozen. If you come from 4.4.0, install 4.4.1 over it; your projects need no step. If you come from 4.3.x or older 4.x, read the notes of 4.4.0 first. If you come from 3.x, read the notes of 4.0.0 too: each project is upgraded once to format 4. The guide is *Upgrade a project* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### From 4.4.0 to 4.4.1

- **Install over 4.4.0.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Update the whole team at the same time.** 4.4.0 and 4.4.1 each write their version into `project.json` and the generation record. A team that mixes them changes these files on every save, and a 4.4.0 tool still calls a device *up to date* when only its ICD or a pin level changed in the library.
- **Projects stay as they are.** Every file that 4.4.0 wrote has the same content, apart from the version stamp and the model hash that includes it. The command line, its `--json` keys and the scripting interface are unchanged.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 4.4.0 fail it until you export them with 4.4.1.

### A new ICD issue of a library device shows as a change

- **Why.** A device that came from the library follows its library file: the editor and `libraries DIR --devices` say whether it is *up to date*, and `update-device` (or **Review…**) lists the fields that differ, one row each, and takes the library's version. The fields that say which ICD a box connector came from (`source_doc`, `source_version`, `source_link`, since format 3) and the level of a pin (`level`) were not among the fields it compared. So a library file whose only change was a new issue of the device's ICD read *up to date*, the review showed no row and taking the library's version took nothing. When another field changed as well, the whole connector was taken and these fields came along without a row (pull request 350).
- **What changes.** They are compared like the other fields of the library. Such a device reads *library changed*, the review lists a row for each (`RW1-J01  source_version  -  Issue 2`, `RW1-J01  1  level  -  3V3`; the connector's after its row layout, the pin's after its direction), and taking the library's version takes them, one undo step as before. A level row of a pin that a released harness uses names that harness, as the other fields of the pin do.
- **What you may see after the upgrade.** A linked device whose library file changed only in these fields since you last took it reads *library changed*. A device whose ICD fields or pin levels were changed in the project, and not in the library, reads *changed here*. In 4.4.0 both read *up to date*. A device whose fields are the same as in the library reads *up to date* and gives the same rows as with 4.4.0. See [Use the library](../user-manual/use-the-library.md).
- **Where it comes from.** The design of the next major release (pull request 351) found it while it planned how ICDs are kept, and asked for it as a fix of 4.4.0, ahead of that release.

### Known limits

- **The limits of 4.4.0 stand.** Nobody on a team has named pins after devices in this tool yet; a device ID that looks like a port name makes every port named after it that device's; the signal map renames at import only; there is no importer of a team's ICD format.
- **Nobody has used the library update with a real team's ICD issues.** The fix was tested with the example projects and a library folder made by the tests.
- **No look at a real display.** Nobody has looked at the screens on a real display; they were tested offscreen. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
