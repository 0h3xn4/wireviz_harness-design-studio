This is **version 5.1.0**, a minor release of 5.0.0. It brings **a template for each feature**: the list of examples has a second group, **Feature examples**, with fourteen small projects that show one feature each, among them a project whose connectors are fully populated and two that show how to make a spliced harness. A new project made from an example now also gets the extensions and the device library that the example keeps beside its model. **There is no format change:** 5.1.0 writes format 5 as 5.0.0 does, and format 5 stays frozen. A project keeps every file it wrote with 5.0.0, apart from the version stamp, and one wrong note less where devices are joined only by a harness drawn by hand. The guide is the new page *Examples* of the user manual (`docs/user-manual/examples.md`), which lists every feature with the example that shows it and the page that explains it.

The work answers the owner's request of 2026-11-24 for example projects that cover every feature of the tool, one with connectors that are not empty but fully populated, and examples that show how to make a spliced harness ([the design](../ait/DESIGN_5.1_FEATURE_TEMPLATES.md), decision D-268; the release, D-269).

### From 5.0.x to 5.1.0

- **Install over 5.0.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Your projects open as they are.** Nothing is upgraded and nothing in a project file changes; there is no step to run.
- **Export once if you use `verify --outputs`.** It compares the files in `outputs/` with the version that runs, so outputs written by 5.0.x fail it until you export them with 5.1.0.
- **Two tools on one team.** A 5.0.0 tool opens a project made from a feature example, or a copy of one, as it is: the examples hold no key that 5.0.0 does not read (the code of `v5.0.0` opened, checked and ran `drc` on every example with 0 errors). It lists only the five examples of *Start*, and its `new` copies the model of an example but not its `extensions/` or library folder.
- **From 4.x or older**, read the notes of 5.0.0 first: a format 4 project is upgraded once to format 5.

### The feature examples

Each is a small project of two to four devices, made by the tool's own edit functions and shipped ready to look at: generated where Generate has something to make, with no journal and no `outputs/`. On every one `check` gives 0 errors and 0 warnings, `generate` has nothing to do, `drc` gives no open error, and `export` writes the outputs that `verify --outputs` checks with 0 errors. Make your own copy with `harness-design-studio new practice --template NAME`, **File > New project from an example…**, or the button **Show the feature examples…** on Home.

- **Connectors.** `full-connectors`: PCDU1, OBC1 and TTC1 with six nine-way Micro-D device connectors whose 54 pins all carry a fixed, named signal and a wire; named ports with each interface put on its port, the pin rows 1 to 5 over 6 to 9, the keying `A` and `B` on the two identical connectors of a device; generated, no spare pin.
- **Splices.** `splice-by-hand`: a power line drawn by hand from PCDU1 to OBC1 and TTC1 through the splices `W001-X1` and `W001-X2` of the EXAMPLE part `EX-SPLICE-1`, so the wire list has the column *Via* and `tests.csv` the tests through each splice. `splice-from-connection`: a connection that joins one pin to two pins (a junction), with pin currents, so its harness has the splices and its wires carry 4 A on the trunk and 2 A on each branch, worked out from the pins.
- **Routing.** `branching-harness`: four devices, and Generate makes two harnesses that branch where one connector serves two devices. `loose-cable-end`: a bench cable drawn by hand from a test port, with its far ends loose and a leg added behind a branch point, so a release asks for a reason (`--accept-loose-ends`). `shields-and-ends`: a grounding concept, shielded pairs and an overall shield, pigtails landed on a pin and on the lug of a backshell, 360 degree ends in backshells, and one end without a place. `lengths-to-the-face`: segments measured to the mating face, the depth of each connector and backshell taken off each wire, and a length model with a cut allowance.
- **Change control.** `released-harness`: a harness reviewed and released with the review checklist and three different people, then its next version started, so `log`, `diff` and the version report have something to show. `overrides-and-deviations`: a gauge set by hand with its reason, a warning waived and two errors accepted as deviations (`drc` says *Waived: 1. Deviations: 2.* and exits with 0).
- **Data in and out.** `names-and-ports`: OBC1 talks to TTC1 and TTC2 on one connector whose ports are named after them, with the pinouts read in the team's words through the project's signal map. `build-data-and-as-built`: strip lengths, a contact and its crimp tool, accessories, a colour code by pin and the Cover of the harness plans, then a record of what was built with one value out of its limit. `imports-from-files`: the devices of `first-steps` and what the import templates hold, each import with its record; `imports DIR --source` with the files `templates` copies says *unchanged* for all seven.
- **Library and extensions.** `device-library`: devices taken from a library folder inside the project, one checked against its ICD, one with a copy, one changed in the library since it was added, and a subsystem, so `libraries --devices` and `update-device` have something to show. `extensions`: a rule and a table in data files, both applied (*Rules run: 45*), and a Python plug-in that stays off until you trust it (`trust DIR duplicate-signal-wires` is the exercise).

**EXAMPLE data only.** Every engineering number in a feature example (a length, a depth, a current, a rating, a tolerance) is an EXAMPLE value; every configuration file stays a placeholder; every part the examples add (`EX-SPLICE-1`, `EX-BACKSHELL-MICROD`, `EX-CONTACT-22`, and the EXAMPLE contact ratings) is in the example's own library, unverified and never approved; and an example with numbers says *(EXAMPLE)* in its title, so every title block of its outputs says so. The starter library does not change. The new import template `device-pinout-EXAMPLE.csv`, which `templates FOLDER` copies, holds the pinout of one nine-way connector with every column `import-pinout` reads, EXAMPLE values only.

### The list, the window and Home

- **`new --list`** prints a heading line per group, *Start:* and *Feature examples (small projects, one feature each; the manual page Examples lists them):*, and pads the names to the longest name plus two. The five examples of *Start* come first and are as they were.
- **The window *New project*** has a heading row per group, **Start** and **Feature examples**, which cannot be chosen and which the arrow keys pass over, each with its own accessible name. *New project from an example…* still chooses `first-steps`.
- **Home** lists the group *Start* as before and ends with one line, *14 feature examples, one per feature: File > New project from an example…*, and the button **Show the feature examples…**, which opens the window with `full-connectors` chosen.
- **The user manual** has the new page *Examples*, and each page whose feature an example shows has the line *Example* under its title. The in-app guide (section 3), `README.md`, *Getting started*, the FAQ and the examples page say that there are two groups.

### A new project gets the files beside the example's model

`create_project` (the command `new` and the editor's *New project*) now also copies, from the example's folder, the folder `extensions/`, the file `device-libraries.json` and the library folders it names that lie inside the example's folder, and nothing else. A path with `..`, a link, and a folder whose place the new project has already taken are not copied, and no file is written over another. The trust of a Python plug-in is kept in your settings folder and is never copied, so a plug-in of an example stays untrusted until you trust it. A project made from one of the five examples of *Start* gets none of these files, as before.

### Fixes

- **The note `isolated` no longer names a device that a harness drawn by hand plugs into.** It said *OBC1 is not connected to anything yet* of a device that a drawn harness or a cable with a loose end plugs into, because it counted only interfaces and connections. It now also counts the device connectors a harness plugs into, and `explain` of the finding lists the harnesses that plug into the device. The words of the note do not change.
- **`explain` of the gauge of a wire drawn by hand without an interface** said *Gauge the search gives now = not decided [... interface current (set Max current on the interface)]*, though Generate never sizes such a wire. It now says *drawn wires are not sized; set the gauge*.
- **The build of the examples stops on an open error only.** The builder of the examples (`tools/feature_examples.py`, which is not part of the program) counts the errors that are not accepted, as `drc` counts its open errors, so the two errors that `overrides-and-deviations` accepts as deviations do not stop it, and any other error does.

### Which written files change

- **Nothing**, for a project of 5.0.0: every file of `export`, `export-data` and the harness plans has the same content as with 5.0.0, apart from the version stamp and the model hash that includes it. The stored hashes of the written files, the numbers snapshot and the golden outputs are as for 5.0.0, apart from the stamp.
- **The findings of a project whose devices are joined only by harnesses drawn by hand**: one note `isolated` less per such device in `drc`, `system/drc_findings.csv` and the design rule report. No example and no project of the output-hash baseline is such a project.
- **The files of the five examples of *Start*** are as in 5.0.0, apart from the version stamp.

**The scripting interface** (`harness_design_studio.api`): `API_VERSION` stays 1; `list_templates()` gives each `TemplateInfo` the field `group`, a field added (the API snapshot `tests/fixtures/api_snapshot.json` was made again on purpose). **The extensions:** `PLUGIN_API_VERSION` and `format_version` of the extension data files stay 1.

### Sizes

The fourteen feature examples are 414 files with 1,185,362 bytes in the package's folder of examples (1.19 MB, most of it JSON), and the import template `device-pinout-EXAMPLE.csv` 1,444 bytes; the folder of examples grows from 178 files and 1.57 MB to 593 files and 2.75 MB. Packed with zip compression, as in the wheel, the folder grows from about 45 kB to about 156 kB. The design had estimated about 0.9 MB in about 400 files.

### What is not in it

- **No format change and no new key.** Format 5 stays frozen; every field an example uses exists in format 5.
- **No new command, option, design rule or part of the starter library.** The EXAMPLE parts are in the examples' own libraries only.
- **No example shows** the standard profiles, *Join into one harness*, `compare`, `merge-fix`, `migrate` (no example can be in an older format), a trusted plug-in or an open error; the page *Examples* says why.
- **The five examples of *Start* do not change.**

### Known limits

- **The nineteen entries were not looked at on a real display**, neither in the window *New project* nor on Home; they were tested offscreen, at the default scale. The screen reader was not tried on the headings. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **The examples are for learning.** Their numbers and parts are EXAMPLE data, not engineering data; `drc` names the unapproved `EX-` parts and the placeholder configuration on every example. Do not copy a number from an example into a real design.
- **More to keep up to date.** A change of an output or a rule now meets fourteen more projects in the tests.
- **The known limits of 5.0.0 stand.**
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
