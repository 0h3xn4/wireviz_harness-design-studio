This is **version 4.1.0**, a minor release of 4.0.1, and it is about the paper a harness is built from. The build workbook and the harness plan get a sheet **Production**: for every connector of a harness, which wire goes from which pin to where, with its part, colour, gauge, length, the label printed at that end and its shield groups. Every length in those two files now says what it is measured from: the rear of one connector to the rear of the other. The plan's harness sheet prints over several pages at a readable scale instead of being squeezed onto one, and a new label format, `harness_device_connector`, labels a cable connector by harness, device and device connector name (`W001:MTQ1:J01`). **A project you start with 4.1.0 is in that format.** **There is no format change:** 4.1.0 writes format 4 as 4.0.1 does, and format 4 stays frozen. But a 4.0.x tool refuses a project in the new label format, so read *Update the whole team at the same time* below before anyone starts a new project. If you come from 3.x, read the notes of 4.0.0 first: each project is upgraded once to format 4. The guides are *Export the outputs*, *Export the harness plans* and *Naming and title block* in the user manual (`docs/user-manual/export-the-outputs.md`, `docs/user-manual/export-the-harness-plans.md`, `docs/user-manual/naming-and-title-block.md`).

The work answers the feedback of an electrical engineer from November 2026 ([the plan](../ait/ELEC_FEEDBACK_PLAN.md), milestone E1; [the design](../ait/DESIGN_4.1_PRODUCTION_SHEET.md)). The top request was production-ready output: which pin goes to which pin, with which wire, which length and which label, clear at a glance on paper.

### From 4.0.x to 4.1.0

- **Install over 4.0.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Update the whole team at the same time, before anyone starts a new project with 4.1.0.** A new project names the label format `harness_device_connector` in `config/model.json`, and 4.0.x does not know that value. With 4.0.1, `validate` and `generate` report `config_invalid` (*label_format must be one of standard, compact, descriptive, custom*) and Generate does not save; `export` writes the outputs with the standard labels and says nothing about it. A connector template with the new field `{mates_name}` is refused the same way. So a colleague still on 4.0.x cannot work on a project that someone started with 4.1.0. Projects that existed before are not affected.
- **Your projects keep their labels.** A project that names no label format is read as `standard`, as before. That is every project made before 4.1.0, and every project made from the `flatsat`, `minimal-satellite`, `small-satellite` or `first-steps` template. To use the new format in such a project, set it on purpose: `harness-design-studio settings DIR --set model.label_format=harness_device_connector`.
- **Export once.** Every build workbook changes (below), and so does every harness plan. `verify --outputs` compares the files in `outputs/` with the version that runs, so outputs written by 4.0.x fail it until you export them with 4.1.0.

### The Production sheet

- **What it is.** One block per connector of the harness, in natural ID order (`W001-P2` before `W001-P10`), the splices last. Each block starts with a heading row: the connector, its part and gender, what it plugs into (`mates MTQ1-J01 (MTQ1:J01)`: the device connector's ID, then its device and name), and its label. Then one row per pin and wire: the pin, the signal, the wire, where it goes (the far connector and pin, and in brackets what that connector plugs into), the wire part, the colour, the gauge, the length, where the length comes from, the label printed at this end, and the shield groups of the wire with their end here and at the far end (`W002-S12 shielded pair: here backshell 360, far floating`).
- **Both ends.** Every connector has a block, the far ones too, so every wire appears twice: once at each end, each time with the label that goes on that end. A builder terminating a connector finds everything on one block.
- **Easier to scan.** A run of spare pins is one row (`3 to 9`, `(spare)`), so the eye goes to the wires; on harness `W002` of `flatsat` the sheet has 74 rows, where one row per pin would have taken 484. A pin with a signal and no wire stays a row of its own, marked `(no wire)`, because a checker needs to see it. A pin with two wires has a row for each.
- **Nothing invented.** A value the design does not hold reads `to fill in` on an amber cell, as on the other sheets. A loose end reads *open end, to fill in*. A label accessory on a connector puts its position into the block heading (`label at 50 mm from the P1 end`).
- **In the build workbook** it comes after *Cut list* (and *Routing*) and before *Connectors*, with a tick column **Done (x)**, and *Start here* lists it. It prints like the other sheets: A4 landscape, one page wide, the headings on every page, a new page before a block that would pass 42 rows. *Connectors* stays the sheet for contacts, tools and the three ticks per pin.
- **In the harness plan** it comes after the harness sheet, with the lengths in mm and plain values only. While the plan colours the ends by pin code it has a column *Pigtail colour* as well.
- **Which end is end A.** A shield group names no connector, so the sheet places its ends by the rule the drawings have always used: end A is where the group's wire with the lowest ID starts. That rule is now written down in [shield groups and shield ends](../models/shields.md).

### Every length says what it is measured from

The headings now read **Length (m), rear to rear** on the *Cut list* and *Production* sheets of the build workbook, **Length (m), rear or branch centre** on *Routing*, and **Length [mm] rear to rear** in the plan. A short text says the rest in words taken from your project's settings; on `flatsat` it reads *Lengths run from the rear of a connector, where the wires leave its body or backshell. They follow the routing segments through the centre of each branch point to the rear of the other connector. A wire Generate made adds 2 service loops of 0.1 m.* The build workbook has it in a row **Lengths** on *Start here* and under *Cut list*, *Routing* and *Production*; the plan has it in `H9` of the harness sheet and in row 2 of *Production*. The column **Length from** says for each wire whether the length is *on the wire*, *locked*, or *segments only, no service loops*: a wire with no length of its own is measured from the segments alone, without loops. See [wire length](../models/wire-length.md#what-the-written-files-say).

### The harness plan prints over several pages

Until now the harness sheet was fitted to one A4 page, which for a harness with many far connectors meant text too small to read: W001 of `flatsat` printed at about 22 %. Now it prints at a fixed scale, the largest whole percent at which the sheet is one page wide (61 % for that harness), over as many pages as it needs. Rows 6 to 9, with the header line, the title and the length note, are repeated at the top of every page, and a connector block that would not fit in what is left of a page starts on the next one. *Production* prints at 100 % with its own headings on every page. The other sheets keep their one page. `verify --outputs` checks the print set-up of both sheets.

### A label format by device connector name

- **The texts.** In `harness_device_connector` a cable connector's label is the harness, the device and the name the device gives its connector: `W001:MTQ1:J01`. A loose end reads `W009:W009-P2 open end`; a connector that plugs into nothing reads `W001:W001-P3`. A wire keeps the standard text (`W001-017 PWR to W001-P10.1`). The label a person gave a connector is not part of this format, so the bench can rely on its form; to print both, choose `custom` with the template `{name} {harness}:{device}:{mates_name}`, where the new field `{mates_name}` is the device connector's name.
- **Where it shows.** `labels.csv`, the *Labels* sheets, the headings of the Production sheet and, in the harness plan, the cell `B4` (*Connector Name*) of each `CON_…` sheet and the header of a near block (`[W001:MTQ1:J01]`, a formula over `B4`). In every other format the plan is as before.
- **Two plugs on one device connector** (a harness drawn by hand) read the same in this format, as they can with a custom template, so Generate warns `label_not_unique` for both.
- `explain DIR W001-P1` names the device and the device connector name, and when the connector has a label of its own it says that this label is not printed.

### Every shield group of a wire

A wire of a twisted pair inside an overall shield is in two groups, but the *Shield group* column of `wirelist.csv`, of the *Wire list* sheet of `<ID>.xlsx` and of the build workbook's *Cut list* showed only one of them. The export's own check used the same rule, so it could not see the loss. Now the column lists every group in natural ID order, joined by `;` (`W002-S2;W002-S3`). A wire in one group keeps its one ID.

### Which written files change

- **Every build workbook** (`<ID>_build.xlsx`) of every project: the new sheet *Production*, the line and the *Lengths* row on *Start here*, the headings of *Cut list* and *Routing*, and the length sentences under them.
- **Every harness plan** (`<ID>_plan.ods`, only with `export --harness-plan`): the new sheet *Production*, `H9`, the length headings and the print set-up of the harness sheet.
- **`wirelist.csv`, the *Wire list* of `<ID>.xlsx` and the *Cut list*** of a harness with a wire in two shield groups (W002 and W004 of `flatsat`, and harnesses of `small-satellite`): the shield-group column.
- **Labels** change only in a project that names the new format: a new project, or one you switch on purpose.
- Nothing else. The other CSV files, `system/export.json`, the drawings, `manifest.json` and the project files are as 4.0.1 writes them, apart from the version stamp.

### Known limits

- **Nobody has printed the sheets at a bench.** The scale, the rows per page and the page breaks are worked out from the column widths and an estimate of the row heights; a long label or shield text wraps in its cell and can make a block taller than the estimate, so a program may break a page elsewhere. Where LibreOffice is installed the tests convert a plan to PDF and read it back; Excel's import of the page breaks of an `.ods` was not tried. The column order of the Production sheet, the folding of spare pins and the word *to* in `3 to 9` have not yet been tried by a builder.
- **What the sheet cannot say yet.** A length reference per connector end (face or rear), a connector depth, the pin a shield pigtail lands on and the backshell a shield end uses need new fields, so a new format; they are planned for a later major release (milestone E5 of the plan).
- **No look at a real display.** No screen of the editor changed in this release. Nobody has looked at its screens on a real display; they were tested offscreen. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
