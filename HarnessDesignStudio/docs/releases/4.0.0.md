This is **version 4.0.0**, a major release. It brings **format 4**, a new version of the project file format, and with it the **row layout of a connector**: a connector part, or a device connector where it differs from its part, can hold the rows of pins on its face, for example a 21-pin Micro-D with the rows 1–11 and 12–21. The pinouts and the harness plan then show the row of each pin, three checks compare the rows with the pins, and the check of power and return pins counts the neighbours on the face. **Format 4 is frozen with this release:** it does not change any more, and a later change of the file format would be a new format with its own upgrade. **Upgrade each project once** (`migrate`, or the editor's question): the step writes the number 4 and nothing else, and after it versions 3.x open the project read-only, so update the whole team at the same time. 4.0.0 also drops the older names that 3.0.x kept for scripts (`revision` beside `version`), and `system/export.json` has `format_version` 2. **One change breaks extensions:** the expression field `harness.revision` is removed, so a rule or a table that names it is refused; use `harness.version`. If a script reads the written files or the output of the commands, read *For scripts* below: every new key, column and command and every dropped name is listed there. The guides are *Pin rows of a connector* and *Upgrade a project* in the user manual (`docs/user-manual/pin-rows-of-a-connector.md`, `docs/user-manual/upgrade-a-project.md`).

### From 3.x to 4.0.0: upgrade each project once

- **Install over 3.x.** Install the `.deb` or the Windows setup program the same way as before. Unpack the `.tar.gz` into a new folder and run `./install.sh` there, or unpack the `.zip` into a new folder.
- **Nothing is upgraded without you.** A project saved by 3.x is in format 3. This version reads it, but saves it only after you upgrade it. Commands that save refuse a format 3 project and write nothing; `validate`, `check`, `drc` and `export` still read it.
- **How to upgrade.** In the editor, open the project and answer the question with **Upgrade**. On the command line, look first with `harness-design-studio migrate DIR --dry-run` (it writes nothing; it lists `project.json`, and `journal.jsonl` when the project keeps a change journal), then run `harness-design-studio migrate DIR`. The backup is the folder `.migration-backup-v3/` with the record `MIGRATION.json`.
- **What changes.** The number in `project.json`, and nothing else: nobody has a row layout before format 4, and the new key is left out of the files while it is unset. The model hash, the findings, the baselines and the released harnesses stay as they are; the upgrade checks them, and a full export, before it keeps the files.
- **Export once after the upgrade.** The design does not change, but `system/export.json` of 4.0.0 has `format_version` 2 and no key `revision` (see *For scripts*), so `verify --outputs` fails on the outputs of 3.x (`out_json`) until you export them with 4.0.0. A project without a row layout writes every other file as 3.x wrote it, apart from the stamp and one more sentence in the advice of the rule `power-return-adjacent`, where it has such findings.
- **Older versions and Git branches.** After the upgrade, versions 3.x (3.0.0 to 3.1.0) open the project read-only (*saved by a newer version of the tool*) and change nothing: `generate` and `export` refuse it (*this project is read-only*), while `validate`, `check` and `drc` still read it. Once a part or a connector has rows, 3.x also sets it aside as a damaged file (*row_layout: Extra inputs are not permitted*), and the connectors of such a part lose their part: `validate` lists errors, and `generate`, `export` and `drc` refuse the project (*the project has damaged files*) and write nothing. A device library file or a subsystem file that holds rows has a newer file version, which 3.x does not read. Upgrade on the main branch first, then bring the other branches up to date before they merge; the files of a format 3 branch are valid in format 4, so a merge needs no rewrite.
- **From 2.x or older**, the upgrade goes through every step in one go (from format 2 with the mapping of the revision letters, and `--set-version` where it needs it); read the notes of 3.0.0 first.

### The main changes

- **The row layout of a connector.** The rows of a connector part are shared by every connector of that part; a device connector may have rows of its own; a connector of a harness takes those of its part, else those of the device connector it plugs into. In the editor, the line over the pin table of the **Devices** tab says *Rows: 1–11 / 12–21, from part …* with **Edit rows…**: one row per line, or the **Row lengths** `11, 10` with **Fill**, and **Rings of a circular insert**; **Use for every connector of this part**, **Back to the part's rows** and **Clear**. The pin table has a column **Pin row**, the Inspector of a part edits its rows, and the Inspector of a connector of a harness shows the rows it takes. Each change is one undo step and goes into the change journal; a release does not lock the rows.
- **The command line.** `pin-rows DIR --part ID | --connector ID` shows the rows and where they come from, and sets them: `--set "1–11 / 12–21"`, `--lengths 11,10`, `--clear`, `--rings`/`--no-rings`, `--to-part`. `import-pinout` reads a *Pin row* column into a connector's own rows and says when they could go on the part; `export-pinout` writes it, so its file reads back as no change. The device library commands and the subsystem file carry the rows. `explain` of a connector names its rows.
- **The checks.** `check` and `validate` warn when the rows of a part name a pin a connector lacks (`row_layout_pin_missing`) and when two mating connectors or parts hold other pins in a row (`row_layout_mate_differs`), and note pins in no row (`row_layout_pins_outside`). None of them is an error.
- **Power and return pins on the face.** The rule `power-return-adjacent` reads the face of a connector with rows: along a row it counts the free contacts between two pins, and two pins of rows next to each other are neighbours when their places differ by one place or less, the rows taken as centred on each other (*PCDU1-J01: PWR (pin 1) and RTN (pin 6) are neighbours on the face of the connector (rows 1 and 2), with no unassigned contact between them*). Pins of different rings are not judged, and `unchecked-config` says so. **A project without rows gives the same findings as before.** Generate does not read the rows (owner answer L2): on a connector with rows the rule can warn about the pins Generate chose; move one pin or lock the pins.
- **The written files.** Where a connector has rows, `system/box_pinouts.csv` and the pinouts of its harness get a last column *Pin row*; in the harness plan, the `CON_…` sheet of such a device connector has *Pin row* in column F, and its near block lists the pins row by row with *Pin row* in column A. `verify --outputs` reads the rows again on its own. **A project without rows writes the files it wrote**, apart from the version stamp, `system/export.json` (below) and one more sentence in the advice of `power-return-adjacent`.
- **One breaking change for extensions.** The expression field `harness.revision`, which 3.0.0 kept as the older name of `harness.version` through 3.0.x, is removed. A rule or a table of an extension that names it is refused with *unknown field 'harness.revision' (did you mean harness.version?)*. Write `harness.version` in its place: it holds the same value. Nothing else of the extensions changes (`PLUGIN_API_VERSION` and `format_version` of their data files stay 1).
- **The older names for scripts are gone.** Each harness of `system/export.json` has `version` and no longer `revision` (its `format_version` is 2), and each entry of `log --json` has `version` and no longer `revision`. A script reads `version`, which holds the same value. `revise` stays as the older name of `new-version`.
- **No rows are shipped.** The starter parts and the example projects have no row layout (owner answer L3): enter the rows of your parts from their datasheets.

### For scripts

Every place where a script can meet a change, from sections 6, 7, 10 and 11 of the design (`docs/ait/DESIGN_4.0_ROW_LAYOUT.md`). The new keys and columns are sparse: they appear only in a project in which a part or a connector has rows. The dropped names of 3.0.x are gone in every project.

**Written files**

| File | 3.x | 4.0.0 |
| --- | --- | --- |
| `system/export.json` | `"format_version": 1`; each harness with `"version"` and `"revision"` beside it, the same value | `"format_version": 2`; each harness with `"version"` only. New: `"row_layout": {"rows": [["1", …], …]}` (and `"rings": true`) on a part of `parts` and a connector of `box_connectors` that has rows |
| `system/box_pinouts.csv` | the columns of 3.0.0 | a last column `Pin row` (the row of the pin, from 1; empty for a pin in no row) while some device connector of the project has rows |
| `harnesses/<ID>/pinouts.csv`, the *Pinouts* sheet of `<ID>.xlsx` | the columns of 3.0.0 | a last column `Pin row` while a connector of that harness has rows |
| harness plan `<ID>_plan.ods`, `CON_…` sheet | the pin table in columns A to E from row 18 | for a device connector with rows, column F *Pin row* (heading in row 18) |
| harness plan `<ID>_plan.ods`, the harness sheet | a near block in pin order; column A empty | for a device connector with rows, the pins row by row in the order of the layout, then the pins in no row; column A *Pin row*, a formula `=[$'CON_…'.F19]` with its value |
| `system/drc_findings.csv`, `system/drc_report.md` | `power-return-adjacent` judges the list of pins | on a connector with rows, the face: new texts (*are neighbours on the face of the connector (rows 1 and 2)*, *along row 1 of the face*); the finding IDs stay. The fix of every finding of the rule has the second sentence *On a connector with a row layout, a neighbour in the next row counts too; move one pin or lock the pins (Generate does not read the rows).* `unchecked-config` gets one finding per connector with power and return pins in different rings (object `power-return-rings`) |

**Project files (format 4)**

| File | 3.x | 4.0.0 |
| --- | --- | --- |
| `project.json` | `"schema_version": 3` | `"schema_version": 4` |
| `library/connector.json` | — | `row_layout` on a part of category `connector`, while it has rows |
| `physical/connectors/*.json` | — | `row_layout` on a device connector (one with `unit_id`) with rows of its own; never on a connector of a harness |
| device library file (`harness-device-library`, `NAME.device.json`) | version 1 or 2 | version 3 when a part or a device connector in it has rows; else as before |
| subsystem file (`harness-subsystem-library`) | version 1 | version 2 when a part or a device connector in it has rows; else 1 |
| `journal.jsonl` | — | the step's entry *migrated from format 3* |

The schemas of `schema FOLDER` and `docs/FILE_FORMAT.md` follow. A layout that breaks a rule (an empty row, a pin twice, more than 64 rows or 1000 names, more names than the part has pins, a layout on a part that is not a connector or on a connector of a harness, a name that is not a pin of the connector) sets the part or the connector aside with the reason.

**The command line**

| Place | 3.x | 4.0.0 |
| --- | --- | --- |
| `pin-rows` | — | new: `pin-rows DIR (--part ID \| --connector ID) [--set TEXT \| --lengths N,N… \| --clear] [--rings \| --no-rings] [--to-part] [--json]`; `--json` prints `ok`, `changed`, `object`, `kind` (`part`, `connector`), `rows`, `rings`, `source` (`own`, `part`, `mated`, `none`), `source_id`, `text` |
| `import-pinout` | — | reads the column *Pin row* (also *Row*, *Contact row*); `--json` adds `row_layouts` (the connectors given rows of their own), before `import`; the import record has the lines *Row layouts set: …* in its `notes` |
| `export-pinout` | the columns of `box_pinouts.csv` for the device, then Level and the source columns | `Pin row` before Level and the source columns while a connector of the device has rows |
| `check`, `validate` (and `--json` `issues`) | — | the codes `row_layout_pin_missing` (warning), `row_layout_pins_outside` (info), `row_layout_mate_differs` (warning); the two warnings are also findings of `model-inconsistent` in `drc` |
| `explain CONNECTOR` | — | an input *Pin rows* with its source, while the connector has rows |
| `settings` | the assumptions A-RETURN-GAP and A-PIN-ORDER on the list of pins | A-RETURN-GAP names the neighbours on the face (rows centred on each other); A-PIN-ORDER is Generate's order, which does not read the rows |
| `log --json` | each entry with `version` and `revision` beside it | `version` only |
| `update-device` | — | lists `row_layout` of a device connector as a field of its diff, in the short form |
| `migrate` | — | the step from format 3 to format 4; no new option |
| the expression field of the extensions | `harness.version`, and `harness.revision` as its older name | `harness.version` only; a rule or table that names `harness.revision` is refused with *unknown field 'harness.revision' (did you mean harness.version?)* |

**The scripting interface** (`harness_design_studio.api`): `API_VERSION` stays 1; it only adds. `row_layout_of(source, connector_id)` gives a `RowLayoutRecord` (`object`, `kind`, `rows`, `rings`, `source`, `source_id`, `text`); `set_row_layout(folder, *, part=None, connector=None, rows, rings=False, author=None)` (rows as lists of pin names or in the short form) and `clear_row_layout(...)` save through the same plans as the editor; the models it returns have `Part.row_layout` and `Connector.row_layout` (`RowLayout` with `rows` and `rings`).

**The extensions:** `PLUGIN_API_VERSION` and `format_version` of the extension data files stay 1. Removing `harness.revision` is the one exception to the rule that a field is not removed without a new `format_version` (`docs/developer/extensions.md`): 3.0.0 announced it for 3.0.x only.

**What stays:** `revise` as the older name of `new-version`; `diff --from A` reading an old letter; `revision_not_version` with `merge-fix`; the step from format 2; `--unit`; the aliases `harness` and `harness-gui`.

### Known limits

- **No look at a real display.** The new screens (the line *Rows* and **Edit rows…** of the Devices tab, the window **Pin rows of …**, the column **Pin row**, the Inspector's **Pin rows**, the rows of the Problems list) were tested offscreen only. The Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **The row layout.** No datasheet was read: the rows in the documents are examples of the form. The rule takes the rows as centred on each other, so a face whose rows are offset otherwise is judged with the pin across and both diagonal pins, which can warn where the real face does not; pins of different rings are not judged. No face is drawn, Generate does not place pins by the face (a later minor release can, without a format change), and the far side of the harness plan keeps its columns.
- **3.x and a project with rows.** 3.x opens a format 4 project read-only; a part or a connector with rows is set aside there as a damaged file, so `generate`, `export` and `drc` of 3.x refuse such a project. This was tried with the code of 3.0.0 and of 3.1.0.
- **No compliance and no sign-off is claimed.** The configuration values and the parts are placeholders and example parts until your project supplies its own.
