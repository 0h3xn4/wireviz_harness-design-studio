## Library layout (D-175, since 1.8.0)
`core/subsystem_library.py` (no Qt): a subsystem is a set of devices with the links between them in one file `harness-subsystem-library` (version 1; schema in `docs/FILE_FORMAT.md`); `export_subsystem`, `read_subsystem`/`write_subsystem`, `plan_subsystem_import` (devices through `device_library.plan_device_import`, so a taken ID is renamed and nothing is overwritten; `Unit.subsystem` set to the name; connections through `links.plan_add_link` on the new connectors via `DeviceRow.connector_ids`; all or nothing; one undo step; `with_placements` puts them in one lane). `core/library_folder.py`: the library folder (`scan_folder` never raises and reads only; `load_entry`, `describe_entry`; `save_devices`, `save_subsystem` are the only writers and never replace a subsystem file). `core/copies.py`: a number of the same device (`plan_copies`, `device_count`, `copy_ids`: `ID`, `ID-R`, `ID-3` ...; built on `edit.ops_redundant_copy(suffix=...)`; nothing stored). Screens: `gui/library_window.py` (`LibraryWindow`, non-modal top-level window over the shared controller, `SaveToLibraryDialog`; reads the folder with `JobRunner`; own size and place under `library/`), `MainWindow.library_folder`/`set_library_folder`/`open_library_flow`/`choose_library_folder_flow` (File > Library…, Ctrl+Shift+O; Ctrl+Shift+L is Arrange; File > Library folder…; the setting `library/folder` is per person), the Settings > Project row, the Home page button, `ctl.add_device(count=)` and `ctl.make_copies`, the number field of the Add device window and the Devices tab. **Rules:** the tool stays offline (a shared library is a shared folder, never network code or `subprocess`); nothing is written into the folder except by *Save*; the model got no field, so files and outputs of a project that does not use the library stay byte-identical (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_BASELINE.json`); the blank example holds no subsystem (`tests/test_subsystem_library.py`). User page: `docs/user-manual/use-the-library.md`; pictures `docs/img/library-window.png`, `library-save-window.png` (`tools/tab_screenshots.py`, `_library_pictures`). Tests: `tests/test_subsystem_library.py`, `test_subsystem_cli.py`, `test_ui_library_window.py`.

## Waivers and pair parts (release 1.11, D-187, D-188)
- A waiver is tied to the finding it was made for. `Waiver.finding_hash` (`core/model/review.py`, sparse, 12 hex characters) is set by `checks.waive_op` from `checks.finding_hash(finding)`: a hash of the rule and the finding's `title`, not of `why`. `checks.with_waiver` applies a waiver only while it has no hash or the hash still matches; otherwise the finding stays open with `waiver_changed` set, `drc.report` lists it under *Waivers that no longer fit* (`changed_waivers`), and the Problems card and the Checks panel say so (`panels.py`, `checks_panel.py`, `strings.CHECKS_WAIVER_CHANGED`). A waiver without a hash (an older file) still applies. `tests/test_waiver_finding_hash.py`, `tests/test_gui_drc.py`.
- `Part.conductors` (`core/model/library.py`, whole number 1 to 64, default 1, left out of the files while 1) says how many conductors one metre of a wire part carries (2 for a twisted pair). Each wire that names the part is one conductor of it, so the BOM (`outputs/tables.bom`) adds `length / conductors` per wire and the mass (`generate/mass.py`) `mass_per_m_g * length / conductors`; the wire list and the cut list stay one row per wire. The independent output check counts the same way from the project (`outputs/verify.py`: `_bom_rows`, `_mass`). The tool never guesses it for a project's own parts; the parts import reads a *Conductors* column (`library_import.py`). `tests/test_pair_part_counts.py`.

## Derivations (D-191, transparency work step 1)
`core/derive.py` (no Qt) says how a number was made: `Derivation` (quantity, value, unit, equation, `Input`s with unit and source, `Step`s, a `Check` of actual against limit, assumption IDs, reference, what is missing), `wire_current_limit_derivation`, `wire_voltage_drop_derivation`, `explain_wire` and `render`. It computes no result of its own: every value comes from `sizing.wire_current_limit`, `sizing.voltage_drop_v` and `lengths.wire_length`, the functions the generator and the rules call, so it cannot disagree with them; the steps are for the reader. `core/assumptions.py` lists the choices built into the program (`A-ROUND-TRIP`, `A-DC-SOLID`, `A-BUNDLE-ALL`, `A-TEMP-FACTOR`, `A-AMPACITY-AWG`) with an ID a derivation can cite; it is the seed of the registry of constants. `cli/explain.py` is the command (`explain DIR WIRE [--json]`). Since 4.3.0 (design of 4.3.0, section 7) an ID that names no object (`explain_object` raises `NotAnObjectError`, whose text is `not_an_object`) is looked up among the findings `drc` prints and explained by `explain_finding`, so `explain DIR FINDING` shows what the editor's *Explain* shows; an ID that is neither says *or a finding of this project* (`tests/test_explain_finding.py`). A new derivation is added with a test in `tests/test_derivations.py` that compares it with the number of the function it explains, and a page in `docs/models/`. S1 of the transparency work (D-191, D-193) added `core/derive_build.py` (readiness and its eight checks, the test limits, labels, colours, shield groups), `core/derive_layout.py` (pin allocation, segmentation, the choice of a connector), `core/derive_rules.py` (the limit or the comparison of every design rule: `INFO` has one entry for each rule, `explain_rule`) and `core/derive_kinds.py` (every kind of derivation with its page); the generator and the build workbook were split so that they call the same functions (`buildsheet.open_items`, `tables.wire_label_texts`, `wirecolours.signal_colour`, `generate/shields.py`, `drc/rules.wires_on_pins`, `standard_rules.emc_class_bundles`). `explain_wire` and `explain_harness` keep giving the numbers; `explain_wire_all`, `explain_harness_all` and `explain_object` give everything. `core/derive_routing.py` (2.3.0, D-243) gives the routing tree of a harness (`routing_tree`, the command `routing DIR HARNESS`), the derivations `segment` and `branch-point` (on demand, `derive_kinds.ON_DEMAND`, so `derivations.json` is unchanged) and `length_source` (no field holds where a segment length came from: an import record of kind `lengths` with the same value means imported, else entered; kept by Generate on a generated harness); the wires per segment and the sides of a branch point are PR 4's rows (`outputs.tables.segment_wires`, `branch_sides`). A `Derivation` whose result is a text has `text`; `Derivation.known` says whether there is a result. A test (`tests/test_s1_rules.py`) walks every rule of the registry and fails for one without an explanation, and `tests/test_s1_build_layout.py` ties every kind to a page.

## Import records and units on import (D-191, D-193, transparency work step 6)
- `core/model/imports.py` is the entity (`ImportRecord`, sparse: optional fields are left out while empty), `Project.import_records` the dict (key `<kind>:<file name>`), the collection `import_records` of `Put`/`Delete`, the file `imports/records.json` (`io/layout.IMPORT_RECORDS_FILE`, folder `imports` in `MANAGED_DIRS`). It is **not in `model_hash`** (`layout.model_hash` skips the file) and in no output file; it is carried by save, load, the autosave journal and undo. The schema version stays 1.
- `core/import_record.py` has `ImportReport` (what an importer found out: rows, columns read and left out, dropped rows, `Conversion`s, unit given or assumed; `.lines()` is the echo, `.record()` the entity, capped at 200 listed rows), `record_ops` (one `Put`, none when the project holds the record already, so an identical re-import changes nothing), `check_sources` (`unchanged`, `changed`, `missing`, `unchecked`; a recorded path cannot leave the project folder) and `CachedHasher` (the editor asks on every refresh). **No clock, no user name, no absolute path ever goes into a record** (`project_relative`, `clean`); a test compares two projects' bytes.
- `core/import_reports.py` has one report builder per importer; `cli/data.py` and `gui/import_kinds.py` both use it, so the command line and the wizard say the same. A new importer needs a kind in `core/model/imports.py` (`ImportKind`, `IMPORT_KINDS`, `KIND_WORDS`), a builder there, a record op appended to its undo step (`[*plan.ops, *record_ops(project, record)]`) and a line in `docs/IMPORTS.md`.
- Units: `generate/lengths.LENGTH_UNITS_M` (mm, cm, m, in, ft), `library_import.MASS_UNITS_G` (g, kg, lb, oz). The default is the unit the column was always read in (mm, g); a plan with the default scale takes the same code path as before (`mass_scale` 1.0 multiplies nothing).
- The tool's own CSV (`imports.STAMP_LINE`, `parse_csv_file`): the stamp line is skipped and the apostrophe of `outputs/stamp._safe` is taken away; any other file is read as it is.
- Part ratings: `library_import.rating_columns` (a heading that names a rating key; the fields of the wizard's mapping page are unchanged). KiCad: `NetlistPlan.pin_types`, `PIN_TYPE_DIRECTION`, `use_pin_type_direction` (off by default).

## Scripting interface (R11, transparency work step 7)
`api.py` (no Qt, no printing, no `sys.exit`) is the stable way to drive the tool from Python: `load_project`, `create_project`, `validate`, `run_checks`, `verify`, `generate`, `export(out=)`, `explain`, `explain_all`, `explain_finding`, `write_derivations`, `get_config`, `set_config`, `list_rules`, `list_templates`, `save_project`. It calls the functions the commands call and adds no behaviour; the result types and the code that builds them from the tool's objects are in `core/records.py` (frozen dataclasses with `to_dict()`), and the command line prints `to_dict()` of the same objects with `--json` (`cli/jsonout.py`: `Report`, `SHAPES`; the keys of every document are in `docs/CLI.md`, made from `SHAPES`). `core/validation.py` is what `validate` and `check` look at, shared by both. **Rules:** a new command that has a result in data form gets `--json` and a `SHAPES` entry (a test fails otherwise); the text of a command without `--json` stays byte for byte (the commands print through `Report.say`); a name added to `api.__all__` needs a docstring and a run of `python -m tools.gen_api_snapshot` (`tests/fixtures/api_snapshot.json`, `API_VERSION`); the examples in `docs/examples/scripting/` import only `api.__all__`. Page for developers: `docs/developer/api-stability.md`; user page: `docs/user-manual/script-the-tool.md`. Tests: `tests/test_api.py`, `test_api_stability.py`, `test_cli_json.py`, `test_scripting_examples.py`.

## Extensions (D-191 (5), transparency work stage S8)
`core/extensions/` (no Qt): `registry.py` (the one list of rules, fields, models, tables, lookup tables and importers, built-in and extension; `builtins.install` registers the tool's own), `expr.py` (the hand-written parser and evaluator of the condition language: no `eval`, `exec`, `compile` or `ast`; a field is a registered name, a function is on a whitelist), `jsonpos.py` (JSON with lines), `schema.py` (the description of the two file formats, also their JSON Schemas), `declarative.py` (`read_file`, `DeclRule`, tables, lookup tables), `fields.py`, `plugins.py` (the only place plug-in code is imported: enabled and trusted and a valid declaration), `trust.py` (the store in the user's settings folder, name + SHA-256), `pluginapi.py`, `manager.py` (`discover`, `runtime`, `run_extension_rules`, `provenance`, `loaded`). Hooks: the loader sets `project.extensions` when the folder exists (None otherwise: every hook tests for that first, so a project without the folder is untouched), `drc.run`/`all_rules`/`by_rule`/`report`, `derive.is_explainable`, `derive_rules.explain_rule`, `outputs.build`/`provenance`, `validation`, `schemas`. Rule IDs of extensions start with `x-`; the 43 stay 43. See `docs/developer/extensions.md`.

## Open data, the run record and mm² beside AWG (S5)
- `core/open_data.py` builds every table of `export-data` from the functions the generator, the rules and the derivations call (`sizing`, `bundle`, `lengths`, `mass`, `tables.bom_contributions`, `derive_rules.explain_rule`), never from a second copy of a formula; a test compares each number with its derivation. Pure and byte-deterministic: no time, user or path (a test scans the files); numbers are written with 12 significant digits (`num`). A new table is a `DataTable` in `all_tables`; add a test row in `tests/test_open_data.py` and, if an importer can read it, a line in `docs/IMPORTS.md`.
- `docs/examples/open-data/reproduce.py` is the self-check: it imports only `csv`, `json`, `math`, `sys` and `pathlib` (a test reads its imports) and recomputes from the files. If a model of `docs/models/` changes, the script changes with it.
- `core/run_record.py` is the only place that reads the clock or the operator. The record is written only when asked, next to the outputs (`outputs/run_record.json`, exempt in `core/outputs/verify.py`), and is in no hash and no manifest. Do not put a time or a name in any other file.
- The cross-section is for people: `units.format_gauge`, `gauge_short`, `with_area` on the screen, in `core/derive.render` and in the Assumptions text; never in a file the project hashes or the outputs write (`tests/test_numbers_snapshot.py`, `tests/test_output_hashes.py`, `tests/test_gauge_area.py`). In data it is the number `area_mm2`.

## The workflow and the as-built records (S9)
- `core/workflow.py` is the one table of the nine steps (what each uses and makes, the intermediates, the command, the screen) and `workflow_status` (the state of each from the project, with the steps that block it). The page `docs/user-manual/follow-the-workflow.md` holds two tables made from it (`python -m tools.gen_workflow_doc`); `tests/test_s9_workflow.py` fails when the page differs and when a step names a project file (`io.layout.is_managed`), a configuration file, an output file of the real output set, an `export-data` table or a command that the tool does not have. A new step, file or output is added there and nowhere else.
- `core/model/asbuilt.py` is the entity (`AsBuiltRecord`, sparse), `Project.asbuilt` the dictionary, `asbuilt/records.json` the file (`io/layout.py`, `io/loader.py`, `schemas.py`); like `imports/records.json` it is left out of `model_hash`, `journal.files_hash` and every written output except the as-built report and the *As-built* sheet. `core/asbuilt.py` has the template (`template_rows`, `template_bytes`), the import (`plan_asbuilt_import`, `read_import`: units from the headings, an empty cell never clears, a refused row refuses the whole import) and the report (`asbuilt_report`, the statuses `RECORDED`, `MISSING`, `WITHIN`, `OUT`, `NOT_COMPARED`, `DIFFERS`, `STALE`). The limits are `tables.limit_value` (the Tests sheet's), the designed length is `wire_length`; no tolerance. **The module never says that anything passed**; a test reads the report for the word.
- The written outputs (`system/asbuilt_report.md` and `.csv`, the *As-built* sheet, `asbuilt_hash` in the manifest) exist only for a project that has records, so a project without them writes every file as before (`tools.output_hashes --check` and `tools.numbers_snapshot --check`); `core/outputs/verify.py` accepts them only then. The derivation kind `asbuilt-result` is `core/derive_asbuilt.py` (page `docs/models/asbuilt.md`). `journal.rows_for_save` makes the entries of kind `asbuilt`.
