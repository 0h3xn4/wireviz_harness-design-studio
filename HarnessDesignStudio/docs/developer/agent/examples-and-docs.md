# Examples, templates, documentation and the compliance set: notes for agents

These sections were moved word for word from [`CLAUDE.md`](../../../CLAUDE.md) on 2026-10-29 (decision D-182); only this introduction is new. Read them when you change an example project, a template, a document that a test reads, or the compliance files.

## Examples, templates and documentation
`core/templates.py` (`create_project`, `copy_import_templates`), `cli/start.py` (`harness-design-studio new`, `harness-design-studio templates`), `resources/examples/` (`projects/` built by `tools/build_examples.py`; `templates/` written by hand: CSV, netlist, CI scripts, review checklist, demo values), `resources.examples_path()` (also inside PyInstaller). Docs for newcomers: `docs/LEARNING_PATH.md`, `GETTING_STARTED.md`, `CONCEPTS.md`, `INSTALL.md`, `CHEATSHEET.md`, `FAQ.md`, `CLI.md`; map in `docs/README.md`. Examples: `blank`, `first-steps`, `minimal-satellite`, `small-satellite`, `flatsat` (generated, with EXAMPLE numbers; walkthrough `docs/FLATSAT_EXAMPLE.md`); the template `design-worksheet.md` is for planning on paper.
- The groups of the examples (5.1.0, `docs/ait/DESIGN_5.1_FEATURE_TEMPLATES.md`, D-268 proposed): `core/templates.py` `TEMPLATES` is the one list (name, title, summary, `group`: `START` or `FEATURE`, `GROUPS`, `in_group`, `template_info`); the help of `new`, `new --list` (a heading per group, `cli/start.GROUP_HEADINGS`, `list_lines`), the New project dialog (a heading row per group), Home (the group *Start* and one line for the feature examples) and `tools/build_examples.py` (titles, and `BUILDERS` in the order of the list) read it. The feature examples are built by `tools/feature_examples.py` (one builder per example, every edit through `History.execute`, an open `drc` error stops the build) and checked by `tests/test_feature_examples.py` (REQ-EX-01: `NAMED` lists the findings beyond the baseline that each example's page names). A new example: a `TemplateInfo` in `TEMPLATES`, a builder, a row in `NAMED`, then `python -m tools.build_examples`. The feature examples so far: `full-connectors`, `splice-by-hand` (a harness drawn by hand with two splices) and `splice-from-connection` (a connection with junctions and pin currents; the EXAMPLE values of `templates/config-demo-values/` through `_demo_values`, EXAMPLE contact ratings); the two splice examples put the unverified, unapproved EXAMPLE part `EX-SPLICE-1` in their own library (`_splice_part`). Then `branching-harness` (segmentation `per_connector_group` set with `_setting`, as `settings --set` does), `loose-cable-end` (`manual_harness.plan_cable_from_port`, `branching.plan_add_leg`), `shields-and-ends` (the grounding concept, the EXAMPLE backshell part `EX-BACKSHELL-MICROD` through `_backshell_part`, `wires.plan_set_shield_place`) and `lengths-to-the-face` (`model.length_reference`, `connector_edit.plan_set_length_to`, `build_data.plan_set_part_depth`); EXAMPLE segment lengths through `_segment_lengths`. Then `released-harness` (the devices of `first-steps` through `_first_steps_devices`, the review checklist and different people, a review, a release with ticks and a new version through `vcs.release` with the fixed dates of `EXAMPLE_DATES`; the release gate reads outputs that `_exported` writes into a scratch folder, and no `outputs/` is shipped) and `overrides-and-deviations` (`wires.plan_override`, `checks.deviate_op`, `checks.waive_op`; `_no_errors` counts only the errors that are not accepted). Then `names-and-ports` (the project's signal map and `naming.far_device_names` through `configcheck`, pinouts in the team's words imported by `_import_pinout`), `build-data-and-as-built` (`build_data`, `devices.ops_set_contacts`, the EXAMPLE contact part `EX-CONTACT-22` through `_contact_part`, `plan_config.plan_example_code`, `document.plan_document_edit`, an as-built sheet read by `asbuilt.read_import`) and `imports-from-files` (every import through the plan and report functions the import commands call, `_recorded` adds the import record; a table a builder makes is written into a scratch folder by `_write_table`, so its record has the same name and SHA-256 each build). The import template `templates/device-pinout-EXAMPLE.csv` is the pinout that `imports-from-files` reads.
- Team use with Git (release 1.9, F-05): `new` writes a `.gitattributes` (`core/mergefix.py` `GITATTRIBUTES`, written once by `templates.create_project` and by `tools/build_examples.py`, shipped as `templates/ci/gitattributes`) that makes Git treat `generated/generation.json` as binary, and `merge-fix DIR` (`cli/merge.py`) keeps one side of that record, runs `generate` and `check`, and refuses when any other file is in conflict. It finds conflicts from markers and from the Git index (`core/vcs/gitindex.py`, read directly: the tool never starts `git`, `tests/test_security.py` forbids `subprocess`). `tests/test_merge_fix.py` makes real merges with `git`. `logical/links.json` (sequential IDs) and the change log still conflict by design (A-23, not fixed: a file-format change).
- A new CLI command needs an entry in `tools/gen_cli_docs.py` (group and examples) and in the user guide; a changed example needs `python -m tools.build_examples`.
- Demo values in the templates are for learning only, never engineering data, and stay `"placeholder": true` (D-129). Do not make the examples look reviewed.
- If you change what the tutorial prints (the example, the sizing, the drawings), update `docs/GETTING_STARTED.md` and `docs/img/` (a test checks the commands and the quoted model hash).

## Compliance audit (ECSS/ESCC)
`compliance/` (assessment, gap analysis, evidence, process documents; the requirement lists and the matrix quote the standards and are made locally only, D-221), `core/standard_profiles.py` (optional value profiles, D-131), `core/drc/standard_rules.py` (rules that apply the supplied standards), `tools/extract_requirements.py`, `tools/build_compliance_matrix.py`, `tools/trace.py`, `tools/metrics.py`, `tools/gen_scf.py`.
- Never add a standard value as a default; profiles fill unset values only and cite a requirement ID that has a row in `compliance/assessment/design_assessment.csv` (a test checks it).
- A new rule that serves a requirement names it in `sources=`; a rule that needs a number stays silent without it and adds a line to `standard_rules.unchecked`.
- Rebuild after changing assessments: `python -m tools.trace` (and, where the standards are at hand, `python -m tools.build_compliance_matrix` locally; its output is not committed), and after adding or moving modules `python -m tools.gen_sdd_components` (every module needs a docstring); the outputs are checked for freshness by tests.
