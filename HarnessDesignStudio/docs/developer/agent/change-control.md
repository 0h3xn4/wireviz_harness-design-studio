# Change control, releases of a harness: notes for agents

These sections were moved word for word from [`CLAUDE.md`](../../../CLAUDE.md) on 2026-10-29 (decision D-182); only this introduction is new. Read them when you work on versions (revisions before 3.0.0), baselines, the release freeze or the review workflow of a harness.

## Change control layout (M6)
`core/vcs/` (`release` plans, `locks` enforced in `History.execute`, `diff`, `snapshot`, `hashing` content hash, `report` change log and version report, `consistency` released-vs-baseline, `versions` the one order of versions `version_key` and, for format 3, `bump`, `letter_to_version`, `kind_between` and the pinout test, D-242), `cli/changes.py`. Format: `docs/FILE_FORMAT.md`; decisions D-102 to D-109.
- Release, new version (and the kind chosen again, `version_changed`) and review are plans of ops run through `History`; never write baselines or the change log directly.
- Anything that may change a released harness must pass `check_locks`; `apply_ops` bypasses it on purpose (generation, loaders, tests), so keep new editing paths on `History`.
- Generation's input hash must not include release bookkeeping (status); the outputs gate uses `content_hash`.
- Add a diffable object kind in `vcs/diff.py` (`_flatten_*`) and its name in `KIND_NAMES`.
- Sort versions only with `vcs/versions.py` `version_key` (or `sort_versions`), never as text: as text, AA comes before Z (design of 3.0.0, section 5.2).
- The review checklist and the release (4.3.0, `docs/ait/DESIGN_4.3_REVIEW_VIEW.md` parts A, B and D; REQ-CC-11). `vcs/release.harness_findings(project, h, findings)` is the one selection of the findings that belong to a harness: its object is one of `related_ids`, or `drc.locate` places it in the harness or on an interface it carries, or places it nowhere and its object is a part the harness uses; the rules of `PROJECT_RULES` (`config-invalid`, `unchecked-config`) are the whole project's. `release_blockers` takes its rule errors from it (the same blockers as before 4.3.0) and the Review sheet and page (`core/review.review_view`) take every severity from it; the verifier has its own copy (`verify_review.about_harness`). `release --ticked POINTS` and the editor's release dialog pass `ticked=` (point numbers, or the text that `review.parse_ticked` reads) to `plan_release` and `release_blockers`: `ticked_blockers` gives `ticked_invalid` and `ticked_no_checklist` (`about="ticked"`), and there is **no gate on the checklist** (R5). `review_note(project, by, ticked)` is added last to the comment, after the notes of placeholders, parts, loose ends, as-built and deviations, so their text and order stay; nothing in a project without a checklist, so the comment of such a release is byte for byte as before. The note is in the change-log entry and the baseline, and from there in `log`, the Releases tab, `system/changelog.csv`, `system/version_report.md` and row 3 of the Review sheet. `naming.review_checklist` is not frozen by a release (`snapshot.FROZEN_CONFIG_FILES`) and not read by generation (`generation_status.NOT_READ_BY_GENERATION`); the list hash (`review.list_hash`) names the list in the note and on the sheet. Tests: `tests/test_review_view.py`, `tests/test_release_ticks.py`, `tests/test_e2e_430.py`.
