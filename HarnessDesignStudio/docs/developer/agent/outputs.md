# Outputs and the build workbook: notes for agents

These sections were moved word for word from [`CLAUDE.md`](../../../CLAUDE.md) on 2026-10-29 (decision D-182); only this introduction is new. Read them when you work on a written file (`core/outputs/`, the independent verifier, the goldens) or on the build data.

## Outputs layout (M5)
`core/outputs/` (`canvas` SVG/PDF writers, `drawing`, `system` diagrams, `tables`, `buildsheet` the build workbook of a harness (D-169: styled write-only openpyxl workbook, no formulas, deterministic; the verifier reads it cell by cell), `exports` YAML/JSON/XLSX, `stamp`, `build` build/write/status, `verify` independent verifier). Format and limits: `docs/OUTPUTS.md`. `build_outputs(project, drawings=True)` has the drawings on by default as a library call; `harness-design-studio export` and the Export window pass `drawings=False` unless `--drawings` or *Include the PDF drawings* is chosen, and `drawings_exported(folder)` tells whether the last export had them (the self-check accepts a set with the drawings of every harness or of none).
- `build_outputs` is pure and deterministic: no dates, sorted rows, uncompressed PDF, XLSX re-zipped with fixed timestamps. Keep it that way; goldens depend on it.
- `core` must not import modules that import network code at import time (`xml.sax.saxutils` does; use `canvas.escape`). The offline test catches this.
- `core/outputs/verify.py` must stay independent of `tables.py`/`drawing.py`: derive expectations from the project.
- Connection list (release 1.9, W2, REQ-OUT-09): `core/outputs/connections.py` builds `system/connections.csv` and `system/connections.xlsx` (styled like the build workbook, deterministic), written by `build_outputs` **only when `project.links` is not empty**, so a project without links keeps byte-identical files. Links are also edges (tagged with the link ID) in `system.block_diagram` and rows (with a `Kind` column, header `Interface or connection`) in `tables.traceability`, again only with links. `verify.py` re-derives every cell of these on its own (`_connections`, `_trace_rows`; the interface cell is checked to be possible, not rebuilt). `export` (CLI and the Export window) needs a harness **or** a link. `tables.py` cannot import `core.links` at module level (import cycle through `core.devices`).
- Signal, interface and requirement (release 1.10, D-184, REQ-OUT-07): in the pinout tables a cable pin without a signal of its own shows the signal and the interface of the wires that end on it (`tables.wire_signals`, different values sorted and joined with `;`; `_pin_rows(..., carried)`; the verifier derives them again with `_harness_carried`); a pin of its own keeps its value. The wire list gets a *Requirement* column after *EMC class* and `traceability.csv` one after *Routed* (before *Kind*) only while an interface has a `requirement_id` (`tables.uses_requirements`; `verify._trace_header`), so a project without requirement IDs keeps both tables. `tests/test_signal_requirement_columns.py`.
- Units of `export.json` (release 1.13, D-195): the object `field_units` comes from the one table in `outputs/export_units.py`; a numeric field added to the model needs an entry there (`tests/test_export_units.py` fails without it); `verify.py` reports `out_json` for a number with no unit when the file has `field_units`.
- Pair parts (release 1.11, D-188): the BOM (`tables.bom`) and the mass (`generate/mass.py`, and `tables.mass_length` through it) divide a wire's length by `Part.conductors`; `verify.py` does the same on its own in `_bom_rows` and `_mass`, so a change to one counting rule must change both. Only the BOM, the mass table and `export.json` of the examples changed with it. `tests/test_pair_part_counts.py`.
- Loose ends (M4b, D-201, REQ-OUT-11): `tables.is_open_end`, `part_text`, `mates_text` and the constants `OPEN_END`, `OPEN_END_PART` (the BOM line `(open end)`), `OPEN_END_TEST` word a connector of role `loose` in the pinouts, labels, BOM, tests and WireViz file; `drawing.py` draws it dashed with `data-ref` `part/ID` and `end/ID`; `buildsheet._connector_sheet` writes *open end, to fill in*; `generate/mass.py` never counts it (`open_end_missing`); `asbuilt._parts_of` leaves its part out; `vcs/diff.kind_name` says *Loose end*. `verify.py` states every word again (`_OPEN_*`, `_drawn_open_ends`, the Connectors heads). Only a harness with a loose end changes; its golden set is `tests/fixtures/outputs/loose_ends.json` and `loose_ends/` (`tools.gen_output_goldens`, built by `tests/loose_support.generated_loose`).
- The `.ods` writer (3.0.0, D-242, pull request 2 of `docs/ait/DESIGN_3.0_HARNESS_PLAN.md`): `core/outputs/ods.py` turns a frozen model (`Workbook`, `Sheet`, `Cell`, `Style`, `Condition`, `Page`) into the same bytes for the same model (stored entries, fixed dates, `create_system` 3) and refuses a formula outside the closed list of section 7.2 (`check_formula`). It imports only the standard library and the core (`tests/test_offline.py`, `STDLIB_AND_CORE_ONLY`); `tests/test_ods.py` holds a golden digest of its sample, made again on purpose only. Its caller is the harness plan.
- The print set-up of the `.ods` writer (4.1.0, pull request 4 of `docs/ait/DESIGN_4.1_PRODUCTION_SHEET.md`, section 5.1): `Page.scale` (10 to 400 %, `ods.SCALES`, `style:scale-to`; not with `fit`), `Sheet.repeat_rows` (first and last row, 0-based, inside `table:table-header-rows`) and `Sheet.breaks` (rising, 0-based, not inside the heading rows; row style `ods.BREAK_ROW`). Each writes nothing while off, so the sample digest of `tests/test_ods.py` stays; the heading rows and each break start a group of their own in `_table_xml`, so `_repeat_rows` merges no run across them. A reader of the rows must walk into `table:table-header-rows` (`verify_plan.read_cells` and `tests/plan_support.py` iterate with `iter`, so they do; a regex for a bare `<table:table-row>` misses a break row). `tests/test_ods_print.py` has its own sample and digest and, with LibreOffice, reads it back and counts its PDF pages.
- The harness plan (3.0.0, D-242, pull request 3 of the same design): `core/outputs/harness_plan.py` builds the model of `harnesses/<ID>/<ID>_plan.ods` (`plan_workbook`, `plan_ods`), written by `build_outputs(..., harness_plan=True)` only (off by default, so the output-hash baseline does not move). Like the writer it imports only the standard library and the core. Every formula carries its stored value; `tests/plan_support.py` is the tests' own reader and evaluator, and `tests/test_harness_plan.py` checks every formula of the goldens' plans with it. A change of the layout renews `tests/fixtures/outputs/harness_plan/` with `tools.gen_output_goldens` (on purpose). The verifier does not check the plan until pull request 4; keep `plan_sides`, `direction_word` and `lookup` the one place of their rules, so that its copies can be compared with them.
- The check of the harness plan (3.0.0, D-242, pull request 4 of the same design): `core/outputs/verify_plan.py`, called by `verify_outputs` (`verify_plans`) for each plan the manifest lists, must not import `ods.py` or `harness_plan.py` (`tests/test_verify_plan.py` reads its imports; it imports only the standard library and the core, `tests/test_offline.py`). It states every cell of the layout a second time (`expected_plan`), with its own `plan_sides`, `direction_word`, `mirrored` and `lookup`, compared with the core's by Hypothesis; it reads the package with ElementTree after refusing a DOCTYPE or ENTITY declaration, as `core/kicad.py` does, and evaluates every formula of the closed list (`parse_formula`, `Evaluator`). Its codes are `out_plan_package`, `out_plan` and `out_plan_formula`; the stamp is read from the About sheet (`plan_stamp`, `out_stamp`). A change of the plan's layout changes both modules: the random-plan test of `tests/test_verify_plan.py` fails until they agree.
- Splices in the harness plan (3.0.0, D-242, pull request 6 of the same design): `plan_sides` leaves the splices out and joins two connectors when wires reach both through splices (`harness_plan.joined_wires`, built on `core/nets.splice_ids`; only a splice node joins wires, a plug pin with two wires does not); a near row's far pins are every far pin its wire reaches that way, each with the wire that ends on it. `verify_plan.py` has its own `spliced` and `plan_sides`; the random harnesses of `tests/test_verify_plan.py` hold up to two splices. `tests/test_plan_splices.py` has the cases of section 11 (*Branching*) and the mutations; the golden `harness_plan/splices` is `tests/splice_support.branch_leg_project`.
- The `.ods` writer (3.0.0, D-242, pull request 2 of `docs/ait/DESIGN_3.0_HARNESS_PLAN.md`): `core/outputs/ods.py` turns a frozen model (`Workbook`, `Sheet`, `Cell`, `Style`, `Condition`, `Page`) into the same bytes for the same model (stored entries, fixed dates, `create_system` 3) and refuses a formula outside the closed list of section 7.2 (`check_formula`). It imports only the standard library and the core (`tests/test_offline.py`, `STDLIB_AND_CORE_ONLY`); `tests/test_ods.py` holds a golden digest of its sample, made again on purpose only. No caller until the harness plan (pull request 3).
- Splices (format 3, M6a): only a harness with a splice changes (`nets.has_splices`): `tables.tests` per pair of ends of a net through a splice (`VIA`, `SPLICE_ISOLATION`), the last wire-list column `Via`, no label for a splice, not a connector of the mass table (its mass only under `full_bom`, `generate/mass.py`), the splice block of the *Connectors* sheet (`buildsheet.SPLICE_BLOCK`; a node takes no contact), `drawing._draw_splice` (`data-ref` `splice/ID`), `style: simple` in `wireviz.yaml`. `verify.py` words each of them again with its own nets (`_nets`, `_SPLICE_*`).
- The command line of the harness plan (3.0.0, D-242, pull request 5 of the same design): `export --harness-plan` (`cli/main._export`), `harness_plan_exported(folder)` and `harness_plans_in` read the manifest as `drawings_exported` does, and the re-export at a release (`cli/changes._restamp`) and `api.export(harness_plan=)` keep the choice; `ExportResult` lists the plans (`harness_plans`, `harness_plans_removed`). The Cover's data is set by `core/document.py` (`plan_document_edit`, one `SetMeta`, the command `document` in `cli/document_cmd.py`). The notes of `check` on the plans (`plan_colour_example`, `plan_colour_missing`, `plan_document_unknown`) are `core/validation.plan_notes` with `harness_plan.colour_notes`; they are not issues of `configcheck.validate`, because those stop generation.
- The search boxes of the harness plan (3.1.0, D-250, section 25 of the same design): `I2:I3` and `M2:M3` of the harness sheet and a conditional format on `I` and `M` of every near block (`harness_plan.search_format`); `ISNUMBER` and `SEARCH` are in `CONDITION_FUNCTIONS` only, in `ods.py`, `verify_plan.py` and `tests/plan_support.py` (`evaluate(..., condition=True)`, `read_conditions`, `marked`). Every `.ods` holds `ods.CALCULATION_SETTINGS` (regular expressions and wildcards off), which `verify_plan.check_settings` checks; `tests/test_plan_search.py`.
- The row layout in the outputs (4.0.0, D-251, pull request 3 of `docs/ait/DESIGN_4.0_ROW_LAYOUT.md`): only a project in which a connector has a layout changes. `tables.PIN_ROW` is the last column of `box_pinouts` (while some box connector has one; `devices.pinout_sheet` drops it again for a device without one, for `export-pinout`) and of `pinouts` (while a connector of the harness has one), filled from `row_layout.layout_of`. `harness_plan.con_sheet` writes *Pin row* in F and keeps `ConSheet.pin_rows` and `order`; `near_rows` follows `order` and `pin_row` copies F into A (`COL_A`). `verify.py` and `verify_plan.py` read the rows with `verify_plan.face_rows` (their own resolution, never `core/row_layout.py`; `tests/test_row_layout_outputs.py` reads their imports and compares it with the core's by Hypothesis). `export.json` needs nothing new: `row_layout` is a sparse model field. The golden set is `tests/fixtures/outputs/row_layout*` and `harness_plan/row_layout*` (`tests/row_layout_support.row_layout_project`).
- Label formats (1.15.0, D-198): `tables.wire_label_texts` and `connector_label_text` write the labels table and the Labels sheet in the format of `model.label_format`; `verify.py` words them again for every format with its own copy of the template rules (`_LABEL_*`, `_label_template_usable`, `_fill_label`, never `core/label_format.py` or `tables.py`). A change of a format or of the template rules changes both: `tests/test_label_format_outputs.py` reads the imports, compares the copy with the core's by Hypothesis and exports an example in every format.
- Adding an output file: build it in `build_outputs`, add its check to `verify.py` with a mutation test, regenerate goldens, document it in `docs/OUTPUTS.md`.

## Build data layout (1.7.0)
`core/build_data.py` (D-170: `plan_set_strip`, `plan_set_strip_all`, `plan_set_contacts`, `plan_set_part_tool`, `plan_set_accessory`, `plan_delete_accessory`, `check_accessory`; pure plans of ops, one undo step, a released harness refuses with the reason) and `core/build_data_import.py` (`plan_build_data_import`: the kind of table is told by its headings, every row gets a verdict, a refused row stops the whole import; used by `cli/data.py` `import-build-data`). The data: `Wire.strip_a_mm`, `Wire.strip_b_mm`, `Pin.contact_part`, `Part.tool`, `Harness.accessories` (a list of `Accessory`); all sparse (`OMIT_WHEN_DEFAULT`, left out of the files while empty) and a person's values: the tool computes nothing from them and sets no default. Generation keeps them (`generate/engine.py`; the contact of a unit pin is copied to the cable pin, so for a generated harness it is set on the unit's pin in the Devices tab). `core/integrity.py` has `dangling_accessory`; `vcs/diff.py`, `vcs/snapshot.py` and `vcs/lockview.py` carry accessories and the contact parts for change control. Where the values show: optional columns in `outputs/tables.py` (only when used), `accessories.csv`, and always in the build workbook (`core/outputs/buildsheet.py`, whose cells read *to fill in* when empty); `outputs/verify.py` checks all of it. Editing: *Edit wire* (strip lengths), the Devices pin table (*Cable contact…*), the Connectors and Accessories tabs, the Inspector (*Crimp tool* of a contact part). Templates: `strip-lengths.csv`, `pin-contacts.csv`, `accessories.csv`. User manual: `docs/user-manual/enter-the-build-data.md`.
- Block diagram looks (REQ-GUI-25): `core/outputs/system.py` draws each card of `system/block_diagram.svg|pdf` (and Export diagram, `gui/diagram_export.py`) with a band and a badge from `core/outputs/looks.py` (a `Shape` item of `core/outputs/canvas.py`: SVG `<path>`, PDF `m l c h` operators, painted by `gui/diagram_export.py` and `gui/preview.py`), in the light colours of `core/device_kinds.ACCENTS`, plus a key to the kinds. Only `block_diagram` has them (`_diagram(..., looks=True)`); `harness_overview` is as it was. Coordinates are rounded when made (`core/pictograms.py`) and written with three decimals, so the bytes are the same on every platform. Changing a look renews the block diagram entries of `docs/ui/OUTPUT_HASHES_BASELINE.json`, `tests/fixtures/numbers/snapshot.json` and `tests/fixtures/outputs` with the tools, with a reason in `docs/changes.md`.
